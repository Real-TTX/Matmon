# CLAUDE.md

Guidance for working in this repository. Keep it in sync with the code - update it whenever architecture, persistence, interfaces, or major data flow change.

## What Matmon is

A lightweight, self-hosted network monitoring platform (a compact PRTG-style alternative) for home / small-business networks. ASP.NET Core on **.NET 10**, C#, Razor Pages UI, Docker-first. **Proprietary** (was MIT; relicensed before any public download - see `LICENSE` and `docs/matmon-cloud-and-licensing.md`). Published images: `ghcr.io/real-ttx/matmon` + Docker Hub (`matmon`).

## Build / run / verify

- **Requirements:** .NET 10 SDK (developed against `10.0.203`), Docker Desktop or compatible runtime.
- **Build:** `dotnet build Matmon.slnx` (note: `.slnx`, not a classic `.sln`).
- **Run locally (dev):** `dotnet run --project src/Matmon.Host` → http://localhost:5084 (`ASPNETCORE_ENVIRONMENT=Development`). Default login `admin` / `admin`. For a live loop use `./scripts/dev.ps1` (`dotnet watch run`) - rebuilds/reloads on every change so the browser always shows current code.
- **Run via Docker:** `docker compose up --build` → primary on http://localhost:8099, sample secondary probe on http://localhost:8100.
- **Health check:** `GET /healthz` and `GET /api/mode` (both anonymous).
- **Tests:** `dotnet test tests/Matmon.Tests/Matmon.Tests.csproj` (xunit). Baseline covers the pure core logic (threshold parsing/evaluation, channel-threshold escalation, schedule calculator, settings inheritance). Coverage grows with each refactor.

## Solution layout

Two projects under `src/`:

- **`Matmon.Core`** - framework-free domain. `Domain/` holds the monitoring model, the `ISensorExecutor` implementations, inheritance/threshold/schedule logic, notifications. `Sample/` holds the default sample topology (`SampleTopologyFactory`).
- **`Matmon.Host`** - the web app.
  - `Program.cs` - startup, cookie auth, authorization policies, minimal APIs (probe heartbeat/assignments/observations/discovery), sensor-executor DI registration, mode-dependent hosted services.
  - `Services/` - persistence, polling, probe registry, dashboard/config providers, backup scheduler, slave (secondary) workers.
  - `Pages/` - Razor Pages UI (`.cshtml` + `.cshtml.cs`). Shared layout in `Pages/Shared/_Layout.cshtml`.
  - `wwwroot/` - `css/site.css` (large, ~9k lines), `js/site.js`, Bootstrap 5 + jQuery under `lib/`.

## Architecture: primary / secondary / executor

Mode is set via `Matmon__Mode=Primary|Secondary|Executor` (default Primary; `AppMode` in `Matmon.Core`, string aliases master/slave/executor).

- **Primary** owns the UI, configuration, alerts, history and global state. Registers `SensorPollingService` + `BackupSchedulerService`. Exposes the `/api/probes/*` endpoints that secondaries call.
- **Secondary** connects **outbound** to the primary (works behind firewalls/NAT), pulls assigned sensor work, executes it, and POSTs results back. Registers `SlaveHeartbeatService` + `SlaveSensorWorker`.
- **Executor** is a **stateless sensor-executor service** for Matmon.Cloud's cloud sensors: **no workspace, telemetry, auth-cookie, UI or background loops**. `Program.cs` branches early on `AppMode.Executor` and builds a minimal app registering only the sensor executors (`RegisterSensorExecutors(..., includeProbeSensors:false)` - probe heartbeat/health need probe infra + are meaningless in the cloud) + `StatelessSensorRunner`. Two token-authed endpoints (`X-Matmon-Executor-Token` = `Matmon__ExecutorToken`, `FixedTimeEquals`, `IsExecutorAuthorized`): `GET /api/sensor-catalog` (the runnable `SensorDefinition`s - `StatelessSensorRunner.Catalog` filters `SensorDefinitionCatalog.BuiltIns` to registered types) and `POST /api/execute` (`ExecuteSensorRequest{sensorTypeKey,target,parameters,timeoutSeconds,credential{kind,values}}` → runs one `ISensorExecutor` via the same context/credential-mapping as Primary/Secondary → returns `SensorExecutionResult`). Nothing is persisted. `SensorDefinitionCatalog.BuiltIns` (Host/Services) is the single source of the built-in definition list, shared by the store's `EnsureSensorDefinitionCatalog` and the executor. This is how cloud sensors reuse 100% of the executor code with the RCE/native-deps surface isolated in a sidecar (see Matmon.Cloud).
- Probe auth: a per-probe token sent as `X-Matmon-Probe-Token` header or `?token=` query (`ReadProbeToken` in `Program.cs`; validated via `IMonitoringWorkspaceStore.TryValidateProbe`).
- **Heartbeat full-sync:** the secondary heartbeat (`ProbeHeartbeatRequest`) also carries system details - OS, host name and reachable IPv4 subnets (CIDR), collected by `ProbeSystemInfoProvider`. The primary keeps them on the in-memory `ProbeStatusSnapshot` (`InMemoryProbeRegistry`). They surface on the probe **Usage** page ("System & networks" panel; the local primary reports itself) and the scoped probe's reported subnets are folded into **Discovery**'s subnet suggestions. The new heartbeat fields are optional (backward-compatible).

## Domain model

Tree of `MonitoringElement`s: `ProbeElement` → `FolderElement` → `HostElement` → `SensorElement` (see `Matmon.Core/Domain`). Settings and credentials are **inheritable** from parents; a sensor overrides only the fields that differ (`MonitoringInheritanceResolver`). Thresholds per channel: `SensorThresholdEvaluator`. Scheduling: `MonitoringSchedule` / `MonitoringScheduleCalculator`.

**Default conditions** (`Matmon.Core/Domain/SensorThresholdDefaults`) - the single source of sensible per-sensor-type, per-channel warning/critical thresholds (CPU/mem/disk % 85/95, latency ms, UPS battery %, SMART status, cert days, …). Two uses: it seeds the Thresholds-editor placeholder + comparison for a channel (`TryResolve`, wired through `Workspace.TryGetDefaultThresholdRule`), and `Apply(type, settings)` bakes those thresholds onto a **new** sensor's own settings on create (only where the user hasn't set one) so it alarms sensibly out of the box. Wired at the two user-facing create paths (`store.CreateSensor` - manual create + discovery apply); the internal demo/provision seeders and the auto-created probe heartbeat/health sensors are intentionally left alone (heartbeat state stays driven by `FromHeartbeatAge`, not a channel threshold). Deliberately no defaults on cumulative counters (interface errors, container restarts) or redundant/overlapping channels (one clear signal per condition). SSL keeps its own `EnsureDefaultThresholds` (it also migrates the legacy `ssl.warningDays/criticalDays` params).

**Tags** (`MonitoringElement.Tags`, `MonitoringTemplate.Tags`) are free-form labels that **cascade**: a sensor's *effective* tags are its own plus every ancestor's (`MonitoringTagResolver.ResolveEffective`; `Normalize`/`Parse` clean + dedupe). Template tags merge into an element's own tags on apply (copy semantics). Tags show as chips on the Sensor Detail header (inherited ones styled subtly) and on monitoring tree/list nodes (own tags), and the monitoring search box matches tags so you can filter the tree by tag.

**Element picker** (`Pages/Shared/_ElementPicker.cshtml` + `Ui/ElementPicker.cs` + `initializeElementPickers` in site.js) is the reusable replacement for long element/sensor `<select>` dropdowns: a field that looks like a `workspace-input` but opens a modal that shows the topology as an **indented tree** while browsing and a flat **tag-filterable** path list while searching (`is-flat` toggled by the filter; `ElementPickerOption.Depth` drives indentation), single-select, writing the chosen id into a hidden input (fires `change`). Client-side filtering, so it stays instant regardless of element count. Rolled out to: notification rule Target, **map tile Target**, and every **parent/target select** (SensorCreate/SensorAssistant/ElementEditor - carrying `data-sensor-parent-select` so the preview re-post still fires - plus FolderCreate/HostCreate/ProbeCreate). `WorkspacePageViewModel.PickerElements` + `Model.PickerOptionsFor(validOptions)` build the per-context option set from the legacy `SelectListItem` ids. *(Discovery's scope-probe select is a separate `DiscoveryModel` page and still a plain select.)* For map tiles the picker's hidden value carries `data-map-property-element` + `data-selected-name` so the map designer's change-sync/preview keep working, and `addTile` re-runs `initializeElementPickers` for cloned tiles. Tag fields (ElementEditor/TemplateEditor/SensorCreate/SensorAssistant) are progressively enhanced into a **chip editor** (`data-tag-input` + `initializeTagInputs`); the original input stays as the hidden comma-joined value.

**Tag-as-target** (`MonitoringTargetResolver` in Core - pure token parse/format; `IMonitoringWorkspaceStore.ResolveTargetSensors(token)` - topology resolution): a target is a single string token that is either an element id (GUID) or a tag, written `tag:<name>`. A picker with `AllowTags=true` shows an **Element ⇆ Tag** toggle plus a selectable tag list; choosing a tag writes the `tag:<name>` token into the hidden value and the trigger shows `# <name>`. `ElementPickerModel.SelectedValue` (string, wins over `SelectedId`) round-trips the token; `is-tag-mode` (root class) + `setMode` in `initializeElementPickers` flip the two lists. A **tag** target resolves dynamically to every sensor whose *effective* tags include it (cross-tree aggregation, same as a folder subtree). Wired so far: **map tiles** - `MonitoringMapTile.TargetTag` (mutually exclusive with `ElementId`); `MapEditor`'s `MapTileInput.TargetToken` parses into `ElementId`/`TargetTag` via the resolver; `MapDisplayProvider.BuildTagAggregateTile` → the shared `BuildAggregateFromSensors` rolls the matching sensors up (worst state + healthy count) exactly like a container tile. *(Notification rule targets still store a plain `TargetElementId` (+`IncludeDescendants`); tag-as-target matching for rules is not wired yet.)*

**Notification dispatch (N0 - email).** Alerts are actually delivered now (previously the whole model/config/templates existed but nothing fired). When an alert is **raised**, `SyncSensorAlertFromObservation` enqueues a lightweight `AlertNotificationEvent` via `INotificationSink` (`NotificationSpooler` - a bounded, dependency-free queue, so no DI cycle with the store; enqueue is under `_gate` but non-blocking, off the hot path). The Primary-only `NotificationDispatchService` (BackgroundService, 5s tick) drains the spooler, matches **enabled email** `NotificationRule`s (`TriggerStates` + `TargetElementId`/`IncludeDescendants` ancestry walk), resolves the SMTP sender (rule `SenderId` → `NotificationSender.Email`, else workspace `NotificationConfiguration.Email`) and recipient (rule `Recipient` else `ReceiverId` → `NotificationReceiver.Target`), renders subject/text/html via `NotificationTemplateRenderer` from a context built off the alert/element/latest observation, and sends via `MailKitEmailSender` (MailKit). **Retry spooler:** each delivery is retried with backoff (0s/30s/2m/10m/30m, 5 attempts) then logged+dropped; **in-memory only** (a restart mid-retry loses pending sends). **Anti-spam (N1):** `NotificationThrottle` (Core, unit-tested) is a rolling rate limit per (rule, element): at most `NotificationRule.Threshold` "raised" mails per `NotificationRule.CooldownMinutes` window (it tracks recent send timestamps per key; a null/≤0 threshold = 1, which reduces to the classic "one mail per window" - backward compatible). New rules default to 15 min / 5. With the persist-until-ack model this is the practical flap suppression. **Recovery mails:** the store enqueues a `Recovered` event when an alarm clears; the dispatcher sends a "Recovered" mail but only to a rule that actually sent the raise this episode (`NotificationThrottle.IsEpisodeActive`), so a cooldown-suppressed re-raise produces no recovery spam either. **Unified Notifications UI.** The `/Notifications` page (`@model WorkspaceModel`, `@inject IMonitoringWorkspaceStore` for the report) is **one list of both notification types** with a client-side filter toolbar (All / **Trigger** / **Scheduled** + name search) and add-actions below: the alert-based `NotificationRule`s (Type = Trigger, edited on `/NotificationRuleEditor`) **and** the single scheduled summary report (Type = Scheduled, edited on the new `/NotificationReportEditor`). **Rules, Senders and Receivers are three client-side `.sensor-tabs` on the single `/Notifications` page** (not separate pages) - the URL stays `/notifications` so the sidebar nav stays highlighted; `data-tab-hash` gives `#senders`/`#receivers` deep-links, and add/edit links carry `returnUrl=/notifications#senders|#receivers` so an editor save returns to the right tab. The old `/notifications/senders` + `/notifications/receivers` routes are kept as 302 redirects to the hash (bookmarks / editor back-links). Each rules row carries `data-notif-type`/`data-notif-name` for the inline filter. A **built-in virtual receiver** (`NotificationReceiverDefaults.AllUsersReceiverId`, "All users") is offered in every receiver picker (rules + report) - not persisted, injected into `BuildNotificationReceiverOptions` + the report editor - and expands at send time to all enabled users' e-mails via `IMonitoringWorkspaceStore.ResolveAllUsersRecipients()` (honoured in both `NotificationDispatchService.ResolveRecipient` and `SummaryReportSender.ResolveRecipients`), so new users are covered without maintaining a recipient list.

**Scheduled summary report (N3).** `SummaryReportSettings` (on `WorkspaceDocument`) is admin-configured on the **`/NotificationReportEditor`** page (the "Scheduled" entry in the unified Notifications list - **moved out of System/Config**, which now shows only a redirect note): enabled, daily/weekly, hour, weekday, subject, AttachPdf, and - like a trigger rule - an optional **`SenderId`** (SMTP endpoint) + **`ReceiverId`** (recipient), falling back to the workspace default SMTP + the free-text `Recipients` string. `SummaryReportSchedule` (Core, pure, tested) decides when a slot is due; `ReportSchedulerService` (Primary-only, 1-min tick) sends when due and records `LastSentUtc`. `SummaryReportDataCollector` gathers uptime (from the per-window statistics buckets, deduped), counts and recent events; `SummaryReportBuilder` (Core, pure, tested) renders subject+text+HTML; `SummaryReportSender.SendAsync` resolves sender/recipient from the settings (`ResolveSmtp`/`ResolveRecipients`) and sends via the MailKit sender (also wired to a "Send now" button). *(The old Config `OnPostSaveSummaryReport`/`SendSummaryReportNow`/`DownloadAuditPdf` handlers still exist but are unreachable - superseded by the editor page.)* **PDF audit report (N4).** `AuditReportPdfBuilder` (Host, QuestPDF - Community license set in `Program.cs`) renders a customer-facing PDF (summary cards, sensor-uptime table, recent-events table, page footer) from the same `SummaryReportData`. `SummaryReportDataCollector.Collect` takes a `maxSensorLines` (short list for the e-mail body, fuller list for the PDF). Wired two ways: the **Reports** tab has a "Download audit PDF" button (`SummaryReportSender.BuildAuditPdf`), and enabling **Attach PDF** (`SummaryReportSettings.AttachPdf`) attaches it to the scheduled e-mail (`INotificationEmailSender.SendAsync` gained an optional `EmailAttachment` list). Not yet done: batching/digest, webhooks. *(Note: `tests/Matmon.Tests` now also references `Matmon.Host` so the PDF builder can be unit-tested - it asserts real `%PDF` output.)*

**Templates** (`MonitoringTemplate` + `TemplateEditor`) are **copy + origin**, not live inheritance. Applying a template (at sensor creation, or via the edit page / Templates "apply") bakes the template's resolved settings into the element's own `Settings` and records `MonitoringElement.TemplateOriginId`. Editing the template afterwards does **not** change existing elements; a "Restore from template" action re-copies the current template values (template wins). `ApplyTemplateCopy` (Workspace.cshtml.cs) is the single entry point; create lets the user's form values win, re-apply/restore lets the template win. The legacy live-inheritance list `AppliedTemplateIds` is no longer populated - `MigrateAppliedTemplatesToCopies` (store ctor) bakes any remaining links into `Settings` + sets the origin + clears the list on load. The TemplateEditor "Impact" tab lists sensors whose origin (directly or via the template's parent chain) is this template. Templates still chain via `ParentTemplateId` (resolved when copied).

**Sensors** are `ISensorExecutor` implementations registered in `RegisterSensorExecutors` (`Program.cs`): Ping, HTTP (+ HttpAdvanced), SNMP (+ interface/UPS), Synology NAS/Health, **Proxmox Health** (`proxmox-health`, cluster: quorum, nodes online, VM/container/storage rollups) and **Proxmox Node Health** (`proxmox-node-health`, per-node CPU/mem/disk + VM/container online/offline; `pve.node` selects a node, else the first visible one) - both thin wrappers that clone settings + set `pve.scope` and delegate to `ProxmoxPveSensorExecutor` (kept as the internal shared REST/auth engine + parameter source; the legacy selectable `proxmox` scope-based type was **retired** - not in the catalog nor DI-registered); the shared `AppendResourceTypeChannels` always emits `vmOnline`/`vmOffline`/`containerOnline`/`containerOffline` (+ totals) and storage online/offline, **VMware Health** (`vmware-health`, vSphere **SOAP/vim25** API at `/sdk` - works on vCenter *and* standalone ESXi: hosts connected, VM power rollup, datastore usage) + **VMware Host Health** (`vmware-host-health`, per-ESXi-host CPU/mem from `summary.quickStats` + VM online/offline on that host; empty list = nothing runs; surfaced read-only on the System/general page; the path is picked as a **dropdown** (`program.base`, options built from the allow-list at startup) plus an optional `program.relative` for a program under an allowed directory; ## Persistence (important - and the current bottleneck)

App state lives in a single JSON workspace file (`data/workspace.json`, configurable via `Matmon__WorkspacePath`), loaded and held entirely in memory by `Services/InMemoryMonitoringWorkspaceStore.cs` (~3700 lines; still large - decomposition is Phase B, in progress). The state is one private `WorkspaceDocument` with 13 collections, guarded by `_gate`. The class is now `partial`, split by concern into sibling files: `InMemoryMonitoringWorkspaceStore.Backup.cs` (backup/restore), `.Persistence.cs` (load/save: `LoadDocument` - runs `NormalizeLoadedDocument` to null-coalesce every singleton (`CloudSettings`/`NotificationConfiguration`/`SummaryReport`/`Cloud`) + collection so a `null` in `workspace.json` can't NRE the host, e.g. a null `cloudSettings` previously crashed the whole host via `TunnelClient` - the debounced `QueueSave`/`SaveDocumentLocked`, `.bak` refresh) and `.Telemetry.cs` (the telemetry facade: `RecordSensorObservation`, history/event/statistics getters, `RunTelemetryMaintenance` rollup+retention, `CleanupStorage`, `MigrateDocumentTelemetryIntoRepository`). The core `.cs` (~3100 lines) keeps topology/template/notification/user/map CRUD, alerts, credentials, defaults and the sensor-definition catalog. There is **no relational database for app state**; the `Microsoft.Data.SqlClient` dependency is only for the MSSQL *sensor*.

- Saves are debounced via a timer with two priorities: `Configuration` (~750ms) and `Telemetry` (~10s, max 30s dirty delay). `SaveDocumentLocked` serializes the **entire** document to a temp file then atomically moves it; a full-file `.bak` copy is refreshed every 5 min. Section-based backups live under `data/backups/`.
- Data-protection keys: `data/dataprotection-keys`. Runtime `data/` is gitignored.
- **Retention & statistics are per-sensor-type by default.** `Matmon.Core/Telemetry/SensorTelemetryProfiles` maps each sensor type to a profile (raw-observation days, statistics bucket minutes, statistics-retention days, event-retention days): *Responsive metrics* for latency/throughput sensors (raw 3d, hourly buckets, stats 14d), *Availability* for up/down sensors (raw 3d, daily buckets, stats 14d, events 90d), *Infrastructure* for probe sensors (raw 2d, stats 14d), and *General* as the fallback (raw 3d, hourly, stats 14d). (Defaults are deliberately lean - ~3 days raw + ~2 weeks of statistics - to keep `telemetry.db` small; bump per-sensor for a longer history.) An explicit `MonitoringSettings` override on the sensor/its ancestors always wins; the profile is only the fallback. The ElementEditor surfaces this as a visible **Telemetry & retention** section that shows the active profile and uses it for the field placeholders.
- **Poll cadence is per-sensor-type by default too.** `Matmon.Core/Domain/SensorScheduleDefaults` maps each type to a fallback poll interval in three intent-driven tiers: **ping 30s**; slow-changing infra (the per-platform disk sensors + backup-job) **6h**; rarely-changing (windows/linux/synology-update + ssl-certificate/certificate-chain) **once a day**; everything else the `Default` **5min**. A hard `Minimum` 15s floor clamps every result. `SensorPollingService` uses it as the `IsDue` fallback so a sensor with no explicit `PollingInterval` polls at a sane type-specific rate. An explicit schedule on the sensor/its ancestors still wins. **The service ticks every 5s, computes the due set (any non-paused, enabled, local sensor whose last observation is older than its interval - this is how catch-up works after downtime or resuming a paused sensor/folder: a single catch-up poll, no backfill), sorts it most-overdue-first (never-run first) and runs it through a bounded worker pool (`Parallel.ForEachAsync`, one DI scope per execution, store writes serialized on `_gate`).** Worker count = `MatmonRuntimeOptions.PollingWorkers` (`Matmon__PollingWorkers`, default 8, min 1), surfaced read-only on the System/Config page. So one slow/timing-out sensor no longer blocks the rest of the cycle.
- **Statistics are accurate, downsampled aggregates - not a running average - and are stored per channel.** `SensorStatisticsBucket` carries avg/min/max, the low/high percentile (bottom 1% / top 1%) and a healthy/warning/critical distribution (→ uptime %); `DefaultChannelKey` is the channel identity. `Matmon.Core/Telemetry/TelemetryRollup.AggregatePerChannel` (pure, unit-tested) emits one bucket **per numeric, non-virtual channel** per window (a bare value with no channels folds into a `"default"` bucket); `Aggregate` (single default-channel) is kept for the unit tests. The SQLite `sensor_statistics` PK is `(sensor_id, bucket_minutes, bucket_start, default_channel_key)`; `SqliteTelemetryRepository.MigrateStatisticsToPerChannelKey` rebuilds an older 3-column-PK table once (existing rows keep their channel key, so prior history survives as the then-primary channel). `StatisticsRollupService` (Primary-only, every 5 min) calls `IMonitoringWorkspaceStore.RunTelemetryMaintenance`, which recomputes the recent buckets per sensor/channel from raw data **and** applies all telemetry retention (raw/statistics/events) **plus resolved-alert retention** (keeps every active alert but caps the resolved tail to the newest 500 within the event-retention window, so `_document.Alerts` - Alerta-style persist-until-ack, previously never pruned - and `workspace.json` stay bounded; the AlertRaised/Resolved events keep the audit trail). The Alerts page also renders only active alerts + the newest `ResolvedRenderCap` (200) resolved rows into the DOM (tab counts still use the full set) so a long history doesn't inflate the page. Pruning and aggregation are therefore **off the polling hot path** - `RecordSensorObservation` only appends the raw observation, its state-change event and the alert sync. The SensorDetails Statistics tab shows one channel at a time (the "primary"/graph channel by default) with a **Channel** selector (`StatsChannel`) when a sensor has multiple channels with stats. **Per-channel logging is opt-out:** each channel value carries `SensorChannelValue.LogByDefault` (executors set it `false` for noise like boolean up/valid flags - e.g. SSL `valid`, TCP `open`); the user can override it per channel via a "Log to statistics" checkbox in the Channels & thresholds editor, stored as `MonitoringSettings.ChannelLogging` (channel key → bool, inheritable + trimmed like `ChannelVisuals`). `RunTelemetryMaintenance` reads `GetChannelLogOverrides` and passes it to `AggregatePerChannel`, which skips channels resolving to not-logged (`override ?? channel.LogByDefault`). **Virtual `sensorState` channel:** `SensorExecutionResultHelper.ApplyDefaultChannelSelection` (called centrally in `SensorExecutionService`) prepends a virtual `sensorState` channel to every result (`1` = healthy, `0` = problem, `IsVirtual = true`); it's excluded from the statistics rollup (numeric, non-virtual only) but **is** surfaced in the Channels & thresholds editor as a read-only row - no thresholds, but it can be picked as the **primary/default channel** (→ `MonitoringSettings.DefaultChannelKey = "sensorState"`, honored by `ApplyDefaultChannelSelection`) and given a visual/logging. `WorkspaceSensorChannelThresholdFieldInput.IsVirtual` drives the read-only rendering in `_SensorThresholds` (the `BuildSensorChannelHints` `!IsVirtual` filter was removed; virtual channels sort last). **Dynamic (script) sensors don't fabricate channels:** `BuildSensorChannelHints` no longer synthesizes a placeholder row from `defaultChannelKey` - a dynamic sensor with no observation shows an empty-state ("channels appear after the first run") and its channels are only the ones from the latest observation (plus any the user adds manually). A managed channel key (has stored thresholds/visuals/logging) that isn't in the latest reported channels is flagged `WorkspaceSensorChannelThresholdFieldInput.IsOrphaned` (only once the sensor has actually reported channels) and rendered as a dimmed "no longer reported" row with a delete affordance - never auto-pruned, so config survives a transient empty run. `SensorThresholdEditorState.visibleCount` is driven by real (reported/configured) rows, so a fresh dynamic sensor shows no blank channel cards.
- **Telemetry now lives in SQLite (Phase A done).** `Matmon.Core/Telemetry` holds `ITelemetryRepository` (storage contract for observations/events/statistics) and the embedded `SqliteTelemetryRepository` (WAL, `Microsoft.Data.Sqlite`). `InMemoryMonitoringWorkspaceStore` delegates all telemetry storage/queries/prune/cleanup to it; the `SensorHistory`/`Events`/`SensorStatistics` collections on `WorkspaceDocument` are kept only as a backup/restore transport and are **always empty in `workspace.json`** (cleared on load). On startup `MigrateDocumentTelemetryIntoRepository` moves any telemetry found in an existing `workspace.json` into `telemetry.db` once (only when the DB is empty), then drops it from the JSON. DB path: `data/telemetry.db` (override `Matmon__TelemetryPath`). The former save bottleneck is gone - telemetry saves no longer re-serialize history. Backup create pulls the selected telemetry sections from the repo into the snapshot; restore pushes them back via `ReplaceAll*`. **Perf:** the repo keeps an in-memory latest-observation-per-sensor cache (`_latestBySensor`), so `GetLatestObservations`/`GetLatestObservation` (dashboard + polling hot paths) never scan the table; WAL is checkpoint-truncated on startup and after bulk imports, with `wal_autocheckpoint` on. Without this the dashboard did a full-table window scan per load (~15s on a real DB).

## Auth & authorization

Cookie auth (`Program.cs`). Roles `Viewer` / `User` / `Admin` (`MatmonUserRole`). Admin-only pages are declared with `AuthorizePage(..., MatmonSecurity.AdminPolicy)` conventions; a global `MatmonPageWriteGuard` MVC filter enforces write protection (POST allowed only on `/Login`, `/Logout`, `/Setup`, `/Account` (self-service, any authed user), `/Alerts` for operators (`CanOperateAlerts` = Admin/User, so **Viewer is read-only**), else Admin). API paths return 401/403 (JSON) instead of redirecting. Passwords hashed via `MatmonPasswordHasher`. **Secrets encrypted at rest via ASP.NET DataProtection:** credential bundles (`HydrateCredentialBundles`/`ProtectCredentialBundles`) **and** notification secrets - SMTP `EmailNotificationSettings.Password`, `WebhookNotificationSettings.Secret`, `NotificationReceiver.Secret` (`HydrateNotificationSecrets`/`ProtectNotificationSecrets`, called from the credential hydrate/protect on every load/save; the plaintext is `[JsonIgnore]`-cleared before serialize and restored after, ciphertext in `Protected*` fields; legacy plaintext migrates on first save). Never written to `workspace.json` in the clear. The **Local Program** allow-list (`LocalProgramSensorExecutor.IsAllowed`) resolves symlinks (`File.ResolveLinkTarget`) to the final target before the allow-list check, so a link inside an allowed dir can't escape it.

**First-run setup (`/Setup`).** A fresh install with **no provisioned admin** runs a one-time setup that creates the first admin account (e-mail + password, `MatmonUser.Email`; login matches e-mail *or* username). `IMonitoringWorkspaceStore.IsSetupRequired()` is true while `WorkspaceDocument.SetupCompletedUtc` is null; a Primary-only middleware (before auth, in `Program.cs`) funnels every non-exempt page to `/setup` until done. `CompleteInitialSetup(email, password)` creates the admin + stamps `SetupCompletedUtc`. **No admin is auto-seeded by default** - `MatmonAuthOptions` defaults to empty and the old "fall back to admin/admin" lines are gone; setting `Matmon__Auth__Username/Password` (env) still pre-provisions an admin headlessly and marks setup done. `EnsureDefaultUsers` migrates any **existing** install (already has users) to `SetupCompletedUtc = now` so the wizard never hijacks a configured workspace. The optional setup *wizard* steps (networks / discovery / probes / notifications, skippable) land after account creation - not built yet.

**Credential editor (definition).** Container/host + template credential bundles render as a compact **list** (one row per bundle: name + kind chip + Edit/Delete) with editing in an **overlay modal dialog** (`credential-row` + `credential-modal-*`, `initializeCredentialEditors` in site.js; Add reveals a hidden slot and opens its dialog, a row left blank collapses out). **Every credential kind now has explicit mapped fields** - Windows (`winrm.*`), SSH/Linux (`ssh.*`), Proxmox (`pve.*`), SQL Server (`mssql.*`), SNMP (`snmp.*`), UniFi (`unifi.apiKey`), Generic (`generic.username/password/token`, consumed by the script sensors via the MATMON_* substring resolver). The legacy raw **key=value "Advanced values"** editor was removed app-wide; `ApplyCredentialBundles` starts from the bundle's already-stored values and overlays the explicit per-kind fields (a blank Secret field preserves the stored secret - `ApplyCredentialSecretField` - so dropping the raw editor never wipes data). **Generic fallback:** `MonitoringSettings.ApplyCredentialValuesForKinds` first resolves a bundle of the sensor's expected kind; if none exists it falls back to a **Generic** bundle (the explicitly-selected one when it's Generic, else the first) and maps its `generic.username/password/token` onto the keys the sensor actually reads (Windows→`winrm.*`, SSH/Linux→`ssh.*`, SQL→`mssql.*`, UniFi→`unifi.apiKey` from the token; Proxmox token-auth + SNMP have no mapping). So one shared Generic credential can serve typed sensors that lack a dedicated bundle.

## Configuration (env vars)

All under the `Matmon__` prefix (see `appsettings.json` + README). Common: `Matmon__Mode`, `Matmon__WorkspacePath`, `Matmon__Auth__Username|Password`, `Matmon__HeartbeatIntervalSeconds`. `Matmon__AllowedProgramPaths` (semicolon/newline list) is the allow-list for the **Local Program** sensor - read directly from the env var by `LocalProgramSensorExecutor` (not appsettings), empty by default = nothing runs. Seeding/provisioning flags default to false: `SeedSampleData`, `ProvisionLocalDockerProbe`, `ProvisionDemoSensors`, `AutoCreateProbeSystemSensors`, `CreateStarterMap`. Secondary: `ProbeId`, `ProbeName`, `ProbeToken`, `PrimaryUrl`. **Matmon.Cloud link - managed in the UI (System → Cloud), not env.** The primary connect is an **OAuth/PKCE claim** (UniFi-style, no password on the instance): enter a name, hit **Connect** → the admin's browser is redirected to the cloud consent page (`/instances/claim`, cloud-login-gated) which creates the instance under the signed-in account and hands a one-time code back to the instance's `/CloudClaim` callback, which exchanges code+verifier at `POST /api/instances/claim/exchange` for the id + token (see **Cloud instance claim** below). Two **Advanced** fallbacks remain: e-mail+password headless provision (`OnPostCloudProvisionAsync` → cloud `/api/provision`) and manual paste of an existing instance id + token (`OnPostCloudConnect`). Disconnect to unlink. **While connected the link identity is locked** - the cloud URL/id/token are shown read-only and only the display name stays editable (`OnPostCloudRenameAsync`); changing the URL or linking a different instance requires **Disconnect** first (the old `OnPostCloudUrl` in-place URL edit was removed). This persists to `WorkspaceDocument.CloudSettings` (`CloudConnectionSettings`; token **DataProtection-encrypted** at rest via the credential protector), exposed through `GetCloudConnectionSettings`/`GetCloudConnectionToken`/`SetCloudConnectionSettings`/`DisconnectCloud`. The Primary-only `CloudConnectionService` re-reads settings every ~5s and connects/disconnects **live (no restart)**; it sends a heartbeat once a minute (`Matmon__CloudHeartbeatIntervalSeconds`, default 60, floored at 15 - **separate from the probe `HeartbeatIntervalSeconds`** so slowing the cloud beat doesn't slow probes) carrying aggregate metadata (version, host, sensor/probe/map counts, and open-alert / error / warning / ack counts from `GetActiveAlertCounts`) - the dead-man-switch + public-dashboard feed - **plus a protocol version** (`CloudConnectionService.ProtocolVersion`, int, bumped when the cloud↔instance contract changes): the cloud stores it on the instance and flags any instance reporting an older protocol than `InstanceService.CurrentProtocolVersion` (or none = pre-versioning) as an **"Outdated"** badge in the instance lists (`InstanceService.IsOutdated`) - and records the last outcome in `WorkspaceDocument.Cloud` / `CloudConnectionState` (shown on the tab). The cloud aggregates these across an account's instances into a sidebar alert box (Err/Warn/Ack/Offline) + dashboard, and treats an instance offline after 150s (`InstanceService.OfflineAfter`, ~2.5 missed beats). A **deliberate disconnect** (`OnPostCloudDisconnect`) now also tells the cloud first (best-effort `POST /api/instances/{id}/disconnect`, instance-token auth, before `DisconnectCloud` drops the token) so the cloud marks it offline **immediately** (`RecordDisconnectAsync` clears `LastHeartbeatUtc` + sets `OfflineNotified` to suppress the dead-man alert) instead of lingering "online" for the 150s timeout; if the cloud is unreachable the timeout is still the fallback. The instance can set its own **cloud display name** from System → Cloud ("Update name" → `OnPostCloudRenameAsync` → cloud `POST /api/instances/{id}/name`, instance-token auth); the cloud owner can also rename it on the instance's Members page. Over the Full Access tunnel the embedded UI's live AJAX poll drops to 30s (the `_Layout` emits `data-embedded` → `site.js` reads it). The env vars `Matmon__CloudUrl` + `Matmon__CloudInstanceId` + `Matmon__CloudInstanceToken` are only a **first-run bootstrap**: once the user connects/disconnects in the UI (`CloudSettings.Configured`), the UI wins and env is ignored. Empty = fully offline; the link never takes the monitor down (failures are logged + retried). Login is **e-mail + password** (`LoginModel.Email`), aligning the local identity with the cloud account. Matmon.Cloud is a **separate repo** (proprietary, same stack: ASP.NET Core .NET 10 + PostgreSQL, accounts/ownership).

**Cloud alert relay (as a "Cloud" notification sender).** The relay is a **sender kind**, not a separate side-channel: `NotificationEndpointKind.Cloud`. Enabling it in System → Cloud (`CloudSettings.RelayAlerts`, master switch, **no recipients field**) auto-provisions/enables a built-in **"Matmon Cloud"** sender (`SetCloudRelaySettings(bool)` → ensures one exists/enabled; disabling turns it off but keeps it so rules keep their reference). A rule that selects the Cloud sender delivers through the gateway like any other rule - recipient from the rule's **receiver** (`ResolveRecipient`), templates from the rule. `NotificationDispatchService` matches rules **once** then routes by the rule's sender kind: a Cloud sender → `ProcessRelaysAsync` POSTs to the cloud's `/api/instances/{id}/notify` (instance-token auth, `RelayBody{channel,to,subject,text,html}`) when the link is connected + relay enabled (`ResolveCloudRelay`); anything else → local SMTP (`ResolveSmtp`). Same cooldown/episode throttle + retry/backoff for both. (A rule with a Cloud sender gets `ChannelKind=Email` so the dispatch email gate doesn't skip it.)

**Cloud instance claim (OAuth/PKCE "Connect").** The chicken-and-egg-free way to link a fresh instance: it has no token yet, so SSO can't be reused. `Config.OnPostCloudClaim` generates a PKCE verifier + `code_challenge = base64url(SHA-256(verifier))` and a random state, stores `{state, verifier, url}` in a **DataProtection-encrypted, HttpOnly, SameSite=Lax, 10-min cookie** (`matmon_cloud_claim`), and redirects the browser to `{cloudUrl}/instances/claim?redirect_uri={self}/CloudClaim&state=…&name=…&code_challenge=…`. The cloud consent page (`ClaimInstanceModel`, cloud-login-gated; validates `redirect_uri` is absolute http/https and shows its host) on confirm calls `InstanceService.CreateAsync` (instance owned by the signed-in account), `ClaimCodeStore.Issue(instanceId, token, challenge)` (single-use, 5-min, in-memory) and redirects back with `?code=…&state=…`. The instance callback `/CloudClaim` (`CloudClaimModel`, admin-only) validates state against the cookie (`FixedTimeEquals`), POSTs `{code, codeVerifier}` to cloud `POST /api/instances/claim/exchange` (anonymous - protected by PKCE), and stores the returned id + token via `SetCloudConnectionSettings`. The account **password never touches the instance**; the token never touches the browser (only the useless-without-verifier code does). `ClaimCodeStore.Consume` removes the code on **any** attempt (one verifier guess per code) - a slightly-stronger-than-spec PKCE. The PKCE helper (`CloudClaimFlow.Challenge`) mirrors the cloud's `ClaimCodeStore.Challenge` exactly.

**Cloud SSO ("Sign in with Matmon Cloud").** OAuth2 authorization-code with the cloud as IdP. `/signin-cloud?handler=Start` → cloud `/oauth/authorize` (member-gated consent) → code → local callback exchanges it at cloud `POST /oauth/token` using the **instance token as the client secret** → maps the account's instance role (Owner/Admin→Admin, Viewer→Viewer) → `store.UpsertCloudUser` find-or-creates a local user (`MatmonUser.CloudLinked`, password-less/SSO-only; an existing local account with that e-mail wins) → signs in. CSRF via a state cookie; codes are single-use (cloud `AuthCodeStore`, 5-min). The Login page shows the button only when the cloud link is connected. **Offline password fallback:** SSO accounts are password-less, so the self-service `/account` page lets any signed-in user set/change their own local password (`store.HasLocalPassword`/`ChangeOwnPassword`; a password-less account may set a first one without the current) - giving SSO users an e-mail+password credential for when the cloud is unreachable. `MatmonPageWriteGuard` allows the `/Account` POST for any authenticated user.

**Full Access (operate the local UI through the cloud).** A WebSocket reverse tunnel so a browser reaches a Primary behind NAT. Enable it in System → Cloud (`CloudSettings.FullAccessEnabled`); the Primary-only `TunnelClient` keeps an outbound WS open to the cloud (`GET /api/instances/{id}/tunnel`, instance-token auth), receives browser requests, replays them against its own UI and returns the responses (multiplexed by id; absolute self-URLs in `Location` are made root-relative). Cloud side: `TunnelRegistry` (one WS/instance) + the browser route `/instances/{id}/app/{**path}` (cloud login + membership gated) forwards via `TunnelProxy`, which rewrites root-relative URLs/redirects/cookie paths into the `/instances/{id}/app` prefix. **Seamless auto-login (no second sign-in inside the console).** A user who opens the console is already authenticated on the cloud and a member, so the cloud injects an identity assertion into the tunneled request - `X-Matmon-Cloud-User: "{email}|{InstanceRole}"` (set in `TunnelProxy.ForwardAsync` from `http.User`/`GetRoleAsync`, on both the `/app` and `/embed` routes) - and the instance auto-signs-them-in. Trust anchor: the instance's `TunnelClient` stamps every request it replays with a **per-process random secret** (`X-Matmon-Tunnel-Auth`, `TunnelAuthSecret` singleton), and the `TunnelAutoLogin` middleware (registered between `UseAuthentication`/`UseAuthorization` in Host `Program.cs`) honours the assertion **only** when that secret matches (`FixedTimeEquals`) → `UpsertCloudUser(email, MapRole(role))` + sets `context.User` from the assertion **on every tunneled request** (a backup cookie is re-issued via `SignInAsync` only when the identity actually changes). Authenticating per-request from the assertion - rather than relying on the auth cookie surviving the cross-origin console iframe round-trip - is what makes sign-in seamless (the cookie-dependent version "stuck" only after navigating back and forth). The instance is directly reachable, so the secret is essential: a forged `X-Matmon-Cloud-User` sent straight to the instance carries no valid secret and is ignored (verified: such a request still 302s to `/Login`). The cloud strips inbound `X-Matmon-Cloud-User`/`X-Matmon-Tunnel-Auth` (browser can't supply them) and the `TunnelClient` skips any inbound `X-Matmon-Tunnel-Auth` before adding its own. `MapRole` mirrors `SigninCloudModel` (Owner/Admin→Admin, else Viewer). The manual **"Sign in with Matmon Cloud"** OAuth button (`/signin-cloud`) still works for **direct** access; it is superseded by auto-login through the tunnel (and its `redirect_uri` is built from the local host, so it does not work *through* the tunnel - auto-login is the tunnel path). Cloud Instances list has an **Open** link. The cloud **console** (`Console.cshtml`) wraps the instance UI in a chromeless iframe (`/instances/{id}/embed/{**path}`) inside the cloud shell (single menu). To keep the browser URL correct on **reload / deep-link**, the console is also routable as `/instances/{id}/c/<inner path>` (`AddPageRoute` → `ConsoleModel.EmbedPath`), and `cloud.js` `initConsoleFrame` mirrors the same-origin iframe's location into that outer URL via `history.replaceState` on each iframe `load` (iframe nav uses `replaceState` so it never pollutes parent history; browser Back within the instance traverses the iframe's own history, and only the console boundary fires a parent popstate → turbo re-render). Runtime URLs (JS `fetch`/XHR, e.g. the dashboard's live `/api/…` polling) are handled by a **client shim** `TunnelProxy` injects into each tunneled page's `<head>` (wraps `fetch`/`XMLHttpRequest.open` to prefix root-relative URLs) - so live AJAX works too. Remaining edge: client-initiated WebSockets aren't tunneled (Matmon's UI uses AJAX polling, so N/A today); a subdomain-per-instance deployment would remove the need for rewriting entirely.

**Licensing (cloud is the license authority; template-based).** The cloud signs a per-instance license token (ECDSA P-256 over a compact payload) that Matmon verifies **offline** against a public key baked into `Matmon.Core` (`LicensePublicKey.Spki`); `Matmon.Core/Domain/Licensing.cs` holds `LicenseTier` (Free/Business/Enterprise/**Custom**), `LicenseInfo`, and `LicenseCrypto` (sign/verify, unit-tested). **The plan is a cloud-managed template** (`LicenseTemplate`): assigning it to an instance **snapshots** its values + price onto the instance (frozen), while the template NAME is read live (rename cascades). The token payload is now `t/p/e/iss/id` **+ `n` (plan name), `sl` (sensor limit), `csl` (cloud-sensor limit), `te` (tunnel/Full-Access), `cse` (cloud-sensors)** - the new fields are **nullable** so legacy tokens verify and map to permissive defaults; **the cloud `LicenseSigner.Payload` and `Matmon.Core.LicenseCrypto.Payload` must stay key-identical.** Local side: `CloudConnectionService` fetches the token each heartbeat + caches it (`store.Get/SetLicenseToken`); `ILicenseService` validates offline (Free fallback) and enforces **probe limit** (`CanAddProbe`) + **sensor limit** (`CanAddSensor`, blocks `OnPostCreateSensor`) + **Full-Access gate** (`OnPostCloudFullAccess` refuses if `!TunnelEnabled`); System → Cloud shows plan name + probe/sensor/cloud-sensor/Full-Access. `LicenseInfo.DisplayName` = plan name (or tier for legacy). NB the cloud's `License__PrivateKey` and Matmon's baked public key are a keypair - regenerate both together. **The production private key is NOT in the repo:** `LicensePublicKey.Spki` holds the prod *public* key (compiled in); the matching *private* key exists only as the cloud's `License__PrivateKey` env (`LicenseSigner` has no committed default - it signs only when the env is set, and the `/api/instances/{id}/license` endpoint issues no token when unset → instance stays on the cached license / Free). Local dev + prod must both set `License__PrivateKey`. `LicenseCryptoTests` use ephemeral keypairs (no committed key matches the baked one) plus a baked-key well-formedness guard. To rotate: `dotnet run keygen.cs`, put the SPKI-base64 public in `Licensing.cs`, the PKCS#8-base64 private in the cloud env.

## Conventions

- C# nullable + implicit usings on; modern C# (collection expressions `[]`, records, pattern matching). Keep new code matching the surrounding style.
- Razor Pages, one page = `Xxx.cshtml` + `Xxx.cshtml.cs`. Create/Edit dialogs are the `*Create` / `*Edit` / `*Editor` pages. The sensor editors (SensorCreate, SensorAssistant, ElementEditor, TemplateEditor) share partials to avoid duplication: `Pages/Shared/_SensorThresholds.cshtml` (`@model ISensorThresholdEditor`), `_SensorSchedule.cshtml` (`@model ISensorScheduleEditor`), `_SensorParameters.cshtml` (`@model ISensorParameterEditor`, the structured per-parameter fields - incl. the per-kind render switch, conditional-visibility data and the "Available variables" panel - a sensor-scope template renders the **same** fields, not a raw key=value textarea) and `_SensorCredentials.cshtml` (`@model ISensorCredentialEditor`, the credential selector + credential-kind fields; lives in the dedicated **Credentials** tab). **All four editors now render params + credentials only via these partials** - there is no inline duplication left, so a per-kind case or panel is added in **one** place. The credential-kind fields and general fields share the same `SensorParameterFields` list (each partial renders its subset by index), so binding reconstructs the whole list. Each input model in `Workspace.cshtml.cs` implements those interfaces; render with `Html.PartialAsync(..., new ViewDataDictionary(ViewData){ TemplateInfo = { HtmlFieldPrefix = "<Prefix>" } })`. The schedule editor is mode-based (inherit/every/daily/weekly/monthly) with value+unit intervals and a JS live "next runs" preview (`initializeScheduleEditors` in site.js). **Weekly fires on multiple weekdays** (e.g. Mon + Thu at 05:00): `MonitoringSchedule.DaysOfWeek` (list; legacy single `DayOfWeek` is the fallback via `ResolveDays()`), the editor renders weekday **checkboxes** (`ScheduleDaysOfWeek` on `ISensorScheduleEditor`), and `MonitoringScheduleCalculator` takes the soonest/most-recent occurrence across all selected days. **Defaults are simple** (`SensorScheduleDefaults`): ping = 30s, every other sensor = 5min, with a **hard 15s floor** (`SensorScheduleDefaults.Minimum`) the calculator clamps every interval to.
- **Tabs are app-wide one style.** The canonical tab UI is `.sensor-tabs` / `.sensor-tab` (clean underline, no panel frame) driven by `data-sensor-tabs` (bar) + `data-sensor-tab-target` (button) + `data-sensor-tab="<name>"` (panel); `initializeSensorTabs` in site.js toggles panels scoped to the bar's `closest("form")`. Used by SensorCreate/SensorAssistant, ElementEditor, TemplateEditor (edit mode), Config/System and SensorDetails. The shared `_SensorThresholds`/`_SensorSchedule` partials carry their own `data-sensor-tab` so any page rendering them gets the Thresholds/Schedule tab for free. Don't reintroduce the old boxed `.workspace-tabs` style.
- **List toolbar + primary button are one style (shared with cloud).** A list page puts a **toolbar tile above the list**: `<section class="panel panel-stack monitoring-controls"><form class="monitoring-filter-bar">…</form></section>`, each control a `<label class="monitoring-filter-field"><span>icon<small>Label</small></span> input/select</label>`; **filters are `<select class="form-select workspace-select">` dropdowns, not pill/segmented buttons** (canonical: `Events.cshtml`; the list sits in its own `.panel.workspace-panel` with a `.panel-header` count). The primary submit button is **`workspace-submit`** - `workspace-primary-submit` is **undefined in both instance + cloud `site.css`** (renders as an unstyled native button), never use it. Favicon is the shared blue Matmon glyph `wwwroot/favicon.svg` (all-blue so it's identical in light/dark), same file in Matmon + Matmon.Cloud + Matmon.Web. **Sidebar nav highlight is section-aware** (both shells): the active item is chosen by URL-path prefix (`NavSection`/`PathStarts` in the instance `_Layout`, `path.StartsWith` in the cloud), so editor and tab sub-pages keep their section lit - `/monitoring` is shared, so Templates (`/monitoring/template`) and Probes (`/monitoring/probe`, `/system/probes`) are matched first and excluded from Sensors; root `/` must be an exact match. **Server-side list paging is a fixed page size of 50** (`Paging.DefaultPageSize`); there is no user-facing "per page" selector - don't reintroduce one.
- **Sensor Create/Assistant "preview" re-post recomputes server-side state** (suggested name via `EnsureSuggestedSensorName`, applied template defaults, rebuilt channel/parameter fields). `OnPostPreviewSensorFields` and `OnPostDiscoverSnmp` must `ModelState.Clear()` before `return Page()` - otherwise the `asp-for` tag helpers re-render bound inputs from the posted ModelState and mask the recomputed values (the prefilled name would stay e.g. "Ping 3" after switching the type to HTTP).
- All workspace mutations go through `IMonitoringWorkspaceStore` and must run under its `_gate`; they call `QueueSave(SavePriority.*)`.
- **Concurrency: read cloned, write under the lock.** The read accessors `GetAllElements`/`GetAllTemplates` return **deep clones** (the tree is cloned once via `MonitoringElement.Clone()`/`MonitoringTemplate.Clone()`, then enumerated), so readers (polling due-set, dashboard, maps, probe-assignment, config-overview) never touch the live `_document` tree. The polling hot path resolves everything atomically under `_gate` via `GetSensorExecutionPlan` (lineage + effective settings + target → a detached `SensorExecutionPlan`); `SensorExecutionService.ExecuteNowAsync` uses it instead of walking live elements. Prefer the closure API **`UpdateElement(id, e => …)` / `UpdateTemplate(id, t => …)`** (mutation runs under `_gate`) over the legacy `FindElement`-then-mutate-then-`Save` pattern - the element save (`ApplyElementEditor`), sensor-create post-mutation and template restore/detach/save handlers already use it. `FindElement`/`Workspace` still return live refs (so any remaining unconverted mutator keeps working, just racy); the `Workspace` getter is deliberately **not** cloned (many per-render `.SensorDefinitions`/`.Templates` reads would make it O(n²)) - use `GetSensorDefinitions()` for the catalog.
- `DashboardSnapshotProvider.CreateSnapshot()` is **heavy** - it clones the workspace twice, builds a telemetry series (graph points) for every sensor and calls `SyncAlerts` (a GET-time mutation). Use it only on the dashboard (`/Index`) and `/api/dashboard`. The shared `_Layout` summary strip uses the cheap `GetWorkspaceSummary()` (topology counts only); never put `CreateSnapshot()` on a path that runs for every page.
- **Alerts are Alerta-style: they persist until acknowledged.** `MonitoringAlert` has `AcknowledgedUtc`, `RecoveredUtc` and `ResolvedUtc` (`IsActive = ResolvedUtc is null`). Recovery does **not** silently close an unacknowledged alert: `MarkAlertsRecoveredForElement` (poll path) and the recovery branch of `SyncAlerts` (dashboard) only set `ResolvedUtc` when the alert is already acknowledged; otherwise they set `RecoveredUtc` and keep it active (shown in the Open list with a "Recovered" pill). Acknowledging a recovered alert resolves it (`AcknowledgeAlert`). A re-alarm clears `RecoveredUtc`. Pausing a sensor still resolves outright via `ResolveAlertsForElement`. **Mute (= acknowledge + suppress re-opening):** `WorkspaceDocument.AlertMutes` (`AlertMute{ElementId, MutedUntilUtc null=permanent, MutedBy}`) records a per-element mute; `MuteElementAlerts` resolves the current episode to history AND sets the mute, `UnmuteElement` lifts it, `GetActiveAlertMutes` lists them (pruning expired). While an element is muted (`IsElementMutedLocked`, prunes lazily) both alert-raise paths skip it - `SyncSensorAlertFromObservation` (poll) and `SyncAlerts` (dashboard) - so no alert re-opens and no notification fires until the mute lifts (timed 1h/24h/7d or manual). The Alerts page has a per-active-row **Mute** menu (duration choices; the button carries `"{elementId}:{duration}"` since it rides the shared form) + a **Muted** panel listing muted elements with **Un-mute**. Emits `AlertMuted`/`AlertUnmuted` events.
