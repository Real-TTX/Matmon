# CLAUDE.md

Guidance for working in this repository. Keep it in sync with the code - update it whenever architecture, persistence, interfaces, or major data flow change.

## What Matmon is

A lightweight, self-hosted network monitoring platform (a compact PRTG-style alternative) for home / small-business networks. ASP.NET Core on **.NET 10**, C#, Razor Pages UI, Docker-first. **Proprietary** (was MIT; relicensed before any public download - see `LICENSE` and `docs/matmon-cloud-and-licensing.md`). Published images: `ghcr.io/real-ttx/matmon` + Docker Hub (`matmon`).

## Build / run / verify

- **Requirements:** .NET 10 SDK (developed against `10.0.203`), Docker Desktop or compatible runtime.
- **Build:** `dotnet build Matmon.slnx` (note: `.slnx`, not a classic `.sln`).
- **Run locally (dev):** `dotnet run --project src/Matmon.Host` → http://localhost:5084 (`ASPNETCORE_ENVIRONMENT=Development`). Default login `admin` / `admin`. For a live loop use `./scripts/dev.ps1` (`dotnet watch run`) - rebuilds/reloads on every change so the browser always shows current code.
- **Run via Docker:** `docker compose up --build` → a plain single-node primary on http://localhost:8099. The **dev/review stack** (primary with `./data` bind-mounted + sample secondary probe on :8100) is `./scripts/docker-refresh.ps1` - it runs `docker-compose.dev.yml` plus the local, gitignored `docker-compose.dev.override.yml` when present (joins the local Matmon.Cloud's `matmon-net` + cloud bootstrap). Don't start the dev file without the override: every rebuild then drops the cloud link. The same goes for the OTHER side: the local Matmon.Cloud is put on `matmon-net` (alias `matmon-cloud`) by a gitignored `docker-compose.override.yml` in that repo; without it a `docker compose up --build` recreates the cloud container on its own default network only and the instance silently loses the cloud ("Name or service not known (matmon-cloud:8055)").
- **Health check:** `GET /healthz` and `GET /api/mode` (both anonymous).
- **Tests:** `dotnet test tests/Matmon.Tests/Matmon.Tests.csproj` (xunit). Baseline covers the pure core logic (threshold parsing/evaluation, channel-threshold escalation, schedule calculator, settings inheritance). Coverage grows with each refactor.

## Solution layout

Five projects under `src/` (the fifth, **`Matmon.Setup`**, is the Windows setup + tray icon of the instance - see **Self-update**):

- **`Matmon.Core`** - framework-free domain. `Domain/` holds the monitoring model, the `ISensorExecutor` implementations (50 classes - only Mail Health, Matmon Update and the two syslog sensors live in the Host; Probe Health lives in `Matmon.Probe`), inheritance/threshold/schedule logic, notifications, and pure presentation helpers such as `MonitoringStatePresentation` (moved here from the Host because the probe side needs it too). `Sample/` holds the default sample topology (`SampleTopologyFactory`). `Syslog/` is the framework-free half of the syslog server (parser, TCP framing, allow-list, settings, models) - see **Syslog** below.
- **`Matmon.Probe`** - everything a probe needs to WORK for a primary and nothing a primary needs to BE one: `SlaveSensorWorker` (assignments, on-demand run jobs, discovery jobs, the offline buffer), `SlaveHeartbeatService`, `SlaveProbeRuntimeState`, `OfflineObservationBuffer`, `ProbeSystemInfoProvider`, `NetworkDiscoveryService` (+ `NetworkTargetParser`, public now that it crosses an assembly), `MatmonVersion`, the **Probe Health** executor + its storage abstraction (`ProbeStorage.cs`: `IProbeStorageSource` → `ProbeStorageSnapshot`, i.e. data dir exists / size / file count / drive free - the Host implements it with `StorageOverviewProvider` over its data directory, the agent with `DirectoryProbeStorageSource` over its install dir or `Matmon__DataPath`; `ProbeStorageScanner` is the one directory walk + drive lookup both use, and resolves the drive as the longest MOUNT POINT prefixing the path - the old `GetPathRoot` lookup measured `/` for every Linux path, i.e. the wrong disk for a Docker data volume or a separate `/opt`), the probe wire DTOs (`ProbeSensorExchangeModels`, `ProbeDiscoveryExchangeModels`, `ProbeHeartbeatRequest`) and `ProbeRuntimeOptions`, the **plugin runtime** (`Plugins/` - see **Plugins**) with the two built-in collectors, the syslog receiver they share with the primary (`Syslog/SyslogReceiver.cs`), the generic `UdpDatagramListener` and the disk queue `JsonLinesQueue<T>`. No workspace store, no UI, no PDF/mail stack. Shared by two hosts: `Matmon.Host` in Secondary mode (the Docker probe) and `Matmon.Agent`. The two registration lists live here too - `AddMatmonSensorExecutors()` (every Core sensor) and `AddMatmonProbe()` (heartbeat + worker + the two singletons, `TryAdd` because the Host registers those in every mode) plus `AddMatmonProbeHealthSensor()` (separate because a primary runs probe-health too without being a probe, and the stateless Executor mode has no storage source) - precisely so the two hosts cannot drift: an agent with its own copy of either list would sooner or later offer different sensors, or do half of what a probe does. ⚠️ `ProbeRuntimeOptions` is the BASE of the Host's `MatmonRuntimeOptions` (the 8 probe settings are declared once, there; the Host binds the whole derived object from the one `Matmon` section and registers the same instance under both types). Its `Microsoft.Extensions.*` references are pinned to 10.0.0 deliberately - a library pins the minimum, so the Host's shared framework and the agent's own Hosting package can lift them.
- **`Matmon.Agent`** - the probe installed ON the monitored machine: a worker (`Microsoft.NET.Sdk.Worker`, multi-targeted `net10.0` + `net10.0-windows` - the Windows build adds the WinForms tray) hosting `Matmon.Probe` + the Core sensors, with `AddWindowsService` + `AddSystemd` (both no-ops unless started by SCM / systemd, so one binary runs as a Windows service, a systemd unit and interactively). Always a secondary; reads the same `Matmon` section / `Matmon__*` variables as the Docker probe. `matmon-agent --version` prints the baked version. See **Agent** below for what it can and cannot do yet.
- **`Matmon.Host`** - the web app.
  - `Program.cs` - startup, cookie auth, authorization policies, minimal APIs (probe heartbeat/assignments/observations/discovery), sensor-executor DI registration, mode-dependent hosted services. Also wires an **in-app log viewer**: a bounded in-memory ring buffer (`Services/InMemoryLogStore`, ~2000 lines) fed by an `ILoggerProvider` (`Services/RingBufferLoggerProvider`, added via `builder.Logging.AddProvider`) and shown on the admin-only **`/Logs`** page (level filter + search + live 4s auto-refresh via a JSON page handler; process-local, resets on restart - a UI-side `docker logs --tail`, not an audit trail). Mirrored in Matmon.Cloud at `/admin/logs`.
  - `Services/` - persistence, polling, probe registry, dashboard/config providers, backup scheduler, slave (secondary) workers.
  - `Pages/` - Razor Pages UI (`.cshtml` + `.cshtml.cs`). The shell is `Pages/Shared/_Layout.cshtml` (drawn from `Ui/InstanceShell`), pages without a menu use `_AnonymousLayout`.
  - `wwwroot/` - `matui/` (the MatUi toolkit, a COPY - see **UI: MatUi** under Conventions), `css/app.css` + `css/features/*.css` (what is Matmon's own, prefix `mm-`), `js/app/*.js` (one classic script per feature, `core.js` first). No Bootstrap, no jQuery.

## Architecture: primary / secondary / executor

Mode is set via `Matmon__Mode=Primary|Secondary|Executor` (default Primary; `AppMode` in `Matmon.Core`, string aliases master/slave/executor).

- **Primary** owns the UI, configuration, alerts, history and global state. Registers `SensorPollingService` + `BackupSchedulerService`. Exposes the `/api/probes/*` endpoints that secondaries call.
- **Secondary** connects **outbound** to the primary (works behind firewalls/NAT), pulls assigned sensor work, executes it, and POSTs results back. Registers `SlaveHeartbeatService` + `SlaveSensorWorker`. **The secondary computes due-ness itself** (`MonitoringScheduleCalculator.IsDue` on each assignment's settings + a local `_lastExecutedUtc`), not the primary. The due sensors of a pass run side by side, **one lane per sensor type** (`MaxParallelSensorTypes` = 6; same-type sensors still one after another, because the probe holds ONE executor per type): the pass used to be strictly sequential, so a few dead WinRM/SSH targets waiting out their timeouts made every other sensor on the probe late. A probe runs only what it OWNS - `MonitoringTopology.EnumerateOwnedDescendants` stops at a nested probe, whose sensors (and their inlined credentials) used to go to the outer probe as well. NaN / Infinity readings are dropped centrally (`SensorExecutionResultHelper.DropNonFiniteReadings`) and `JsonLinesQueue` drops an item it cannot write as JSON: one such value used to jam a probe's offline buffer for good. **Store-and-forward (offline resilience):** `SlaveSensorWorker` caches the last-received assignments (`_cachedAssignments`) and, when the primary is unreachable, keeps executing them on schedule and **buffers** the observations in the in-memory `OfflineObservationBuffer` (append-ordered), flushing them oldest-first (500/batch) on reconnect. Reports carry their real execution timestamp and the primary records at that time (`/observations` uses `observation.TimestampUtc`), so a reconnect **backfills** history at the real check times. That stamp is the PROBE's clock, so every batch (observations, run-job results, plugin events) also says what the probe's clock read when it was sent (`SentUtc`) and the primary moves the stamps by the difference to its own when it is over 30 s (`ProbeClock` in Matmon.Probe) and never records anything in its own future - a probe an hour fast used to keep its results as the sensor's "latest" for the whole hour, one a day slow made every sensor look overdue. A batch the probe sends again because it never saw the answer (timeout, dropped connection) is recorded once: `IMonitoringWorkspaceStore.RecordProbeObservation` skips a result when the sensor already has one at that stamp (within 2 s when the stamp was clock-corrected, since the correction moves by the network time) - check and insert under `_gate`, through `ITelemetryRepository.HasObservation`; it used to store, event and alert-sync every result twice. Run-job results were already idempotent (`Complete` once); plugin events see below (**Plugins**). Retention: `Matmon__OfflineBufferRetentionDays` (default 7; **0 = disable buffering**, drop on failed post = pre-buffer behaviour) + a RAM cap `Matmon__OfflineBufferMaxObservations` (default 100k, oldest dropped past it); `OfflineObservationBuffer.Prune` enforces both (unit-tested). **Kept on disk too** (`ProbeRuntimeOptions.OfflineBufferPath`, `Matmon__OfflineBufferPath`; default: the Docker probe's data directory, the agent's state directory - `offline-observations.jsonl`): every buffered report is appended as a JSON line (`JsonLinesQueue<T>`, the generic disk queue the plugin events ride on too), a flush only advances a `.consumed` counter beside it, and the file is compacted when most of it has been sent, when pruning dropped something and on load (which also skips a line torn by a crash mid-write) - so an outage of the primary survives a restart of the probe as well (an agent update, a reboot), without rewriting megabytes per 500-batch. A disk that cannot be written costs only the restart safety; the memory copy still flushes. NB: backfilled observations still run the primary's per-observation alert sync, so a very long outage can re-drive alert state on flush - notification throttling limits it, but suppressing stale-backfill notifications is a follow-up.
- **Executor** is a **stateless sensor-executor service** for Matmon.Cloud's cloud sensors: **no workspace, telemetry, auth-cookie, UI or background loops**. `Program.cs` branches early on `AppMode.Executor` and builds a minimal app registering only the sensor executors (`RegisterSensorExecutors(..., includeProbeSensors:false)` - probe heartbeat/health need probe infra + are meaningless in the cloud) + `StatelessSensorRunner`. Two token-authed endpoints (`X-Matmon-Executor-Token` = `Matmon__ExecutorToken`, `FixedTimeEquals`, `IsExecutorAuthorized`): `GET /api/sensor-catalog` (the runnable `SensorDefinition`s - `StatelessSensorRunner.Catalog` filters `SensorDefinitionCatalog.BuiltIns` to registered types) and `POST /api/execute` (`ExecuteSensorRequest{sensorTypeKey,target,parameters,timeoutSeconds,credential{kind,values}}` → runs one `ISensorExecutor` via the same context/credential-mapping as Primary/Secondary → returns `SensorExecutionResult`). Nothing is persisted. `SensorDefinitionCatalog.BuiltIns` (Host/Services) is the single source of the built-in definition list, shared by the store's `EnsureSensorDefinitionCatalog` and the executor. This is how cloud sensors reuse 100% of the executor code with the RCE/native-deps surface isolated in a sidecar (see Matmon.Cloud).
- **On-demand runs route to the owning probe.** Any on-demand execution of a sensor that lives under a REMOTE probe (Run now, Test, Run-subtree, SNMP-discover) must run **on that probe**, not in-process on the primary. This uses a pull-based run-job mechanism mirroring the discovery-job flow: `Services/OnDemandRunStore` (`IOnDemandRunStore`, Primary-only singleton, in-memory `ConcurrentDictionary`, prunes >2 min-stale + keeps at most 200 - evicting only FINISHED jobs, so a Run over a folder of 350 remote sensors no longer drops 150 of them moments after queuing; a job carries a `TaskCompletionSource` so a waiting request wakes immediately) holds `ProbeRunJobKind.Sensor|SnmpDiscover` jobs. The primary decides local-vs-remote via `ProbeSensorAssignmentProvider.TryBuildProbeReadyRun` (resolves effective settings + target, **inlines credential values + strips bundles** so the probe runs standalone - the same shape as `BuildAssignments`; the owning probe = nearest `ProbeElement` with a non-null parent, else the local primary root) or `IMonitoringWorkspaceStore.ResolveOwningRemoteProbeId(elementId)` for a not-yet-saved sensor's selected parent. Endpoints (token-authed, Primary-only, next to the discovery ones): `GET /api/probes/{id}/run-jobs` (`TakePending` → Pending→Running), `POST /api/probes/{id}/run-jobs/results` (`Complete` + for a `RecordObservation` sensor job re-records via the SAME server-side re-resolve as `/observations` - `TryBuildRecordingContext`, never trusts probe settings), and `GET /api/run-jobs/{jobId}` (UI poll). `SlaveSensorWorker.SyncRunJobsAsync` (each 5s tick, after assignments) pulls + runs each job (Sensor = same path as `ExecuteAssignmentAsync`; SnmpDiscover = static `SnmpSensorExecutor.DiscoverAsync`, root OID smuggled through `Settings.Parameters[ProbeRunJobParameters.SnmpDiscoverRootOid]` since the DTO has no field) and posts `ProbeRunJobResultBatch` back; tolerates a 404 (older primary) silently. Handlers: `OnPostRunSensor`/SensorDetails `OnPostRunNowAsync` await ~12 s for a synchronous-feeling result then fall back to a "queued on probe" message; `OnPostRunElementSensors` fires remote jobs fire-and-forget + runs local ones in the background loop; the "Test"/SNMP-discover paths (`OnPostRunSensorNowAsync`/`OnPostDiscoverSnmpAsync`) enqueue a non-recording job and expose `RemoteTestJobId`/`RemoteSnmpDiscoverJobId` to the view, which `_RemoteRunPreview.cshtml` + `initializeRemoteRunPreviews` in `js/app/sensor-run.js` poll and render. **Local sensors keep the unchanged synchronous in-process fast path.** A remote Run now gets the sensor's previous result on that probe (an interface sensor computes its rate from it). Network discovery already routed correctly; a scan that has reported nothing for 10 minutes (the probe restarted mid-scan, or could not post its completion) is failed with that reason instead of showing "running" forever (`DiscoveryJobStore.FailStalled`). DTOs in `ProbeSensorExchangeModels.cs`. ⚠️ **"Owning probe" has one exception: a sensor type only the primary can run** (`SensorPlacement.RunsOnPrimaryOnly` in Core - the probe heartbeat, which reads the primary's picture of the probe, and the syslog sensors, which read the log the primary's receiver keeps). It is the ONE rule behind `SensorPollingService.IsLocalSensor`, the probe assignments (`BuildAssignments`, `TryBuildRecordingContext`), `TryBuildProbeReadyRun` (owner = null → in-process) and `ResolveOwningRemoteProbeId(id, sensorTypeKey)`; each of those used to hard-code the heartbeat, and a syslog sensor under a remote probe would have been handed to a probe that answers "No executor".
- Probe auth: a per-probe token sent as `X-Matmon-Probe-Token` header or `?token=` query (`ReadProbeToken` in `Program.cs`; validated via `IMonitoringWorkspaceStore.TryValidateProbe`).
- **Heartbeat full-sync:** the secondary heartbeat (`ProbeHeartbeatRequest`) also carries system details - OS, host name and reachable IPv4 subnets (CIDR), collected by `ProbeSystemInfoProvider`. The primary keeps them on the in-memory `ProbeStatusSnapshot` (`InMemoryProbeRegistry`). They surface on the probe **Usage** page ("System & networks" panel; the local primary reports itself) and the scoped probe's reported subnets are folded into **Discovery**'s subnet suggestions. The new heartbeat fields are optional (backward-compatible). The heartbeat also carries the probe's **build version** (`AgentVersion` = `MatmonVersion.Current`; it used to send the meaningless .NET runtime version and nobody stored it) - shown per probe on the **Probes** page next to OS/host. **Duplicate-probe detection:** a stale container left running after an update keeps pulling the same assignments as the new one, so every other observation comes from the old build and the sensor looks like it is flapping. `InMemoryProbeRegistry.DetectDuplicate` watches the heartbeat stream per probe id and flags it when the reported identity (host or version) ALTERNATES (A, B, A within ~2 intervals of the change), or when the SAME identity beats far faster than `HeartbeatIntervalSeconds`. ⚠️ A single identity change is an UPGRADE, not a duplicate: the rule used to be "changed and within 2 intervals", and since a new container / auto-updated agent beats right after starting, a large share of ordinary updates raised a false "Duplicate probe" warning; telling the two apart costs one interval of detection; the warning is sticky for a few intervals (so it survives the beats the duplicate "wins") and clears once one sender remains. Rendered as a warning line on the Probes page; unit-tested in `ProbeDuplicateDetectionTests`. The heartbeat carries the probe's own cadence (`ProbeHeartbeatRequest.HeartbeatIntervalSeconds` -> `ProbeStatusSnapshot`), and the primary judges a probe's heartbeat age and its duplicate gaps by it (its own interval only for an older probe): an agent beats every 30 s whatever the primary is set to, so a primary on 120 s flagged every agent as a duplicate and one on 10 s made them flap. The root probe never has a token: `TryValidateProbe` and `RotateProbeToken` refuse it and the editor hides the field - a root token opened `/api/probes/<root>` and with it every local sensor's credentials. The run-job and discovery result endpoints accept results only from the probe the job was handed to.

## Domain model

Tree of `MonitoringElement`s: `ProbeElement` → `FolderElement` → `HostElement` → `SensorElement` (see `Matmon.Core/Domain`). Settings and credentials are **inheritable** from parents; a sensor overrides only the fields that differ (`MonitoringInheritanceResolver`). Thresholds per channel: `SensorThresholdEvaluator`. With `describeBreaches` (the script, SQL and generic SNMP sensors, whose message only echoes the default channel) the sensor's message names the channel that crossed its limit when a threshold - not the executor - made the state worse: a Windows Health warning for pending updates used to read "Warning (Cpu Load 11)", in the list and in the notification. A notification rule that cannot be delivered says why at most once an hour per rule and reason (the built-in browser rule without a registered device warned on every alert). Scheduling: `MonitoringSchedule` / `MonitoringScheduleCalculator`.

**Default conditions** (`Matmon.Core/Domain/SensorThresholdDefaults`) - the single source of sensible per-sensor-type, per-channel warning/critical thresholds (CPU/mem/disk % 85/95, latency ms, UPS battery %, SMART status, cert days, …). Two uses: it seeds the Thresholds-editor placeholder + comparison for a channel (`TryResolve`, wired through `Workspace.TryGetDefaultThresholdRule`), and `Apply(type, settings)` bakes those thresholds onto a **new** sensor's own settings on create (only where the user hasn't set one) so it alarms sensibly out of the box. Wired at the two user-facing create paths (`store.CreateSensor` - manual create + discovery apply); the internal demo/provision seeders and the auto-created probe heartbeat/health sensors are intentionally left alone (heartbeat state comes from its `ageSeconds` channel thresholds, which `EnsureHeartbeatThresholdDefaults` derives from the heartbeat interval - warning above 2 beats + 10 s, critical above 4 beats + 10 s, never tighter than an agent's own 30 s beat; a sensor still carrying the old flat 30 / 60 s, or a pair derived for another interval, is moved along, an admin's own values are not. Right after the primary started, a probe it has not heard from yet is "waiting for its first heartbeat" (Unknown, and Ok on the dashboard) for 3 minutes instead of Critical - the registry is in memory, and every primary update used to raise a probe alert). Deliberately no defaults on cumulative counters (interface errors, container restarts) or redundant/overlapping channels (one clear signal per condition). SSL keeps its own `EnsureDefaultThresholds` (it also migrates the legacy `ssl.warningDays/criticalDays` params).

**Tags** (`MonitoringElement.Tags`, `MonitoringTemplate.Tags`) are free-form labels that **cascade**: a sensor's *effective* tags are its own plus every ancestor's (`MonitoringTagResolver.ResolveEffective`; `Normalize`/`Parse` clean + dedupe). Template tags merge into an element's own tags on apply (copy semantics). Tags show as chips on the Sensor Detail header (inherited ones styled subtly) and on monitoring tree/list nodes (own tags), and the monitoring search box matches tags so you can filter the tree by tag.

**Element picker** (`Pages/Shared/_ElementPicker.cshtml` + `Ui/ElementPicker.cs` + `initializeElementPickers` in `js/app/pickers.js`) is the reusable replacement for long element/sensor `<select>` dropdowns: a field that looks like a `mat-select` (its trigger is `<DomId>-trigger`, so a page labels it with `<label for>`) but opens a MatUi `<dialog class="mat-dialog">` (`<DomId>-dialog`) that shows the topology as an **indented tree** while browsing and a flat **tag-filterable** path list while searching (`is-flat` toggled by the filter; `ElementPickerOption.Depth` drives indentation), single-select, writing the chosen id into a hidden input (fires `change`). Client-side filtering, so it stays instant regardless of element count. Rolled out to: notification rule Target, **map tile Target**, and every **parent/target select** (SensorCreate/SensorAssistant/ElementEditor - carrying `data-sensor-parent-select` so the preview re-post still fires - plus FolderCreate/HostCreate/ProbeCreate). `WorkspacePageViewModel.PickerElements` + `Model.PickerOptionsFor(validOptions)` build the per-context option set from the legacy `SelectListItem` ids. *(Discovery's scope-probe select is a separate `DiscoveryModel` page and still a plain select.)* For map tiles the picker's hidden value carries `data-map-property-element` + `data-selected-name` so the map designer's change-sync/preview keep working, and `addTile` re-runs `initializeElementPickers` for cloned tiles. Tag fields (ElementEditor/TemplateEditor/SensorCreate/SensorAssistant) are progressively enhanced into a **chip editor** (`data-tag-input` + `initializeTagInputs`); the original input stays as the hidden comma-joined value.

**Tag-as-target** (`MonitoringTargetResolver` in Core - pure token parse/format; `IMonitoringWorkspaceStore.ResolveTargetSensors(token)` - topology resolution): a target is a single string token that is either an element id (GUID) or a tag, written `tag:<name>`. A picker with `AllowTags=true` shows an **Element ⇆ Tag** toggle plus a selectable tag list; choosing a tag writes the `tag:<name>` token into the hidden value and the trigger shows `# <name>`. `ElementPickerModel.SelectedValue` (string, wins over `SelectedId`) round-trips the token; `is-tag-mode` (root class) + `setMode` in `initializeElementPickers` flip the two lists. A **tag** target resolves dynamically to every sensor whose *effective* tags include it (cross-tree aggregation, same as a folder subtree). Wired so far: **map tiles** - `MonitoringMapTile.TargetTag` (mutually exclusive with `ElementId`); `MapEditor`'s `MapTileInput.TargetToken` parses into `ElementId`/`TargetTag` via the resolver; `MapDisplayProvider.BuildTagAggregateTile` → the shared `BuildAggregateFromSensors` rolls the matching sensors up (worst state + healthy count) exactly like a container tile. **Notification rules** too: `NotificationRule.TargetTag` (mutually exclusive with `TargetElementId`; a tag wins and clears the element on save) - the rule editor posts ONE token (`TargetToken`, the picker with `AllowTags`; the input models derive `TargetElementId`/`TargetTag` from it) and the dispatcher matches through the pure, tested `NotificationRuleTargeting.Matches` (moved out of `NotificationDispatchService`): a tag rule covers every element whose EFFECTIVE tags include it, `IncludeDescendants` does not apply because tags already cascade. The rules list shows "tag #name".

**Maps / wallboards** (`MonitoringMap` in Core, `MapDisplayProvider` + `Ui/MapTileRender` in Host, `/Maps`, `/Maps/Edit`, anonymous `/Maps/Public/{token}`). Since the MatUi conversion the library is a `mat-table`, the viewer is its own page titled with the map name (a "Switch map" menu in the header bar replaces the old select), the designer's property tabs are `aria-pressed` toggle buttons, the icon picker is a MatUi dialog opened by `pickers.js`, and Full screen shows the canvas alone. The designer form is `mat-form novalidate` (MatUi validates). Three things render the **same** `.map-stage > .map-slide > .map-tile` markup via the shared `_MapSlide`/`_MapTile` partials - the editor, the in-app viewer and the public wallboard - so they are WYSIWYG *by construction* rather than by three CSS systems staying in sync by hand. **Geometry is v4 = explicit CELLS on a real CSS grid.** A tile stores `Column`/`Row` (1-based) plus `ColumnSpan` (how many of the slide's `Columns` it occupies) and `RowSpan` (its height in ROW UNITS). The slide is a real CSS grid (`repeat(--map-columns, 1fr)` + `grid-auto-rows: --map-row-unit`) and a tile places itself into it (`grid-column: var(--tile-col) / span var(--tile-span)`), so **there is no transform**: the editor and the viewer show tiles at their true size. This history is worth knowing because the ends look alike: v1 was a fixed 1920px logical canvas that `fitMapStages` scaled into whatever box the editor had left (0.38 at a 1600px window - most of why the editor was unpleasant), v3 threw positions away entirely for a pure `Order` flow, and v4 is the flow's grid with placement put back. **Free placement and guaranteed non-overlap are the same trade-off from two sides** - v4 takes free placement (explicitly chosen), so two tiles CAN overlap; the designer draws the grid so that is a visible decision rather than an accident. `Order` survives as the READING order, derived from the positions and never edited by hand: it is what the stacked one-column view follows and what fixes the DOM order, so stacking needs no re-sorting in CSS. The JSON keys never changed across any of this (`"x"`/`"y"`/`"width"`/`"height"`/`"order"`). `MonitoringMapLayoutMigration` is idempotent and guarded on `LayoutVersion`: v0 keeps its cells, v1 converts px back to them, and **v3 replays the browser's own auto-placement over the stored order** (`MonitoringMapPlacement.PackFromOrder` - row-first with a cursor that never goes backwards, i.e. CSS grid without `dense`) so a board lands on the arrangement it was already being drawn as rather than re-flowing into its own holes. `MonitoringMapPlacement` (pure, tested) is the single placement authority - `Normalize` clamps every tile into the grid, gives an unplaced one (column or row 0, which is what a fresh tile carries) the first free spot rather than a landing on 1,1, and recomputes `Order`; the store calls it on every save and the designer mirrors it in JS (`findFreeCell`/`commitPlacement`). `MonitoringMapTileConstraints` is still the ONE min/default span table (the store, the migration and the designer JS all read it; the designer via a serialized block, never a second hand-written copy) and now also owns `MaxRowSpan` - a tile may be taller than one screen (a long list is a legitimate thing to scroll to) but not unboundedly, or one runaway tile shrinks every other tile on a scaled wallboard to nothing.

- **Auto-Stack** (`data-layout="stack"`) is the same grid with **one column**, switched below a 640 CSS-px **stage** width - stage, not viewport, so it is right inside an embedded/tunneled console too. ⚠️ A stacked tile must **drop its placement** (`grid-column: span 1; grid-row: auto`): a v4 tile pins itself to a column and a row, which in a one-column list would leave holes where the board has empty space and put two tiles on the same line. Stacked, the only thing that matters is the reading order - and the DOM already carries it, because the server sorts by `Order`, so there is still nothing to re-sort in CSS. ⚠️⚠️ **A tile must get a DEFINITE height** (`height: var(--stack-min-h)`, not `height: auto` + `min-height`). The tile is a `container-type: size` query container and its whole type scale is in `cqh`/`cqmin`; a container whose block size comes from its own content is *indefinite*, so the browser resolves every one of those units to **zero**. The tile still measured its min-height, which is what made the symptom so strange: cards, borders, state pills and the SVG gauge arc all drew correctly and every piece of TEXT rendered at `font-size: 0` - the whole mobile board was empty boxes. Stacked also means a phone at arm's length rather than a TV across the room, so the SMALL text carries a rem floor (`max(0.72rem, …)`) while the big reading keeps its cq size, and the **gauge lays out as a row** (`.map-gauge-dial` becomes `display: contents`, arc left / reading right): height-fitted, the arc is only ~86 px across on a phone card and a reading inside its mouth had room for "0…" and nothing else. It must **never** apply to the designer canvas (`fitMapStages` checks for `[data-map-designer]`): stacking the editor would show a list while the user places widgets on a grid. ⚠️ **`.map-tile` must declare `position: relative`** - its resize grip, size badge and pin layer are absolutely positioned children. v2's tile was `position: absolute` and gave them a containing block for free; the v3 rewrite dropped that without replacing it, so every grip on the board escaped to the slide and stacked up in its bottom-right corner - resizing looked simply gone. (The old rule here said the opposite - that the editor tile must NOT declare `position`, because a `relative` there broke v2's absolute placement. That rule died with the canvas.)
- **The editor has three top-level tabs, one per object you can edit: Editor / Slides / Board** (MatUi tabs). It used to have four - Display and Settings were both board-level and split arbitrarily, and Display had decayed into three dead hidden inputs, a timezone and a note pointing at the other tab. **The Slides tab shows the slides**: the list (add / rename / reorder by drag / duplicate / delete) and, under it, the SELECTED slide's own fields - a tab named after a collection has to show the collection, which it did not while the list lived under the canvas. `fillSlidePanel` is split out of `selectSlide` so those fields follow the ACTIVE slide rather than only a click on a row's gear. The canvas keeps a `[data-map-slide-switch]` **select**, not a list: changing slide must not mean leaving the board you are drawing on. Widget properties are General / Data / Display / **Advanced**, the last holding per-tile **colour rules** and the refresh TTL. Colour rules are four buckets (up/warning/down/unknown) while `SensorState` has six - `MonitoringMapColorRules` is the single place they collapse, and Paused counts as unknown rather than green, because painting a non-reporting sensor green is a lie on a wall display. Every rule goes through `BrandingSafety.SafeHexColor` before it reaches CSS. The Editor tab itself is toolbox | canvas | properties. **Dragging a widget MOVES it to a cell** - the pointer's travel is divided by the live cell pitch (`cellMetrics`, derived from the slide's own content width and the used `grid-auto-rows`, so it is right at any zoom, column count or font size) and rounded to whole cells, and the tile's own grid variables are rewritten on every `pointermove`: the drag preview IS the real layout, not a ghost that can disagree with it. `applyTilePlacement` writes the hidden `Column`/`Row` inputs and the CSS variables in ONE place so the model and the canvas cannot drift mid-drag, and `commitPlacement` then re-derives every `Order` from the positions - the same thing `MonitoringMapPlacement.Normalize` does on save, so the two can never disagree. The resize grip changes the SPANS, measured off the tile's own rect (one column is however wide this tile's span turned out to be, gaps included) rather than computed from the canvas; growing a tile at the right-hand edge re-clamps its column so it cannot run off the board. A palette DROP lands on the cell under the cursor (`pointerToCell`). There is no zoom control and no ruler any more - both only meant something for a scaled canvas - and the aspect-ratio / wallboard-fit fields are hidden round-trip inputs on the Board tab (kept on the model so an older board's stored values survive a save; nothing reads them, and the `data-map-fit` / `--map-w` attributes the two viewers used to emit are gone). The **widget palette comes from `Ui/MapWidgetCatalog`** (searchable, grouped by category) - deliberately NOT one entry per `MonitoringMapTileKind`, because Gauge and Progress are both a Value tile with a different `VisualType`, which is the distinction a user picks by. Adding a widget = one catalog entry. A palette entry is a **card with a drawn schematic** (`Pages/Shared/_MapWidgetPreview.cshtml`, a 16x9 currentColor SVG picked by `MapWidgetCatalog.PreviewKey`) rather than an icon and a sentence - Gauge and Progress are the same Kind and a word list makes them look identical, while the whole reason they are separate entries is that they LOOK different. `PreviewKey` derives the schematic from Kind+VisualType, so a new catalog entry gets a sensible preview without a second table to keep in sync. The same catalog defines **layout templates** that fill the current slide with empty, correctly-sized widgets; each declares the grid it was authored for and is disabled on a smaller one (clamped slots would overlap). **A layout is offered on the EMPTY canvas** (`[data-map-canvas-empty]`, shown by the designer whenever the active slide has no widgets) rather than as a permanent row of cards in the slide's properties: a layout is what you start a slide FROM, and a card that silently replaces a board you already built is the wrong affordance for a destructive act. Emptying a slide is its own named action instead (`clearActiveSlide`, the slide panel's "Clear this slide"), which says how many widgets it throws away. `MapWidgetCatalogTests` enforces the invariants a reviewer cannot see: unique keys, real icon keys, slots inside the declared grid, slots at or above the kind minimum, no overlaps. Layout templates render as **thumbnail cards generated from their own slots** (a CSS grid of the declared arrangement), so the preview cannot show a shape the button does not produce. The properties aside opens with a **header card** (icon / title / kind / delete) kept in step with the tile by `syncTileFromPanel`; size is an editable **Width/Height in cells** pair writing the same `ColumnSpan`/`RowSpan` inputs the drag handle does, so keyboard and mouse can never disagree; the display switches are `mat-switch` toggles over real checkboxes (they still post, focus and need no JS); and each colour rule pairs a native swatch with the hex text field - the **text field is what posts**, because only it can hold "" = keep the theme colour. With nothing selected the aside shows **canvas view toggles** (show grid / show rulers) that are view state only, remembered in `localStorage`, never on the map - and deliberately **no "snap off"**: v2 stores cells, so there is no position between two of them to save. ⚠️ The slide-list DOM hooks (`[data-map-slide-tabs]` / `-inputs` / `-add`) are resolved **from the form**, not from the old `[data-map-slide-strip]` wrapper - when that wrapper became the bottom-row card, scoping to it returned null and the failure was silent and total: the hidden `Input.Slides[..]` fields were never written (a save would have dropped every slide) and every tile was filtered against a slide id that then existed nowhere, so the canvas came up empty. JS-rendered slide rows are **cloned from the first server-rendered row** rather than hand-built, so the two markups cannot drift. The **filmstrip reconciles against the slide list** (`syncSlideCards`, same clone-the-server-card trick) instead of only repainting the cards the server happened to render - before that, adding/duplicating/deleting a slide left the strip showing the old running order - and its handlers are delegated, since the cards are rebuilt. ⚠️ **One bound input per property:** autoplay / slide duration / page indicator live ONLY beside the slide list on the Editor tab (the Display tab points at them). Two inputs bound to one property post whichever the binder reads first, so the one the user edited can silently lose. For the same class of reason the duration **select folds the stored value into its own option list** - a select can only post one of its options, so a board saved at 25 s would otherwise be rewritten to the first entry by any unrelated save. ⚠️⚠️ **In the tile `<template>`, a bool's checkbox must come BEFORE its hidden `false` partner** (the order ASP.NET's own tag helper emits): with both posted the binder takes the FIRST value, so hidden-first made `ShowCard`/`ShowTitle`/`ShowStateBadge`/`ShowElementName` read back as false on every widget added from the palette or a layout template - a freshly built board came out as floating text with no tile chrome at all, while a server-rendered (`asp-for`) tile looked right, which is exactly what hid it.
- **Properties** are one aside with three modes - map / slide / tile. The tile tab bar (General | Data | Display | Advanced) sits **outside** the per-tile panels so the chosen tab survives clicking from tile to tile; panels carry `[data-map-prop-group]`. Every panel carries every field and hides the ones its kind has no use for, so a whole group can come out empty (a Clock has nothing to point at) - `applyPropertyTab` therefore **hides a tab whose group has no visible field** and falls back to General, so a tab never opens onto nothing; it re-runs on a kind change, not just on selection. The map panel has its own General | Grid | Wallboard tabs. **Slide** fields are not model-bound: the designer owns the slide list in JS and re-renders the hidden `Input.Slides[..]` inputs (`renderSlideInputs`), which is the path add/rename/reorder/duplicate/delete all go through. Duplicating a slide clones its widgets by re-indexing `Input.Tiles[n]` **and** the element-picker DOM ids in the cloned HTML, after freezing live input values into attributes (`cloneNode` copies attributes, not what the user typed).
- **Grid size commits on `change`, never on `input`** - shrinking the grid re-clamps every widget into it and growing it back cannot undo that, so per-keystroke handling would flatten a board the moment someone typed the "1" of "12".
- **Collection widgets** (`SensorList`, `AlertFeed`, `Sla`, `Clock`, `Heading`) show a LIST or a windowed aggregate rather than one element's current state, so `MapDisplayTileViewModel` grew two optional collections (`Rows`, `Sla`) instead of a parallel view-model hierarchy - every other field (state, icon, colours, card chrome) is shared. Their per-widget options are flat properties on `MonitoringMapTile` (`ListMode`/`ListLimit`/`ListChannelKey`/`SlaWindowDays`), not a key/value bag: there is a handful of them, they are typed, and workspace.json stays readable. `_MapTile.cshtml` suppresses the generic value/subtitle footer for these (it would print the same number twice and steal the rows' height).
- **The Gauge is a real dial, and it refuses to invent one.** It renders as a 180-degree SVG arc whose path carries `pathLength="100"`, so the CSS sets the fill straight from the percentage with no arc-length arithmetic anywhere; the big figure in its mouth is the READING with its unit and the caption underneath is the SCALE (a needle two thirds round is unreadable if nothing says two thirds of what). It used to be a 360-degree conic-gradient donut - a ring chart, not a gauge, and it contradicted the schematic the palette draws for it. ⚠️ **A dial needs a scale and there are exactly two sources:** `MonitoringMapTile.GaugeMin`/`GaugeMax` (in the channel's own unit), or a channel whose unit is already a percentage. With neither, `MapDisplayProvider.ResolveSensorProgressPercent` returns **null** and the tile falls back to the plain reading. The old code clamped ANY number into 0..100 and called it a percent (12 ms of latency drew a dial at 12 %, 4 500 ms drew a full one) and, with no numeric channel at all, invented a needle position from the sensor state - both are made-up readings, and on a wall display a made-up reading is worse than an empty one. **Which channel a Value/Gauge/Progress tile reads is `MonitoringMapTile.ChannelKey`** (null = the sensor's default): a host sensor reports CPU, memory, disk and SMART, so "whichever is default" was a coin toss. `ResolveTileChannel` never picks the **virtual `sensorState`** channel - it is a 1/0 health flag, not a measurement, and letting it win rendered a failing sensor as a great big "0" as though that were its reading.
- **The Multi-graph answers "which of these moved?", and the shared scale is what makes it work.** `MonitoringMapTileKind.MultiGraph` draws up to 8 sensors as lines in ONE chart with a legend. Every line is plotted against a single min/max spanning ALL series (`Matmon.Core/Telemetry/SparklineGeometry`, pure + tested) - normalise each line to its own range and they all look identical, which destroys the only question the widget exists to answer. That also makes a shared UNIT the user's job: the tile's `ListChannelKey` (relabelled "Compare channel" for this kind) reads the SAME channel from every sensor; left empty each plots its own default channel and units can mix. It reuses `ListChannelKey`/`ListLimit` rather than growing two more properties, capped at 8 because each line is one `GetSensorHistory` query and past a handful a chart is spaghetti. **It takes SEVERAL targets** (`MonitoringMapTile.TargetTokens`, unioned with the main one and de-duplicated by sensor id): a chart comparing "these four switches" is a set the tree has no single node for, and a tag would mean labelling the estate first. They bind as ONE newline-joined field (`MapTileInput.TargetTokensText`) for the same reason the pins are one JSON blob - the designer clones whole tiles by rewriting field names, so a nested indexed collection would need re-indexing on every clone and delete. The editor renders a picker row per token plus **one empty trailing row, which IS the add affordance** (no button whose only job is to create a row you then have to fill in). ⚠️ Both editor preview endpoints must receive the series options: `OnGetTileMarkup` without `listLimit`/`listChannelKey`/`targets` renders a one-line "No data" chart while the viewer shows the real one, and the cheap `OnGetTilePreview` JSON - which carries ONE value and ONE subtitle - has nothing useful to say about any collection widget, so `refreshTilePreview` and the provisional-subtitle writer both skip `CollectionTileKinds` rather than overwriting a computed "3 sensors - last 24h" with the target element's name. Colours come from a fixed palette indexed by position so a series keeps its colour between renders (a legend that reshuffles is worse than none), and the legend is ordered by last reading - the line you are hunting is usually the highest. In the live payload the PATHS travel, unlike everything else, because for a line the path IS the value; the series COUNT is in the revision hash, so a sensor appearing under the target forces one honest reload instead of being patched in.
- **Multi-graph v2 - comparing MACHINES.** (a) **Channel families** (`Matmon.Core/Telemetry/ChannelFamilies`, pure + tested): the tile's `ListChannelKey` may hold `family:cpu|memory|disk|latency|temperature` instead of an exact key, and then each sensor contributes ITS OWN channel for that measurement - CPU is `cpuLoad` on Windows health, `cpu` on Proxmox/VMware, `cpuUtilization` on Synology, so an exact key compared nothing across a mixed set. Matching is on the last key segment, normalised; a top-level key beats a per-object one (the node's `cpu`, not `vm.101.cpu`), and a unit/measurement-kind guard keeps bytes off a percentage axis. The disk family also has COMPLEMENT names: a sensor that only reports FREE space (Windows health `systemDriveFreePercent`, Probe Health / Synology `storageFreePercent`) plots as 100 - free (`ChannelFamilies.Match` -> `ChannelFamilyMatch.Complement`, `ValueOf`); a real used-% channel always wins, and `Pick` stays direct-only. The family is picked from the latest observation, else the newest one in the window that has it (a timed-out poll carries no channels and used to drop the machine). The Sensor-list ranking honours families too (`PickChannel`). (b) **Time, not index, on X**: `ReadSeries` reads the WHOLE window (`MonitoringMapTile.GraphWindowHours`: 1 / 6 / 24 / 72 h from raw observations - raw retention is ~3 days - and 7 / 14 d from the statistics buckets via `ReadStatisticsSeries`: one point per bucket at the middle of its span, the named channel (else `default` / the best-covered one), the finest bucket size a sensor has, cached 5 min; one source per window, never a line that switches from raw to averages halfway) and `SparklineGeometry.TimeLine` places points by timestamp, `Downsample` averages into 120 slices. ⚠️ `GetSensorHistory(id, window, maxCount)` returns the NEWEST `maxCount` rows, not a spread - the old chart asked for 64 and labelled them "last 24h", which for a 30 s ping was the last half hour. Raw history is cached per sensor/window for 1 min (a wallboard polls every 30 s). Filtering happens BEFORE the 8-line limit (a host's ping/disk sensors used to push the CPU one out). The single **Graph** tile uses the same `GraphWindowHours` + `ReadSeries` path (it was the newest 64 readings spaced evenly too), plots the SAME channel as the tile's number (it plotted the bare observation value, so a graph on "memory" drew CPU), and closes its area under its own span rather than 0..100 of the width. (c) **Readable scale**: `SparklineGeometry.NiceScale` rounds to 1/2/5·10ⁿ steps and clamps a % axis to 0..100; the Y labels (`MapGraphAxisDto`) are HTML beside the plot, positioned on the grid lines at 5/50/95 % (the viewBox pads 2 of 40 units), with an invisible copy of the longest label sizing the column. (d) **Lines are named after the machine** (`SeriesLabels`: nearest host, else the sensor's target, else its parent; the sensor name only where that is ambiguous, a number where even that repeats) - every health sensor is called "Windows Health". (e) **Hover tooltip** (`initializeMultiGraphTooltips`, delegated, not in the designer): reads `data-series-points` ("x,value;..." - the points the line was drawn from) and the chart's `data-window-start/-end`, shows the time and every line's value there, sorted, built with textContent. (f) ⚠️ **Live patch carries label + colour + points per position**: the legend is ordered by the last reading, so two sensors swap positions whenever another becomes the highest - patched by position with only path + value, a name ended up beside someone else's line. Every path is emitted (even empty) so positions line up. The editor's **Compare** field is a select (`_MapCompareFields`, shared by the tile panels and the `__index__` template): families first, then every top-level channel key actually reported in the workspace (`CompareChannelOptions`), with a stored value no longer reported folded in.
- ⚠️ **Same-named fields in one tile panel** (`ListChannelKey` = "Rank by channel" AND "Compare"; `ListLimit` = "Rows" AND "Lines") used to post BOTH - hidden is not disabled - and the binder took the first, the HIDDEN one: an edit to a multi-graph's channel or line count was silently lost on save, and the preview read the stale value too. `syncDuplicateFields` (run on every kind change) keeps only the field of the current kind enabled - "unused" means hidden by a `data-map-property-*-only` group, NOT merely inside a closed tab (that version disabled the very select the Data tab was about to show) - and mirrors edits into the twins so switching kinds keeps the value. Any new property that gets a second field per kind is covered automatically.
- **A palette CLICK places the new widget in the first FREE cell** (`findFreeCell` in the designer, mirroring `MonitoringMapPlacement.FindFreeSpot`), not at 1,1 - four clicks would otherwise bury four widgets under each other. A DROP lands where the cursor released. ⚠️ That drop path was broken for the whole of v3: it called `pointerToLogical`, a helper deleted with the scaled canvas, so **every** drop threw, hit the `catch`, and silently added a generic State tile instead of the widget being dragged. A `catch` that substitutes a different action is worse than no fallback - it now returns.
- **The designer's grid guides are outlined CELLS, not filled column bars.** Twelve solid stripes running the full height read as content rather than as a guide and said nothing about the other axis - the one a tile's height is measured in. The overlay repeats the tiles' own grid definition (so a guide cannot drift from where a tile lands) and covers however tall the flow has grown, never fewer than the board's rows-per-screen; the last on-screen row carries a line, because a board may be taller than one screen but everything past that is below the fold on a TV. ⚠️ The row count needs the USED row height: `getComputedStyle(el).getPropertyValue("--map-row-unit")` hands back the authored text, and `parseFloat("4.6rem")` is 4.6 - which asked for 28 rows where 8 were needed. Read `gridAutoRows` instead.
- **The gauge's readout is scoped to the DIAL, not the tile** - `.map-gauge-dial` shrink-wraps the arc (same aspect ratio as the viewBox) and is its own query container, because the SVG is fitted by height: on a wide, short tile the arc is a fraction of the tile's width and a readout sized against the tile spilled across its stroke.
- **Tile anatomy: eyebrow / body / detail, with three densities.** A tile is a three-row grid - a quiet uppercase EYEBROW (icon + name + state), the BODY (whatever the widget actually is: dial, bar, chart, rows, reading) which is the only part allowed to grow, and at most ONE detail line. A board is read at a distance: colour and number first, name second, detail last, so the name is a caption above the reading rather than a bold heading competing with it. A healthy tile shows a **dot**, not an "OK" pill - the card is already green; only a non-ok state gets a word. How much a tile says is decided by its height in row units and emitted server-side as `data-density` (`s` = one row: a single line, eyebrow left / reading right, no detail; `m` = two rows: reading plus one caption; `l` = three or more: everything). ⚠️ It has to be an attribute, not a container query: **a query container cannot style itself from its own size**, and the tile is the container. Stacked (one column) a density-`s` tile goes back to eyebrow-over-reading and may grow past one row - side by side it pushed a heading straight off the card.
- ⚠️ **The tile is a `container-type: inline-size` container.** It used to be `size`, because the type scale was a percentage of the tile's height; that scale now hangs off the row unit (`--map-type`), so the only cq units left measure WIDTH. An inline-size container needs no definite height, which retires the whole class of "every piece of text rendered at font-size 0" traps and lets a stacked tile grow to fit its own text. (The gauge's `.map-gauge-dial` is still `size` - it has a definite height from its aspect ratio.)
- **Tile chrome is tuned for reading at distance, not for a desk.** The head icon is a plain glyph sized with the tile (since the MatUi conversion; tile colours are named custom properties on the tile - `--map-tile-tone`, `--map-tile-custom-bg/-accent/-text` - written with `initial` when unset so the stylesheet's fallback applies, and the state word is a MatUi pill scaled through its `--mat-pill-*` hooks), the big value uses `tabular-nums` so a figure ticking 9→10 does not make the line jitter, and the footer earns its lines: the **kind label only shows when no title does** ("State" printed under every state tile is a caption you read once) and the **target name only when it differs from the shown title** (heading "NAS-01" over a footer "NAS-01" is wallboard height spent saying nothing).
- **Uptime lives in `Matmon.Core/Telemetry/SensorUptime`** (pure, unit-tested) and is used by BOTH the scheduled summary report and the SLA widget, because the formula has two rules that are easy to get wrong independently: statistics buckets are per CHANNEL so they must be deduped by window start (otherwise the percentage is right but the sample count is N times too big), and a **Warning counts as up** (the sensor answered). No state samples = `null`, which must never render as 0 %.
- **`GetSensorStatistics(sensorId, fromUtc)`** pushes the window into SQL. The unwindowed overload reads every bucket a sensor ever had across every channel - fine for a nightly e-mail, not for a tile that re-renders per page load. NB `bucket_start` is Unix **milliseconds** (INTEGER): binding a cutoff as an ISO string compiles and silently matches nothing. SLA is the only wallboard query that scales with the sensor count behind a target, so `MapDisplayProvider` (a singleton) caches it per tile/window for 5 minutes.
- **The wallboard fills a TV by pure CSS.** `.public-map-shell .map-slide` derives `--map-row-unit` from the viewport (`(100vh - margins - gaps) / --map-rows`), so a slide of exactly `Rows` row units fills the screen with no JS measuring and nothing to re-run on resize. A taller board scrolls - deliberately: shrinking an arbitrarily long board to fit is how wallboards become unreadable. `fitMapStages` is therefore down to the ONE thing CSS cannot decide, whether this stage is narrow enough to collapse to a single column.
- **The clock ticks client-side in the MAP timezone** (`MonitoringMap.DisplayTimeZoneId`, `initializeMapClocks`), not the browser's: the public wallboard has nobody signed in, and a browser-local clock would contradict every server-rendered timestamp beside it. First paint is server-rendered so the tile is never blank; `MapTileRender.ResolveTimeZone` tolerates an unknown id rather than blanking the board.
- **Pictures and pins.** `Image` (an uploaded floorplan / rack photo, optionally with pins) and `GeoMap` (the shipped offline world map) share one renderer - the world map is just a different picture behind the same pin layer. Uploads go to **`Services/MapAssetStore`** (`data/uploads`, resolved like the backup folder and telemetry.db so it lands in the one mounted Docker volume), **never into workspace.json**: that file is fully re-serialised on a 750 ms debounce, so a 1 MB floorplan in it would be rewritten every time a pin moves. PNG/JPEG only, **magic-byte checked on write AND on read** via `BrandingSafety.DetectRasterContentType`, 4 MB cap; SVG is rejected because `GET /api/map-assets/{id}` is anonymous and same-origin, so a script-bearing SVG would be stored XSS. The served MIME comes from the bytes, never from the upload's claim, plus `nosniff` + an ETag.
- ⚠️ **The world map is painted by a CSS MASK, not by an `<img>`.** `world-map.svg` fills with `currentColor` so it can follow the theme - but an SVG loaded through an `<img>` is its OWN document, where `currentColor` resolves against that document's initial colour (black). The map was therefore a black silhouette in both themes, i.e. a dark smudge on the dark card it usually sits on, while the CSS comment next to it claimed it took the tile's text colour. Masked (`mask: url(...) center / contain no-repeat` + `background-color: currentColor`) the paint is the element's own, so it inherits the tile's text colour, flips with the theme and honours a per-tile `TextColor` - and the file stays one cached external asset. `mask-size: contain` letterboxes exactly like `object-fit: contain`, so the pin geometry is unchanged. **This is why no per-theme colour SETTING is needed**: the default is derived from the theme rather than stored.
- **Pin positions are fractions, never pixels** - an image pin stores 0..1 of the picture, a geo pin is projected from lat/lon by the pure, tested `MonitoringMapGeoProjection` (the shipped `world-map.svg` is equirectangular at 1 unit = 1 degree precisely so the projection is a linear rescale with no map library; the invariant is documented in the SVG too). Both end up in the same 0..1 space, so there is one rendering case and a pin holds at any board size.
- **Pins bind as ONE JSON field per tile** (`MapTileInput.PinsJson`), not as `Pins[i].X` fields: they are an unbounded per-tile collection placed by clicking a picture, and the designer clones whole tiles by rewriting field names - nested index binding would have to be re-indexed on every clone and delete. The (de)serializer needs an explicit `JsonStringEnumConverter`; `JsonSerializerDefaults.Web` has none, and without it every pin is silently dropped.
- ⚠️ **`NormalizeMapTiles` must clone-then-normalize, never hand-build a tile from a field list.** It used to construct a fresh `MonitoringMapTile` from an explicit list of properties, so every property added to the tile afterwards was silently dropped ON SAVE - the widget options and the whole image/pin set went that way at once, and the symptom is the nastiest kind: the editor shows the value, the save succeeds, the tile comes back with defaults. `MapSaveRoundTripTests` walks the tile's properties by reflection and fails the day a new one is not carried through.
- **Backup section `MapAssets`** carries the uploaded pictures - a map restores its pins and layout from `Maps`, but without this its floorplan comes back blank, which reads as "the pins are broken". Restored under their ORIGINAL ids (the restored tiles reference them) and re-checked by magic bytes, so a hand-tampered package cannot drop a script-bearing file into an anonymously-served directory. It is deliberately **NOT** in `WorkspaceBackupSections.CloudConfig`: a nightly cloud job would re-upload every unchanged floorplan. `WorkspaceDocument.MapAssets` is backup TRANSPORT only and is cleared on load exactly like the telemetry collections, so workspace.json never carries image bytes. The store takes the `MapAssetStore` as an OPTIONAL ctor argument - a store built without one simply carries no pictures, which is the honest behaviour for the unit tests that construct it directly. **Every backup section must be selectable in the UI, and a restore starts from NOTHING.** `BackupSectionSelectionModel` (job editor + restore page) has one bool per `WorkspaceBackupSection`, named exactly like the enum member - the restore page posts `Input.Sections.<name>` generated from the enum, so there is no per-section switch to forget - and `BackupSectionSelectionTests` fails the day a section is added to the enum without being added to the model and the catalog. Two things were wrong before, and both looked fine: map images (and later MIBs) were added to the enum but not to the model, so the restore page gave them an empty field name (never restorable from there) and saving a job in the editor silently dropped them; and ⚠️ the restore page's checkboxes are raw inputs - a browser does not post an unticked one - bound onto a model that defaulted every flag to TRUE, so unticking a section changed nothing and restoring "just the MIBs" restored users, topology and notification rules too (found by driving the real page with a browser-like client). `BackupRestoreInput` now starts from `BackupSectionSelectionModel.None()`; the job editor is fine because it uses `asp-for` (checkbox + hidden false partner). **Migration 5** (`MigrateBackupJobsToAllSections`): a local job stored as the old list of eleven sections (what "all boxes ticked" meant then) gets the sections added since; a job stored as the word `All` picks new sections up by itself (flag names resolve at load) and a narrowed one is left alone.
- **Live values, not a page reload.** `Ui/MapLiveData` builds the JSON both viewers poll (`/Maps?handler=Data`, anonymous `/Maps/Public/{token}?handler=Data`) and `initializeMapLiveData` patches the tiles in place. The public board USED to carry a 30 s `<meta http-equiv="refresh">`, and that had a failure mode worth naming: a full reload resets the slide carousel to slide 1, so on a multi-slide board every later slide was effectively unreachable on a TV. Only VALUES travel - anything structural (a tile added, removed, moved, resized) is baked into server-rendered markup, so the payload carries a **revision** hashed over exactly that shape (tile ids/kinds/cells, slide ids, pin and row COUNTS - never their state) and the client does one honest full reload when it changes. A failed poll leaves the last good values on screen: a wallboard is unattended, so blanking it over a network blip is worse than showing slightly stale numbers. The anonymous data endpoint is gated by the very same `FindMapByPublicToken` lookup as the page, so switching `PublicEnabled` off 404s both.
- The public-link opt-in is a real toggle in the map's Wallboard tab now, and the Maps page carries a **share panel**: the URL with a copy button, an offline-rendered **QR** (`TotpQr.Render`, QRCoder SVG - nothing leaves the box) and a kiosk hint. The QR sits on a forced white plate because it is drawn black-on-transparent and would be invisible on the dark theme. Rotating the link invalidates the old one immediately.
- **`PaginationMode` "Below the board" renders the controls OUTSIDE `.map-stage`** (the shared `_MapCarouselNav` partial, rendered either inside the stage for the overlay modes or after it for this one). Inside the stage they are scaled along with the board, which is why this mode used to look identical to "always visible". `initializeMapCarousel` therefore walks up to 3 ancestors to find the nav instead of assuming it is the carousel's sibling.
- **A tile's `RefreshSeconds` is the SLA cache TTL** (falling back to 5 minutes) and is part of the cache KEY, so shortening it takes effect at once rather than waiting out the previous entry.

**Notification dispatch (N0 - email).** Alerts are actually delivered now (previously the whole model/config/templates existed but nothing fired). When an alert is **raised**, `SyncSensorAlertFromObservation` enqueues a lightweight `AlertNotificationEvent` via `INotificationSink` (`NotificationSpooler` - a bounded, dependency-free queue, so no DI cycle with the store; enqueue is under `_gate` but non-blocking, off the hot path). The Primary-only `NotificationDispatchService` (BackgroundService, 5s tick) drains the spooler, matches **enabled** `NotificationRule`s (`TriggerStates` + `TargetElementId`/`IncludeDescendants` ancestry walk) and hands each match to `NotificationDeliveryFactory` (see **Channels** below), which renders the templates from a context built off the alert/element/latest observation and builds the delivery; `NotificationTransportClient` sends it. **Retry spooler:** each delivery is retried with backoff (0s/30s/2m/10m/30m, 5 attempts) then logged+dropped - except a REFUSAL (a 4xx other than 408/425/429, `NotificationDeliveryException.Retryable = false`), which is logged at once and not retried; **in-memory only** (a restart mid-retry loses pending sends). **Anti-spam (N1):** `NotificationThrottle` (Core, unit-tested) is a rolling rate limit per (rule, element): at most `NotificationRule.Threshold` "raised" mails per `NotificationRule.CooldownMinutes` window (it tracks recent send timestamps per key; a null/≤0 threshold = 1, which reduces to the classic "one mail per window" - backward compatible). New rules default to 15 min / 5. With the persist-until-ack model this is the practical flap suppression. **Recovery mails:** the store enqueues a `Recovered` event when an alarm clears; the dispatcher sends a "Recovered" mail but only to a rule that actually sent the raise this episode (`NotificationThrottle.IsEpisodeActive`), so a cooldown-suppressed re-raise produces no recovery spam either. **Unified Notifications UI.** The `/Notifications` page (`@model WorkspaceModel`, `@inject IMonitoringWorkspaceStore` for the report) is **one list of both notification types** with a client-side filter toolbar (All / **Trigger** / **Scheduled** + name search) and add-actions below: the alert-based `NotificationRule`s (Type = Trigger, edited on `/NotificationRuleEditor`) **and** the single scheduled summary report (Type = Scheduled, edited on the new `/NotificationReportEditor`). **Rules, Senders and Receivers are three MatUi tabs (`data-tab-hash`) on the single `/Notifications` page** (not separate pages) - the URL stays `/notifications` so the sidebar nav stays highlighted; `data-tab-hash` gives `#senders`/`#receivers` deep-links, and add/edit links carry `returnUrl=/notifications#senders|#receivers` so an editor save returns to the right tab. The old `/notifications/senders` + `/notifications/receivers` routes are kept as 302 redirects to the hash (bookmarks / editor back-links). Each rules row carries `data-notif-type`/`data-notif-name` for the inline filter. A **built-in virtual receiver** (`NotificationReceiverDefaults.AllUsersReceiverId`, "All users") is offered in every receiver picker (rules + report) - not persisted, injected into `BuildNotificationReceiverOptions` + the report editor - and expands at send time to all enabled users' e-mails via `IMonitoringWorkspaceStore.ResolveAllUsersRecipients()` (honoured in both `NotificationDispatchService.ResolveRecipient` and `SummaryReportSender.ResolveRecipients`), so new users are covered without maintaining a recipient list.

**Channels: the SENDER decides (e-mail, webhook, cloud).** `NotificationDeliveryFactory` (Host) routes by the rule's sender: none = the workspace default SMTP, an Email sender = its SMTP, a **Webhook** sender = an HTTP request, the **Cloud** sender = the Matmon.Cloud gateway (e-mail). The legacy `NotificationRule.ChannelKind` no longer gates anything - it used to, and the dispatcher only let `Email` rules through, so every rule with a webhook sender was dropped without a word while the UI offered webhooks. The **receiver is the one source of the recipient** when a rule names one; the `Recipient` copy on the rule is only read for rules that predate receivers (it used to WIN, so a rule switched to "All users" kept mailing the receiver it had before). A rule that cannot be delivered says why (`Create` returns a problem text: switched-off sender, an e-mail sender with a non-e-mail receiver, a cloud sender with the relay off, a webhook that does not build) - logged by the dispatcher, shown by the editor's test button. **Webhooks** (`WebhookNotificationSettings` + the pure, tested `WebhookRequestBuilder` in Core): the address, `Name: value` headers and the body are TEMPLATES with the rule placeholders plus `{{receiver.target}}` (the receiver's value - an ntfy topic, a Pushover user key, a Telegram chat id: receiver kind "Webhook value") and `{{secret}}` (the sender's Secret, DataProtection-encrypted - a token goes there, never into a header in the clear). Escaping is per target: URL-encoded in the address, JSON-escaped in a JSON body (and the result must parse, else the save is refused in words), URL-encoded per field in a form body (`name=value` per line), stripped of line breaks in a header (no header injection); `{{{key}}}` inserts raw. Method POST/PUT/PATCH/GET, optional HMAC signing (`X-Matmon-Signature: sha256=…` over the body, a template cannot forge it), timeout ≤ 60 s; only scheme+host is ever logged (Telegram's token is in the path). An empty body = the generic JSON document, which is what a pre-template webhook sender sends. **Presets** (`WebhookPresets`, rendered into the sender editor's preset select as data-* attributes - one source; `initializeWebhookPresets` fills the fields on a CHANGE only): generic JSON, ntfy (JSON publish to the root URL, receiver = topic), Pushover (form, Secret = app token, receiver = user key, `{{state.urgent}}` = priority), Gotify, Telegram (`bot{{{secret}}}` in the path), Microsoft Teams (Workflows adaptive card), Slack, Discord - `WebhookNotificationTests` builds every preset with the sample values and parses its JSON. Every save test-fills a webhook with `NotificationTemplateCatalog.SampleValues()` BEFORE applying (the edited sender is the live object). **Templates:** `NotificationRendering.Render` renders the subject and the new **short message** (`NotificationRule.ShortTemplate`, one line ≤ 300 chars, default "{{state.label}}: {{element.path}} - {{message}}") first and puts them into the context as `{{subject}}`/`{{summary}}`, so a webhook body uses them; `{{state.priority}}` (5 critical / 4 warning / 3 else, never empty - ntfy/Gotify want a number there) and `{{state.urgent}}` (1/0). **"Send test"** on the rule editor (`OnPostTestNotificationRuleAsync`) sends ONE notification through the rule as it is in the form (saved or not), filled with the preview data and marked "[Test]", and the page says whether it went out or what the service answered. **Alert delay and escalation.** *Delay* (`MonitoringSettings.AlertDelaySeconds`, inheritable, "Alert after (seconds)" next to Timeout/Retries on the element and template editors): an alert is raised only once the problem has lasted that long - a UPS on battery for two seconds or one lost ping never alarms; the sensor still SHOWS its state at once, only the alert and its notification wait, and the check runs at each poll (so the alert comes at the first poll after the delay). The store keeps `_problemSince` per sensor (first Warning/Critical since it was last fine; in memory - a restart can only delay an alert by one delay more, never raise one early) and `IsAlertDelayPendingLocked` gates BOTH alert paths. ⚠️ The dashboard's `SyncAlerts` raises alerts too and does NOT notify - if it raised one first, the poll path would find it "already there" and the notification would never go out; that is why the delay has to hold there as well (`AlertDelayAndEscalationTests`). *Escalation* (`NotificationRule.Escalations`, up to 3 steps, edited as three always-present rows on the rule editor - no add/remove script): when an alert the rule covers is still open, unacknowledged and NOT recovered N minutes after it was raised, it goes again through the step's sender to the step's receiver (each falls back to the rule's own), subject/short message prefixed "[Escalation n]", `{{escalation.level}}`. `NotificationEscalation.DueSteps` (Core, pure, tested) decides; the dispatcher looks every 15 s; the sent step is marked on the alert (`MonitoringAlert.Escalations`, `TryMarkAlertEscalated`) BEFORE it is queued and persisted, so a restart neither forgets nor repeats it; the throttle does not apply. A recovered-but-unacknowledged alert deliberately does not escalate. The rules list says "escalates after 15m, 1h". Verified live 2026-10-22: a webhook rule with a 1-minute step sent the raise and, 70 s later, "[Escalation 1]".

**Dependencies and maintenance windows - a real problem that is EXPLAINED raises no alert** (store partial `InMemoryMonitoringWorkspaceStore.AlertSuppression.cs`; both only touch alerting, sensors keep running). *Dependencies* (PRTG-style; pure rules in `Matmon.Core/Domain/MonitoringDependencies`): `MonitoringSettings.DependencySensorId` on any element, inherited down the tree, `Guid.Empty` = "none from here down", null = inherit; a sensor never depends on itself (the router ping sits inside the folder it guards, skips its own id and looks further up) and a chain that comes back to the sensor is ignored for it (`ResolveWithoutLoop`; the editor refuses such a setting with the reason - `DescribeDependencyProblem`, checked BEFORE the editor applies anything, by trying the setting under the lock and putting it back). While the dependency is DOWN (its last result Critical, or itself held - that carries an outage down a chain router -> switch -> server), a dependent's Warning/Critical result is recorded as **Unknown** with "Dependency 'X' is down - ... (It said: ...)" and is not judged at all: no new alert, an alert it already had stays exactly as it was (Unknown is NOT a recovery - the poll path skips the alert sync, and the dashboard sync's recovery loop skips held sensors), the problem streak restarts once the dependency is back. Unknown counts as neither up nor down in uptime. Three timing rules, because a router ping every 30 s and an HTTP check every 5 min cannot be relied on to notice in the right order: (1) a failing dependent whose dependency was last checked BEFORE its problem began holds its new alert (`MonitoringDependencies.WaitForCheck`, at most `CheckWait` = 2 min) and the dependency is polled at once; (2) when a dependency goes down, every dependent that is failing right now gets a held result immediately (`HoldDependentsLocked`, through the normal recording path, so events and chains follow) instead of staying red until its own next poll; (3) when it comes back, its held dependents are polled at once (a 6-hour disk sensor would otherwise show Unknown for hours). "Poll now" from inside the store goes through `SensorWakeQueue` -> `SensorWakeWorker` -> `SensorWakeService.WakeSensors` (the store cannot call the wake service, which needs the store; bounded and lossy - a wake is a hurry-up). The held map (`_heldByDependency`, with whether the sensor's own result was Critical) and the waiting map are in memory; the next result of each sensor rebuilds them after a restart. Editor: "Depends on" (inherit (X) / nothing / a sensor + a sensor-only element picker) on every element; the sensor page shows "Depends on" and an info banner while held. *Maintenance windows* (`MaintenanceWindow` + pure `MaintenanceSchedule` in Core, `WorkspaceDocument.MaintenanceWindows`, Setup > **Maintenance**, `/maintenance`, list + editor on one page like the Plugins page, admin edits, everyone reads): once (start-end) / daily / weekly (weekdays) / monthly (day 31 = the month's last day), recurring times are WALL-CLOCK times in the window's zone (default: the workspace display zone; a start in the spring-forward gap moves to the first minute that exists), a recurring occurrence lasts 1 min - 7 days and may run past midnight, end exclusive. Target like a notification rule's - an element with its subtree, or a tag (`NotificationRuleTargeting.Covers`, the shared rule). While a window covers an element: the store raises no NEW alert on either path (poll + dashboard sync), and the dispatcher sends no "raised" (a re-alarm of an alert that was open before) and no escalation (a step that falls due meanwhile goes out once the window is over); recoveries still go out. The next check after the window raises the alert of a problem that is still there. One-time windows that ended over 30 days ago are tidied away. Maintenance windows ride the **Notifications** backup section (and so the cloud config backup). Sensor page: an info banner "In maintenance: <window> until ...".

**⚠️ No sender is a deliberate state.** The load-time fix-up (`EnsureDefaultNotificationConfiguration`) used to give every rule without a sender "the first sender there is" (`ResolveSenderIdForRule`, removed), any kind - so the seeded default rule (no sender = the default SMTP, to "All users") turned into a webhook rule the moment an admin created a webhook sender, and with the old ChannelKind gate its e-mail alerts simply stopped. **SNMP MIBs** (`MibParser` + `MibRegistry` in Core, `Services/MibLibrary` + `/system/mibs` in Host). A walk used to show bare OIDs; now names, enum labels (`up (1)`, also through textual conventions such as IANAifType), units and descriptions come from MIBs. `MibParser` is a tolerant SMIv1/v2 reader - names, OIDs, SYNTAX/enums, UNITS, MAX-ACCESS, DESCRIPTION, INDEX, IMPORTS, TEXTUAL-CONVENTIONs - that records an unreadable assignment in `MibModule.Errors` and keeps going (vendor MIBs are sloppy); a type assignment has no terminator, so `ParseType` reads the type expression structurally to know where it ends. `MibRegistry` resolves symbols own module -> IMPORTS -> any loaded module (vendors forget imports), reports IMPORT modules that are not loaded (what to upload next; RFC-1212/ASN1 are macro-only and never count), prefers an SMIv2 node over its SMIv1 twin (sysUpTime is in RFC1213-MIB and SNMPv2-MIB), and `Translate` returns the longest known prefix + instance (`ifInOctets.3`); `MibTranslation.IsObject` says whether that prefix is a real OBJECT-TYPE - only then is the name used (a bare `enterprises.6574...` is not a channel label). ⚠️ **Names are resolved on the INSTANCE at display time, never on the probe**: a walk runs wherever the probe is, so no MIB is ever shipped to a probe/agent and an upload relabels results that already exist. `MibLibrary` loads the shipped standard set (`src/Matmon.Host/mibs`, copied next to the binaries - IETF + IANA + Net-SNMP/UCD + UPS-MIB, licences in its README) and then `data/mibs` (an upload replaces a shipped module of the same name), rebuilding and swapping the registry whole on every change. Upload: .mib/.my/.txt or a .zip, 2 MB per file, 20 MB / 500 entries per archive (read with a hard cap, not trusting the declared size), UTF-8 with a Latin-1 fallback; a file without a module is rejected; saved as `<FirstModule>.mib`. The walk list is ONE partial now (`_SnmpWalkList`, SensorCreate + SensorAssistant) with a MIB bar: an upload from the walk (fetch to `/system/mibs?handler=Upload` with `Accept: application/json`) relabels the rows in place via `POST /api/mibs/translate`, which also names the OIDs a remote probe reports in `_RemoteRunPreview`. Selected rows go into `snmp.oids` as `oid|mibName`, so the channel is called `ifOperStatus.2`; hand-written lines keep their own text and label on re-apply (they used to lose it). Verified: the parser resolves all 2636 nodes of the 65 MIBs Net-SNMP 5.9.4 ships to the same names as `snmptranslate -Tz` (`MibCorpusTests`, gated on `MATMON_MIB_CORPUS`). **In backups:** the files an admin uploaded (`data/mibs` - NOT the shipped set, which is part of the image) ride in the `Mibs` backup section (`WorkspaceMibFile`: only the base64 BYTES travel, never a file name). `MibLibrary.ReadUploadedFiles` fills it on create and `MibLibrary.Restore` empties it on restore - and that goes through `Upload`: the same 2 MB cap, the same must-contain-a-module rule, the file named after its module - so a tampered package has no say over what is written or where. A restore ADDS to what is there (like the map pictures) and never deletes a newer upload. Like `MapAssets` it is deliberately NOT in `WorkspaceBackupSections.CloudConfig`: a vendor MIB library can be tens of megabytes and a nightly cloud job would re-upload it every run. `Decode` drops a leading BOM, because the file is written back with one of its own and every backup/restore cycle would otherwise stack another on the front.

**Syslog (the central log).** The framework-free half is `Matmon.Core/Syslog` (`SyslogParser`, `SyslogFrameReader`, `IpAllowList`, `SyslogSettings`, models), the receiver itself (`SyslogReceiver.cs`: UDP/TCP listeners, `SyslogIngest`, the allow-list state) in `Matmon.Probe/Syslog` - it writes to an `ISyslogSink` (Core), which is the store on the primary and the plugin event queue on a probe, so the probe-side collector is the SAME receiver - and the rest `Host/Services/Syslog`. **Receiving is the `syslog-collector` PLUGIN** (see **Plugins**) - on the main probe (the primary itself) or on a probe or agent near the devices; nothing listens until an admin adds one on System > Plugins, because it opens a port that takes unauthenticated input. Its ports and allow-list are its plugin settings, and a change restarts it within seconds (`PluginRuntime`). ⚠️ An allow-list that parses to NOTHING keeps the collector OFF (fail closed - `StartAsync` throws; an empty parse would read as "allow everybody"); a partly bad one runs and names the ignored entries in its status; port-in-use / access-denied are said in words. **Migration 9** (`MigrateReceiversToPlugins`) turned a primary receiver that was ON into the collector on the main probe with the same ports and allow-list (`SyslogSettings.Enabled/UdpPort/TcpPort/AllowedSources` are legacy fields now, read only by it) and clears the old switch; one that was off becomes nothing. What stays in `SyslogSettings` is the log's own: `RetentionDays`/`MaxMessages`. `SyslogHousekeepingService` (Primary-only) only prunes: hourly, and at once when the limits tighten. UDP = one datagram one message, dual-stack with an IPv4 fallback; TCP framing is detected per connection (RFC 6587 octet-counting vs newline) and a bad length faults and closes it. **Time is RECEIVE time**: a switch that has just rebooted often has a wrong clock (half the reason to collect centrally), so the device's own stamp is kept only as text (`SyslogMessage.DeviceTime`) and ordering, windows and retention never use it. The parser reads RFC 5424 and RFC 3164 plus the dialects devices really send (Cisco sequence numbers / `*` marks / ms / time zone / no hostname, MikroTik, Ubiquiti, rsyslog ISO) and keeps anything else as `Raw` instead of dropping it. ⚠️ A line stamped with the machine's own month name ("Okt." on a German box) is no time stamp to any parser - `SyslogSelfTest` formats invariant. Severity: a LOWER number is MORE severe, so every filter is `MaxSeverity`; Errors = 0-3, Warnings = 4. **Storage** is its own SQLite, `data/syslog.db` (WAL, `auto_vacuum`, `Matmon__SyslogPath`) - apart from telemetry because it grows and is pruned on its own terms and clearing it must never touch sensor history. `SyslogStore`: a bounded queue + ONE writer loop inserting in batches per transaction (a flood costs log lines, not the monitor; a full queue counts as dropped), a fresh read connection per query, and it **never throws at a caller** - a missing/unwritable database is reported by `GetStorageInfo` and retried after 30 s, because the sensors that read it are resolved by the same container as every executor. Prune = by age, then by count (default 14 days / 2 M messages); `regexp` is a user function (`NonBacktracking` first, a 50 ms-timeout fallback for patterns it cannot do); text is `LIKE ... ESCAPE`; a sender filter matches the source address OR the host name (NOCASE, both indexed); `FlushAsync` waits on `_written + _discarded >= _enqueued` (refused messages count as discarded, or a flush would return early). **Sensors:** `syslog-messages` (errors / warnings / messages in a window + `lastMessageAgeSeconds`; default thresholds errors > 0 warning, > 9 critical, nothing on silence - plenty of devices only log when something happens) and `syslog-match` (phrase or regex, optional minimum severity, first match = warning, the latest hit in the message). Both are `Unknown` - never green - when no syslog or SNMP trap collector runs (`SyslogSensorSupport.ReceiverOff` asks the plugin assignments) or the device never sent anything, and `Critical` for a configuration error (no phrase, invalid regex, no sender). The sender is `syslog.source`, else the host's address; a host NAME is also resolved to its addresses (best effort, 2 s), because the log records where a message came FROM. They run on the primary whatever probe they sit under (`SensorPlacement`, see the run-routing note above) and are registered in Primary mode only (`RegisterSensorExecutors(includePrimaryOnlySensors)`) - a probe has no store. **UI: the log is a TAB of Events, the receiver is a tab of System - there is no menu item.** *Reading* (`Events.cshtml` + the `_SyslogMessages` partial): Events becomes **Matmon | Syslog** (`ShowSyslogTab`: an operator or admin, while a syslog or SNMP trap collector runs - an enabled assignment anywhere. Like every menu entry a plugin brings it is there ONLY while the plugin runs (decided 2026-10-23, "strict"): what was collected before stays in the database, pruned as usual, and is readable again once a collector runs; a Viewer never gets it, and until then the Events page is exactly what it was). Device logs can name users and addresses, so Admin + User read them; the `SyslogData` / `SyslogCounts` / `SyslogSenders` handlers on `EventsModel` (a page every role may open) refuse anyone else with 403 themselves. The filter bar → `SyslogData` JSON, cursor paging by id, live prepend of rows newer than the top id and a full reload when a whole page of news arrives, totals only on a filter change and through `SyslogCounts` after new rows, sender suggestions only when someone starts to type (an aggregate must not run on every Events visit); the tab loads when it is first SHOWN (a `MutationObserver` on its panel - a click, the `#syslog` of a link or a hash change all show it after the script ran), and its live poll stops while the panel is hidden. ⚠️ Every message is put on the page with `textContent` - anything on the network can send a line, so its text is never markup. Links open it filtered (`/Events?source=..&window=..&q=..&regex=..&severity=..#syslog`: a sensor's **Log** button, a sender's **Messages** button); the old `/syslog` address redirects there, query kept. *Setting up* (`/system/syslog`, `SystemSyslogModel`, admin-only - a System tab the collector plugin brings along, see **Plugins**): the collectors (`PluginUi.Placements`, each with its state and a link to its plugin settings, plus "Add a collector"; the head is `SyslogPageSupport.DescribeCollectors`, shared with the Events tab), the storage form (`TryBuildStorage`: retention and message cap, refused rather than clamped, a refused form re-renders with what was typed), "Send a test message" to the collector on THIS machine - offered only while one runs here - through its socket, allow-list, the parser and the database, "Delete all messages", the senders and how to point a device at it. The strictness about allow-lists moved to the Plugins page (`PluginSettingKind.AddressList`: an entry that is not an address refuses the form - ignoring a typo would widen who may write). **Senders (System > Syslog) are (address, host name) pairs** (`GetSenders`): an address behind which two or more host names speak is a relay - or Docker's gateway - and splits into one line per name (`SyslogPageSupport.BuildSenders`); each line is matched to a host in the tree (`FindHost`: address, then name, then the first label of an FQDN; behind a shared address the NAME only) and "Watch" adds a Syslog Messages sensor whose `syslog.source` is the NAME that made the match (empty = the host's own address, when the address did). ⚠️ Verified in a Linux container on Docker Desktop: every message arrives from the gateway address (172.17.0.1), not from the device, so the host name is then the only identity (README and the System > Syslog page say so). A syslog sensor's detail page has a **Log** link to the Syslog tab filtered to what the sensor counts (`BuildLogRoute`). The collectors (plugin assignments) and the log's settings are deliberately **not in any backup section and always stripped from packages**: switching a network listener on is decided on the machine it runs on, never by a restore. **Collecting on a probe** is the same plugin on a remote probe or agent: its lines are queued on the probe's disk and posted to the primary's store with their real arrival time - nothing is lost while the primary is away. Not done: per-device retention, and a "received via probe X" field on a message (a probe-collected line is stored exactly like one that reached the primary).

**SNMP traps (into the same central log).** `Matmon.Core/SnmpTraps` (`SnmpTrapSettings`, `SnmpTrapParser`) + `Host/Services/SnmpTraps/SnmpTrapReceiver.cs` + System > **SNMP traps** (`/system/snmp-traps`, admin-only, a System tab the plugin brings along: the collectors, the processing settings, the v3 users, the status, a test trap). **Receiving is the `snmptrap-collector` PLUGIN** - on the main probe or on a probe near the devices, UDP 162 by default, dual-stack; its port and allow-list are its plugin settings, fail closed like syslog. The primary PROCESSES what any collector took: `SnmpTrapPluginEventHandler` reads `SnmpTrapSettings` per trap (communities, poll switch, v3 users - `WorkspaceDocument.SnmpTraps`) and hands the datagram to `SnmpTrapIngest.Accept(datagram, sender, receivedUtc, viaProbe)`. Migration 9 turned a primary receiver that was ON into the collector on the main probe (`SnmpTrapSettings.Enabled/Port/AllowedSources` are legacy fields, read only by it). Like syslog never in a backup. `SnmpTrapParser` reads **SNMPv1 traps and SNMPv2c traps and informs** with the SNMP sensor's own BER reader (its encode/decode helpers + `BerReader` are `internal` for this - no second copy); a v1 trap is mapped to the v2 trap OID per RFC 3584 (generic n = 1.3.6.1.6.3.1.1.5.(n+1), enterprise-specific = enterprise.0.specific), so a v1 and a v2 linkDown are the same trap; snmpTrapAddress.0 (a relay) / the v1 agent-addr becomes the message's host name; an **inform is answered** with a Response PDU (verified: Net-SNMP `snmpinform` reports it acknowledged); **SNMPv3 traps** are checked against the users set up on the page (`SnmpTrapSettings.V3Users`, max 10; the passwords ride the notification-secret DataProtection lifecycle - `EnumerateNotificationSecrets` - so workspace.json never holds them in the clear, and the form keeps a password left empty, following a rename via `OriginalUsername`): the sender of a trap is the authoritative engine, so the keys are localised with the engine id the MESSAGE carries (nothing to configure per device), the HMAC is checked over the message with the auth parameters zeroed (`SnmpSensorExecutor.ParseV3Message`/`BuildV3MessageBytes`, made `internal` - the SNMPv3 sensor's own code, no copy) and the ScopedPDU decrypted with `SnmpV3Crypto`. Refused in words: no user set up, unknown user, wrong password, and a message LESS protected than its user (no downgrade). A v3 trap skips the community list (its user passed a real check) and its `Community` field carries the user name. Not done: v3 **informs** (the receiver would have to be the authoritative engine = engine-id discovery) and the replay time window (no per-sender engine time kept). `SnmpV3TrapTests` (every auth/priv family, tampering, the form, encryption at rest) + `SnmpV3TrapInteropTests` (Net-SNMP `snmptrap -v 3` SHA-256 / SHA+AES / MD5+DES from a container, gated on `MATMON_SNMPV3_TRAP_INTEROP=1`; verified 2026-10-23). The collector's allow-list decides who may send; the optional community list (or the v3 user) what counts (`SnmpTrapIngest`). A trap is written to the **syslog store** (`app = snmptrap`, `msgId` = the trap's name, message "SNMP trap <name> (<oid>) - <binding> = <value>; ..." with names and enum labels from the MIB library, severity Warning for linkDown / authenticationFailure / upsTrapOnBattery / upsTrapAlarmEntryAdded, else Notice) - so it is searchable on Events > Syslog (`/Events?q=SNMP+trap#syslog`) and a **Syslog Match** sensor on e.g. `upsTrapOnBattery` alarms on it with no trap-specific sensor. **Poll on trap** (on by default): `SensorWakeService` makes every sensor of the sending device poll NOW - a sensor whose own target, or whose nearest host's address, is the device (a host NAME resolved, cached 10 min; an HTTP target's URL host) - locally in the background or as a run job on its remote probe, each sensor at most once per 10 s; a trap says that something happened, the sensors say what (a UPS sending "on battery" is red within seconds). Loopback (the page's test trap) wakes nothing - and on Docker Desktop every trap arrives from the gateway/loopback, so the devices cannot be told apart there (Linux keeps the device address). "Send a test trap" goes to the collector on THIS machine (offered only while one runs here) - its socket and allow-list, then the community check, the parser and the database. `docker-compose.yml` carries a commented `162:162/udp`. `SnmpTrapTests` cover the parser per version, the inform answer, the processing form and the real UDP path through the collector plugin (collector -> event -> handler -> log), `SensorWakeTests` which sensors a trap polls (host address, own target, remote probe = run job, throttle, paused); verified 2026-10-22 with Net-SNMP `snmptrap` v1 + v2c and `snmpinform` from a container. The socket is the generic `Matmon.Probe/UdpDatagramListener` inside the collector, wherever it runs: the collector checks its allow-list and answers a v2c inform itself (whatever the community - the device stops repeating it), the primary applies its communities, SNMPv3 users, MIB names and the poll-on-trap wake - at the time the trap reached the collector.

**Plugins (server services that run where the devices are).** A plugin is a long-running service - a listener, a collector - that the instance switches on, configures and places, and that turns what it receives into **events**. The contract is `Matmon.Probe/Plugins/PluginContracts.cs`: `IMatmonPlugin` (a `PluginDefinition`: id, name, description, `PluginPlacement` Primary|Probe|Both, typed `PluginSettingDefinition`s, version; `StartAsync(PluginContext)` → `IPluginInstance` with a live `PluginStatus` and `DisposeAsync`), `PluginContext` (the assignment id, the settings as strings + `Setting`/`IntSetting`/`BoolSetting`, a logger, a private data directory `plugins-data/<plugin>/<assignment>`, the probe id, and `IPluginEventSink`) and `PluginEvent` (plugin id, KIND, occurred time, source, a JSON payload). It lives in `Matmon.Probe` because the Docker probe, the agent and the primary all run plugins with the SAME `PluginRuntime`. **Where it runs is an assignment**: `PluginAssignment` (Core: plugin id, the `ProbeElement` it runs on, enabled, settings) in `WorkspaceDocument.Plugins`, edited on System > **Plugins** (`/system/plugins`, `SystemPluginsModel`, admin-only, a tab of `_SystemTabs`; a location is offered only where the plugin's placement allows it, settings are validated against the definition, each row shows Running / Error / Waiting / Off with the plugin's own detail line). The root probe = the primary itself (`PrimaryPluginService`, reconciles every 5 s); a remote probe or agent pulls its assignments from `GET /api/probes/{id}/plugins` every 15 s (`ProbePluginWorker`, probe-token auth like the other probe endpoints) and runs them in its own `PluginRuntime`. `PluginRuntime.ReconcileAsync` starts what is new, restarts what changed (`PluginAssignmentSpec.Signature` over plugin + settings), stops what went away and retries a failed start after 30 s - a probe never needs a restart for a change on the page. **Events travel like observations**: on a probe they go into a disk queue (`plugin-events.jsonl`, `JsonLinesQueue<PluginEvent>` - the offline buffer's mechanism, same retention `OfflineBufferRetentionDays`, capped at 200k, oldest dropped) and are posted oldest-first in batches of 500 to `POST /api/probes/{id}/plugins/events` (max 2000 per request) together with each assignment's status, the plugins the probe HAS and its queue length; the primary's `PluginEventDispatcher` routes each event by kind to an `IPluginEventHandler` (`syslog` → the syslog store, `snmptrap` → `SnmpTrapIngest.Accept` via `SnmpTrapPluginEventHandler`) and swallows a failing one (counted) so a poison event can never make a probe resend its batch forever; an event carries an `Id` given on the probe (`ProbePluginEventSink.Publish`, it rides the disk queue along), and the dispatcher remembers the ids it took in the last hour (at most 100k, in memory) and skips a repeat - a batch the probe sent again because it never saw the answer used to store every log line and trap twice (an older probe sends no id and is handled as before; a repeat across a primary restart is not recognised); a probe reports status only for its OWN assignments. A 404 from the plugins endpoint (an older primary - or one in the middle of an update) pauses the plugins for 10 minutes and asks again; it used to switch them off until the probe was restarted. The last assignment list is cached on the probe (`plugin-assignments.json`), so a probe that restarts while the primary is down starts collecting again at once and the backfill keeps the real times (verified end to end: a probe restarted during a primary outage collected, and the lines appeared on Events > Syslog at their arrival times once the primary was back). **Built in:** `syslog-collector` (UDP/TCP ports + an allow-list that fails CLOSED) and `snmptrap-collector` (port + allow-list; forwards the raw datagram, so v3 checks, MIB names and the wake happen on the primary where the users and MIBs are) - both placement **Both**: on the main probe they ARE the primary's syslog server / trap receiver (there is no other socket any more), on a probe they collect near the devices. **A plugin brings its menu entries along**: `PluginDefinition.Links` (`PluginUiLink(Area System|Events, Key, Title, Path)` - an init property, so a plugin built against the constructor without it still loads); `PluginUi` (Host singleton, every mode) shows the entries of plugins with an ENABLED assignment somewhere - `_SystemTabs` renders the System ones (Syslog, SNMP traps), the Events page asks it for its Syslog tab - and nothing else (only paths on the instance). **Strict, decided 2026-10-23:** a plugin that runs nowhere brings no entry at all, and its pages (`SystemSyslogModel` / `SystemSnmpTrapsModel`, `OnPageHandlerExecuting`) send whoever arrives there - a bookmark, an old link, a POST - to System > Plugins with a word on what to add. (It used to keep the open page's own tab in the strip and keep the Syslog tab while the log held messages; both exceptions are gone.) `PluginUi.Placements` / `PluginPlacementView` is the one picture of "where does it run, in which state" for the Plugins, Syslog and SNMP traps pages; a Plugins row links to the plugin's page. One assignment per plugin and place: the Plugins page refuses a second (it would only fail with "port in use"). `PluginSettingKind.AddressList` settings are validated strictly on the page. **External plugins** are DLLs in the plugins folder (`Matmon__PluginsPath`; default `plugins` beside workspace.json on the primary, beside the executable on an agent): `<name>.dll` or `<folder>/<folder>.dll`, each in its own `AssemblyLoadContext` that shares `Matmon.*` and `Microsoft.Extensions.*` with the host (so `IMatmonPlugin` is the same type); a DLL that does not load is listed on the page with its reason (`PluginCatalog.LoadErrors`), never fatal. ⚠️ An external plugin runs **with the full rights of the process** - installing one is a decision of whoever administers that machine, which is why there is no upload on the page, only the folder. Assignments are instance configuration but are **not** in any backup section and are stripped from every package, for the same reason as the receivers' own settings: a restore must not open listeners on a machine. `PluginSystemTests` cover the runtime (start / restart on change / stop / retry, placement), a DLL that does not load, both collectors, the assignment cache, the dispatcher, that assignments reach only their probe and stay out of backups, the menu entries of active plugins only (and never one that leaves the instance), the strict address list and the one-per-place rule, and migration 9; the disk queue is covered through `OfflineObservationBufferPersistenceTests`. **Decided 2026-10-23: plugins SHIP with Matmon** (built into the image and the agent) and run only once activated on System > Plugins - nothing is enabled by default and there is no distribution of plugins to probes; an external DLL stays a manual install by whoever runs that machine. Not done: an event kind that is not syslog or a trap needs its handler on the primary - a plugin alone can only produce kinds the primary knows (unknown kinds are counted, not stored).

**Push sensor (`push`, "Push (heartbeat)") - something calls Matmon instead of the other way round.** A backup script, a cron job, a device calls `GET|POST /api/push/{token}` (Primary only, anonymous by design - the token is the only credential - rate-limited 120/min per IP, policy `push`; optional `status` = ok/warning/error or 0/1/2, `value` = a number, `message` = one line ≤ 500 chars, from the query, a form or JSON - read by hand in `PushRequestReader`, so no antiforgery/form binding is involved; an unknown token is a 404 like a missing page, a bad status/value a 400 in words, a paused sensor takes the call and ignores it). Silence is the alarm: no push for longer than `push.interval` + `push.grace` minutes (defaults 60 + 15) is Critical, else the sensor has the state the last push named; none yet = Unknown. Pure rules in `Matmon.Core/Domain/PushSensor`; the host side is `Services/PushSensorServices.cs`: `PushRegistry` (singleton, the last push per sensor - updated BEFORE the push is recorded, read by the periodic check, so a check running while a push arrives can never record an older "last push" over a newer one) and `PushSensorExecutor` (registered with the syslog sensors, primary only; `SensorPlacement.RunsOnPrimaryOnly` includes `push`; not retried; polls every minute - it only works out whether the last call is overdue). Each push is recorded as an observation at once (`PushSensor.FromPush`), and every observation carries the last push in a VIRTUAL channel `pushedAt` (Unix seconds, its state and message), so after a restart `PushRegistry` starts from the latest observation and a daily backup that pushed before the restart is not called overdue. The token is the sensor's parameter `push.token`: its name ends in "token", so it is sealed at rest like every secret parameter (`enc:dp1:`); a push sensor gets one at creation (`store.CreateSensor`), on every boot if it has none (`EnsurePushTokens`), and when an admin empties it in the editor and saves (a new address - the old one stops working); `FindPushSensor` compares in constant time. The sensor page shows the address with copy buttons and curl / PowerShell examples - to Admin and User only, never to a Viewer (it IS the credential). **Carried-state channels are hidden:** a virtual channel other than `sensorState` only carries state from run to run (`pushedAt`, Mail Health's `probeSentEpoch`) - `SensorExecutionResultHelper.IsCarriedState`; the sensor page's channel list and the Channels & thresholds editor leave it out (it used to show as a raw Unix timestamp).

**Detailed per-platform Disk sensors** (separate from the compact Health sensors' single SMART-summary channel): `SynologyDiskSensorExecutor` (`synology-disk`, SNMP synoDisk table), `WindowsDiskSensorExecutor` (`windows-disk`, a thin wrapper that delegates to the generic `PowerShellRemoteSensorExecutor` engine with a fixed disk script + JSON output - a `state` string key drives the sensor state), `LinuxDiskSensorExecutor` (`linux-disk`, reuses `LinuxSshHealthSensorExecutor.StartSshProcess`/`ParseKeyValueChannels` - now `internal` + a `script` parameter - with a smartctl+df script), `ProxmoxDiskSensorExecutor` (`proxmox-disk`, reuses the now-`internal` Proxmox HTTP/auth helpers `CreateHttpClient`/`BuildApiBaseUri`/`BuildAuthorizationHeader`/`ReadApiDataAsync` over `/nodes/{node}/disks/list`). Each emits `ChannelMode.Dynamic` per-disk channels + an overall `smartStatus` (0/1/2) and `diskCount`; reusing the parent executor's machinery avoids duplicating the remoting/API plumbing.

**UPS sensors - one channel set, a power cut is critical at once.** `UpsChannels` (Core, pure + tested) is the ONE channel set both UPS sensors report: 1/0 flags `on_battery` / `low_battery` / `replace_battery` / `overload` / `on_bypass` (listed first) and the values `battery_charge` %, `runtime_minutes`, `load_percent` %, input/output/battery voltage, `temperature`, `seconds_on_battery` - so a rule, a threshold or a tile works the same for any UPS. Default thresholds (`SensorThresholdDefaults`, both types): on battery / low battery / overload **critical**, on bypass / replace battery warning, plus the old charge < 50/20, runtime < 15/5, load > 70/90; default poll **30 s** (`SensorScheduleDefaults`). ⚠️ Before this the UPS sensor read charge, runtime, load and battery status only, so a power cut stayed GREEN until the battery had drained below 50 %. **`ups-snmp`** (a UPS with a network card, standard UPS-MIB / RFC 1628) runs the generic SNMP read and then `UpsSnmpSensorExecutor.ToUpsResult`: `UpsChannels.FromRfc1628` derives the flags (upsOutputSource 5 or upsSecondsOnBattery > 0 = on battery, 4 = bypass; upsBatteryStatus 3/4 = low), `Merge` adds them in front and puts unit + label on the values read, and the thresholds are applied again (re-applying is safe: `AppendMessage` dedupes). Its default OID list grew by upsSecondsOnBattery / upsOutputSource / upsInputVoltage / upsAlarmsPresent; **migration 7** gives a sensor that still carries exactly the old list the new one (an edited list is left alone, compared ignoring whitespace/line endings - `IsOidList`) and adds ONLY the new alarms (on battery, low battery, on bypass) - not charge/runtime/load, which an admin may have removed on purpose. Some network cards serve the UPS-MIB only once it is switched on in their settings; for an **APC** card that does not, the `ups.profile` parameter ("MIB", default `rfc1628`) switches to APC's PowerNet-MIB (`UpsSnmpSensorExecutor.ApcOids` -> `UpsChannels.FromApc`: upsBasicOutputStatus 3 = on battery, 9/10/16/17 = bypass, upsBasicBatteryStatus 3/4/5 = low, replace indicator 2, runtime TimeTicks -> minutes). Which mapping runs is decided by the CHANNELS (an `apc_*` raw channel = APC), so a hand-edited list works too; `ResolveOids` treats an empty list or ANY built-in default list as "use the chosen profile's default" (the editor pre-fills the standard list, so switching the MIB would otherwise keep reading the UPS-MIB) and leaves an edited list alone. The APC OIDs and codes were cross-checked against the NUT snmp-ups driver's `apc-mib.c`, **not against a real APC card**. **`nut-ups`** (`NutUpsSensorExecutor` + `NutClient`, Core): a Network UPS Tools server (upsd, TCP 3493) - the common small-office case, a UPS on the USB port of a NAS, Proxmox, OPNsense or Home Assistant. Read-only protocol, no login (upsd decides by address - on a Synology the probe must be in "Permitted DiskStation devices"): `LIST UPS` (when `nut.ups` is empty, the first one) + `LIST VAR <ups>`, quoted fields with `\"` escapes; `ups.status` flags OL/OB/LB/RB/CHRG/BYPASS/OVER, FSD counts as low battery; ERR codes are said in words (UNKNOWN-UPS, ACCESS-DENIED with where to allow the address, DATA-STALE, DRIVER-NOT-CONNECTED), something else on the port is not mistaken for NUT. Discovery suggests it when 3493 is open (now in the default discovery port list). `UpsSensorTests` cover the channels, migration 7 and the protocol against a stand-in server - and against a REAL upsd when `MATMON_NUT_TEST=host:port` points at one (Debian `nut-server` + the `dummy-ups` driver in a container; verified 2026-10-22).

**Appliance APIs: Redfish, Proxmox Backup Server, FRITZ!Box.** Three sensors that read a device's OWN interface, each self-contained in Core with a public constructor taking the `HttpMessageHandler` (the tests route requests to stand-ins; DI registers them through a factory so it never has to pick a constructor). **`redfish`** (`RedfishSensorExecutor`, category "Hardware" - new in `SensorTypeCategories.Order`): a server's management controller (iDRAC, iLO, XClarity, Supermicro, iRMC). Service root → Systems (health rollup, `PowerState`, manufacturer + model) → Chassis (max 8) → Thermal (temperatures, fans) + Power (power supplies, `PowerConsumedWatts`), falling back to the newer ThermalSubsystem/ThermalMetrics/Fans and PowerSubsystem/PowerSupplies + EnvironmentMetrics where Thermal/Power are gone (max 16 members each). **The state is the controller's own verdict** (worst Redfish health of systems, chassis and components: OK/Warning/Critical) - it knows every sensor's vendor limits; the readings are channels (`health` 0/1/2, `powerOn`, `temperatureMax` = default, `powerWatts`, `fansFailed`, `psuFailed`, `temp.<slug>` / `fan.<slug>` / `psu.<slug>` carrying the part's own state), the message names the failing parts; default threshold: powered off = warning. Auth: HTTP Basic, and on a 401 a Redfish SESSION that is always DELETEd again (controllers have a handful of session slots - a monitor that left one per poll would lock the admins out). Target = host (https, `redfish.port`) or a full URL (`http://host:8000` - that is how the DMTF mockup is reached). Verified 2026-10-23 against the DMTF's `dmtf/redfish-mockup-server` (gated test `MATMON_REDFISH_TEST=<base url>`, and a Test run in the sensor editor): "Contoso 3500: warning - Power Supply Bay warning (41 °C max, 2 fans, 1 power supply, 344 W)". NOT verified against a real iDRAC/iLO. **`proxmox-backup`** (`ProxmoxBackupSensorExecutor`, port 8007, discovery on 8007): an API token in the Proxmox credential fields (`pve.tokenId`/`pve.tokenSecret`/`pve.user` - a Proxmox credential bundle serves both) sent as `PBSAPIToken=user@realm!name:secret` (a COLON, where PVE has '='); `nodes/localhost/status` (cpu/memory/root → the channel-family names `cpu`/`memoryUsedPercent`/`diskUsedPercent`), `status/datastore-usage` (`datastoreUsedPercent` = fullest, `daysUntilFull` from PBS's `estimated-full-date`, per store `store.<slug>.usedPercent`/`.freeGb`), `admin/datastore/<store>/groups` (`newestBackupAgeHours`, `oldestGroupAgeHours` - no default on the latter: a retired VM keeps its group and its age only grows), `nodes/localhost/tasks?errors=true&since=<24h>` (`failedTasks24h`, `warningTasks24h` - "WARNINGS: n" is a warning, anything else not OK a failure). An unavailable datastore (`error`) is critical; NO datastore says the token lacks the Audit role (a token separated from its user has no rights). Defaults: fullest 85/95 %, days until full < 14, newest backup > 26 h / > 50 h, a failed task, root disk 85/95. 15-min poll. Stand-in tested only - NOT verified against a real PBS. **`fritzbox`** (`FritzBoxSensorExecutor`, port 49000, discovery on 49000, 1-min poll): the connection WITHOUT a login through the UPnP IGD status (`/igdupnp/control/WANIPConn1` GetStatusInfo + GetExternalIPAddress, `WANCommonIFC1` GetCommonLinkProperties + AVM's GetAddonInfos: `connected`, `connectionUptimeHours`, `downloadKbps` = default / `uploadKbps` from the byte rates, utilisation against `downstreamMaxKbps`/`upstreamMaxKbps`); with a FRITZ!Box user (Digest via `HttpClientHandler.Credentials`; no user name = the old `dslf-config` of a password-only box) TR-064 `deviceinfo` (model, FRITZ!OS, uptime) and `wandslifconfig1` (DSL sync rates, noise margin + attenuation - TR-064 reports TENTHS of a dB). Not connected = critical by itself; no UPnP status = critical with where to switch it on; a refused login keeps the sensor healthy and says so (the connection is fine). Default: DSL noise margin < 6 dB = warning. Stand-in tested only - NOT verified against a real box. All three are in the default discovery ports now (8007, 49000 - and 3493 went into `DiscoveryJobStore`'s list, which had missed it). `HardwareSensorTests` covers them.

**Device and service sensors, second batch: printer, domain expiry, SIP, LDAP, OPNsense, Hyper-V.** **`snmp-printer`** (`PrinterSensorExecutor`, category Hardware, 15-min poll, discovery on port 9100 or a printer-ish sysDescr): walks the Printer-MIB (RFC 3805) and the HOST-RESOURCES printer table with the SNMP sensor's own walk (`SnmpSensorExecutor.DiscoverAsync`, every SNMP version and credential): supplies (`prtMarkerSuppliesTable`: a level of -3 = "some left", -1/-2 = unknown - neither becomes a percentage; class 4 = a receptacle, whose level is the space LEFT, labelled "(space left)"), input trays, `prtMarkerLifeCount`, `prtAlertTable` and `hrPrinterDetectedErrorState`. ⚠️ That last one is a BIT MASK in an OCTET STRING, and the walk's display value is text wherever the bytes look like text (0x20 = low toner arrives as a single space) - so `SnmpDiscoveryItem` gained `RawHex` (`SnmpValue.Raw`, the OCTET STRING's bytes) and the bits are read from it. Critical bits: no toner, door open, jam, offline, supply missing; the rest warning; a critical alert = critical, a warning alert = warning. Model from hrDeviceDescr of the printer's row, else `prtGeneralPrinterName`. Channels: `supplyMinPercent` (default, warning < 10), `supply.<slug>`, `tray.<slug>`, `traysEmpty`, `pageCount`, alert counts. Verified against a real Net-SNMP agent serving a colour laser's tables through a `pass` script. **`domain-expiry`** (`DomainExpirySensorExecutor`, category Certificates, once a day): RDAP first - IANA's bootstrap (`data.iana.org/rdap/dns.json`, cached 24 h for the default instance) names the server per TLD - and for a TLD without RDAP (.de, .eu, .io …) WHOIS on 43, the server named by `whois.iana.org`. A sub-domain is walked up label by label until the registry knows it. ⚠️ DENIC (.de) and EURid (.eu) never publish an expiry date: then only the registration is checked and the message says why (default channel `registered`). Redemption / pending delete / client or server hold = critical, an expired date = critical; defaults 30 / 7 days on `daysUntilExpiry`. The registrar comes from the RDAP vcard. Verified against the real registries (`MATMON_RDAP_TEST=1`: Verisign RDAP, nic.io and DENIC WHOIS, free names) and in the sensor editor. **`sip`** (`SipSensorExecutor`, 1-min poll, discovery on TCP 5060): one OPTIONS request over UDP or TCP (RFC 3261 headers, Call-ID matched, 1xx skipped); any final answer = alive - 2xx, and 4xx (401/407 = wants a login, normal for a PBX), healthy; 5xx/6xx = warning; silence = critical. Channels `responseTime`, `statusCode`. Verified against Debian's Kamailio over UDP and TCP (`MATMON_SIP_TEST`). **`ldap`** (`LdapSensorExecutor`, discovery on 389/636): an LDAPv3 client of its own on the SNMP code's BER helpers (`EncodeTagged`/`BerReader`) - no native libldap, which neither the image nor an agent can be relied on to have. Root DSE (anonymous), simple bind (DN or AD UPN), optional search with an RFC 4515 filter (`LdapFilter`: & | ! = =* substrings >= <= ~= and extensible matches such as AD's bit rules; `1.1` attributes, size limit 1000, "1000+"), plain / StartTLS / LDAPS (`LdapSession.Upgrade` keeps the message ids). On AD: `clockSkewSeconds` from the DC's currentTime (defaults 120 / 300 s - Kerberos fails at five minutes), `isSynchronized` FALSE = warning, and a refused bind spells out AD's "data 52e" codes (wrong password, locked, disabled, expired …; result 8/13 = use LDAPS or StartTLS). Verified against Debian's slapd (plain, StartTLS, LDAPS, wrong password, anonymous; `MATMON_LDAP_TEST` + `MATMON_LDAP_PASSWORD`); NOT against a real AD. **`opnsense`** (`OpnsenseSensorExecutor`, 1-min poll): API key + secret as HTTP Basic (the Generic credential fields); `routes/gateway/status` is required (dpinger's "12.3 ms" / "0.0 %", "~" = not monitored; down / force_down = critical, delay / loss = warning), `core/firmware/status` (the last update check - none / update / upgrade / error; `updatesAvailable` with a warning default), `diagnostics/system/systemResources` and `systemDisk` are optional (a user without those privileges just lacks the channels). Field names checked against OPNsense's sources; stand-in tested only - NOT against a real firewall. pfSense has no official API (use SNMP there). **`hyperv-health`** (`HyperVSensorExecutor`, category Windows): a fixed script on the PowerShell engine (WinRM, or locally on an agent on the host) - VMs total / running / off / saved, *Critical states, lost heartbeats of running VMs, replication Warning/Critical, per VM `vm.<name>.up/.problem/.cpu/.memorygb/.uptimehours`, host memory; `Describe` relabels the engine's lower-cased keys from its labels ("SQL 01 CPU") and names the troubled VMs. ⚠️ The engine insists on finding its default channel, so it runs on `vmtotal` (written on the error path too) and `Describe` moves the default to `vmrunning` - with `vmrunning` the error path said "default channel not found" instead of Windows' own message; found by running the script on a real Hyper-V host as a non-member of "Hyper-V Administrators", which now reports Windows' permission text plus what to do. The success path is NOT verified (needs that group). Discovery's default port list gained 389, 636, 5060 and 9100. `DeviceSensorTests` covers all six.

**Update sensors** (pending OS/package updates, same delegation pattern as the disk sensors; default poll 6h, Availability profile): `WindowsUpdateSensorExecutor` (`windows-update`, delegates to the PowerShell engine running a `Microsoft.Update.Session` COM-API script → `pendingUpdates`/`securityUpdates`; live-verified), `LinuxUpdateSensorExecutor` (`linux-update`, reuses the SSH runner with a cross-distro apt/dnf/yum/zypper script → `pendingUpdates`/`securityUpdates`), `SynologyUpdateSensorExecutor` (`synology-update`, SSH `synoupgrade --check` → `updatesAvailable`; best-effort, needs DSM SSH + a privileged account). All default to **Warning** when updates are pending.

## Persistence (important - and the current bottleneck)

**Schema migrations have ONE central place:** `InMemoryMonitoringWorkspaceStore.Migrations.cs` - the instance's equivalent of the cloud's EF Core migration folder. `WorkspaceDocument.SchemaVersion` records how far a document has come, and an ordered, numbered registry (`Migrations`, exposed as data via `SchemaMigrationCatalog` for the shape tests) runs every step above that number, once, then stamps `CurrentSchemaVersion`. Before this, each one-time migration was a method call hand-placed in the store constructor with no version anywhere: it re-ran on every boot, had to detect for itself whether it had already happened, and the ORDER carried logic only a comment recorded (the retired-sensor rewrite must precede the catalog rebuild - now that is migration 2 vs the invariants that follow). A workspace with no `schemaVersion` is version 0 and runs the whole list, which is exactly what it used to get on every start. **Deliberately NOT in the pipeline:** the `Ensure*` seeders/normalisers, which are INVARIANTS that must hold on every boot and therefore still run after it; **map layouts**, because each `MonitoringMap` carries its own `LayoutVersion` and can arrive later via a restore or import, which a per-document version cannot express; and the **telemetry DB**, which has its own schema + migration inside `SqliteTelemetryRepository`. `NormalizeAfterRestoreLocked` runs the same pipeline, so a restored (older) package is brought forward by the same code rather than a hand-picked subset. Adding a migration = append a record with the next version + bump `CurrentSchemaVersion`; never renumber (a workspace in the field already recorded the old numbering), and `WorkspaceSchemaMigrationTests` fails if the numbers are not unique/ascending/gapless or the constant is not the last one.

App state lives in a single JSON workspace file (`data/workspace.json`, configurable via `Matmon__WorkspacePath`), loaded and held entirely in memory by `Services/InMemoryMonitoringWorkspaceStore.cs` (~3700 lines; still large - decomposition is Phase B, in progress). The state is one private `WorkspaceDocument` with 13 collections, guarded by `_gate`. The class is now `partial`, split by concern into sibling files: `InMemoryMonitoringWorkspaceStore.Backup.cs` (backup/restore), `.Persistence.cs` (load/save: `LoadDocument` - runs `NormalizeLoadedDocument` to null-coalesce every singleton (`CloudSettings`/`NotificationConfiguration`/`SummaryReport`/`Cloud`) + collection so a `null` in `workspace.json` can't NRE the host, e.g. a null `cloudSettings` previously crashed the whole host via `TunnelClient` - the debounced `QueueSave`/`SaveDocumentLocked`, `.bak` refresh) and `.Telemetry.cs` (the telemetry facade: `RecordSensorObservation`, history/event/statistics getters, `RunTelemetryMaintenance` rollup+retention, `CleanupStorage`, `MigrateDocumentTelemetryIntoRepository`). The core `.cs` (~3100 lines) keeps topology/template/notification/user/map CRUD, alerts, credentials, defaults and the sensor-definition catalog. There is **no relational database for app state**; the `Microsoft.Data.SqlClient` dependency is only for the MSSQL *sensor*.

- Saves are debounced via a timer with two priorities: `Configuration` (~750ms) and `Telemetry` (~10s, max 30s dirty delay). `SaveDocumentLocked` serializes the **entire** document to a temp file then atomically moves it; a full-file `.bak` copy is refreshed every 5 min. Section-based backups live under `data/backups/`. **Cloud backup/restore (MVP):** `CreateBackupBytes(sections)` / `RestoreBackupBytes(blob, sections)` produce/consume the same package in memory (no disk), so the Config → Backup tab can push a **config-only** snapshot (`All & ~telemetry & ~Users` - Users excluded so a restore can never overwrite/lock-out the local admin) to Matmon.Cloud's `POST/GET/DELETE /api/instances/{id}/backups` (instance-token; cloud stores an opaque `CloudBackup` blob) and restore from it. **The push carries `kind` (manual|scheduled) + `encrypted` + `version` (the build that wrote it) query params** (`CloudBackupClient.PushAsync`; the lists read the cloud's `encrypted` flag back - `CloudBackupItem.IsEncrypted`, the "(encrypted)" in the label is only the fallback for an older cloud - and System → Backup asks for a passphrase only for such a backup); the cloud keeps the **newest 10 per instance PER KIND** (migration `AddCloudBackupKind` adds `CloudBackup.Kind`/`Encrypted`, default manual/false for legacy rows) so a daily scheduled job can't evict the one manual passphrase-protected DR backup - and the `Encrypted` flag rides the list DTOs so the cloud `/backups` page shows a lock + kind. Secrets are DataProtection ciphertext bound to the source instance's key ring → they only round-trip on the **same** instance; a cross-instance restore recovers config but drops credentials. **A package carries only its selected sections:** `CreateBackupPackageLocked` serialises the whole document (a faithful snapshot) and then `StripUnselectedSections` empties every collection outside the mask **and always drops instance-bound state** (`CloudSettings` incl. the cloud token, `Cloud` link status, `LicenseToken`, cached `ServicePartner`). Before this the section mask only gated the *restore*, so a "config-only" cloud backup still shipped every user + password hash and the cloud/license tokens - the "Users are excluded" promise now holds for the blob itself. **Portable secrets (passphrase):** `CreateBackupBytes`/`RestoreBackupBytes` take an optional passphrase - when set, the snapshot's secrets are re-sealed with a passphrase-derived key (`PassphraseSecretProtector`: PBKDF2-SHA256 210k → AES-256-GCM; salt + a verifier blob ride on the package) instead of the instance DP ring, so a **cross-instance** restore recovers credentials too (then re-protected with the target instance's DP on save). The 4 secret Protect/Hydrate methods take an optional `IDataProtector` (default = the instance `_credentialProtector`; the passphrase protector is passed for a portable package). A wrong passphrase is rejected up front via the verifier. The Config → Backup UI has an optional passphrase field on "Back up now" (label marked "(encrypted)") + per-row on restore, and the **BackupRestore** (file upload) page has an optional passphrase field too. **Both restore paths share one body** (`ResolveSecretProtector` + `ApplyRestoreLocked`): the passphrase/instance-protector is resolved once (so the FILE restore honours `SecretsPortable` too - previously it always used the instance protector and silently dropped a portable package's credentials), and after applying the sections the **load-time normalisers re-run** (`NormalizeAfterRestoreLocked`: `MigrateRetiredProxmoxSensors`/`EnsureSensorDefinitionCatalog`/`EnsureDefaultTemplates`/`MigrateAppliedTemplatesToCopies`/`MigrateSslCertificateThresholds`/`EnsureDefaultNotificationConfiguration`/collection ensures) so a restored (possibly older) catalog/topology is migrated + its invariants re-established immediately, not only on the next boot. The `WorkspaceBackupRestoreResult` reports **counts** (probes/sensors/templates/rules/users) and any **dropped credentials** (`HydrationFailed` bundles + notification secrets that could not be decrypted, e.g. a cross-instance restore with no portable passphrase) so the UI says "restored N probes / M sensors … 2 credentials could not be decrypted - re-enter them" instead of just a section count. A portable passphrase must be **≥ 12 chars** (`MinPortablePassphraseLength`, enforced in `CreateBackupBytes`). **The four cloud-backup HTTP calls are centralized in `Services/CloudBackupClient` (push/list/download/delete + the account-scoped list/download below); it resolves url/instanceId/token the same way as the old `ResolveCloud` and is used by the Config Backup tab, the scheduler and the wizard.** **Account-scoped restore (cross-instance DR):** a fresh instance gets a NEW instance id on claim, so its own backup list is empty - the value is restoring a *sibling* instance's backup. The cloud exposes `GET /api/instances/{id}/account-backups(/{backupId})` (instance-token auth) scoped to the **calling instance's `OwnerAccountId`** (join `CloudBackup`→`Instance`), so any instance owned by the account can list/pull the account's backups; `CloudBackupClient.ListAccountAsync`/`DownloadAccountAsync` consume them. The cloud also has an **account-authenticated Backups page** (`/backups`, `InstanceService.ListBackupsForAccountAsync`/`FindBackupForAccountAsync`/`DeleteBackupForAccountAsync` over `AccessibleInstances` = membership ∪ org) to see/download/delete backups across all the account's instances. **Scheduled cloud backup reuses the existing backup-job scheduler** (no new cadence): `WorkspaceBackupJob.Destination` (`BackupDestination.Local|Cloud`); `BackupSchedulerService` pushes a due Cloud-destination job via `CloudBackupClient` using the shared `WorkspaceBackupSections.CloudConfig` mask (= `All & ~telemetry & ~Users`) and records the run via `store.RecordCloudBackupJobRun` (advances the schedule + stamps status, writes NO local snapshot; cloud keeps its own newest-10). The `BackupJobEditor` has a **Destination** select (Cloud disabled until connected; a JS toggle hides the section picker + retention for a cloud job). **A cloud job can carry an optional passphrase** (`WorkspaceBackupJob.ProtectedPassphrase`, DP-encrypted at rest via the same secret lifecycle as notification secrets - the plaintext `Passphrase` is `[JsonIgnore]` and rides `EnumerateNotificationSecrets`) so its scheduled push is **portable** (restorable on a different instance); `BackupSchedulerService` passes it to `CreateBackupBytes` and marks the cloud label "(encrypted)". The editor's passphrase field is shown only for a Cloud destination and is never prefilled - blank on save keeps the stored one (`UpdateBackupJob`). **Setup wizard restore step:** a new `restore` step (after `cloud` in `WizardModel.StepOrder`) lists the account's cloud backups and restores a chosen one (`DownloadAccountAsync` + `RestoreBackupBytes(CloudConfig, passphrase?)`); Users are excluded so the just-created admin survives. Empty/offline/encrypted states are handled (passphrase field only shown for a backup whose label is marked encrypted).
- Data-protection keys: `data/dataprotection-keys`. Runtime `data/` is gitignored. `data/syslog.db` is the central syslog (see **Syslog**), created on first use.
- **Retention & statistics are per-sensor-type by default.** `Matmon.Core/Telemetry/SensorTelemetryProfiles` maps each sensor type to a profile (raw-observation days, statistics bucket minutes, statistics-retention days, event-retention days): *Responsive metrics* for latency/throughput sensors (raw 3d, hourly buckets, stats 14d), *Availability* for up/down sensors (raw 3d, daily buckets, stats 14d, events 90d), *Infrastructure* for probe sensors (raw 2d, stats 14d), and *General* as the fallback (raw 3d, hourly, stats 14d). (Defaults are deliberately lean - ~3 days raw + ~2 weeks of statistics - to keep `telemetry.db` small; bump per-sensor for a longer history.) An explicit `MonitoringSettings` override on the sensor/its ancestors always wins; the profile is only the fallback. The ElementEditor surfaces this as a visible **Telemetry & retention** section that shows the active profile and uses it for the field placeholders.
- **Poll cadence is per-sensor-type by default too.** `Matmon.Core/Domain/SensorScheduleDefaults` maps each type to a fallback poll interval in three intent-driven tiers: **ping 30s**; slow-changing infra (the per-platform disk sensors + backup-job) **6h**; rarely-changing (windows/linux/synology-update + ssl-certificate/certificate-chain) **once a day**; everything else the `Default` **5min**. A hard `Minimum` 15s floor clamps every result. `SensorPollingService` uses it as the `IsDue` fallback so a sensor with no explicit `PollingInterval` polls at a sane type-specific rate. An explicit schedule on the sensor/its ancestors still wins. **The service ticks every 5s, computes the due set (any non-paused, enabled, local sensor whose last observation is older than its interval - this is how catch-up works after downtime or resuming a paused sensor/folder: a single catch-up poll, no backfill), sorts it most-overdue-first (never-run first) and runs it through a bounded worker pool (`Parallel.ForEachAsync`, one DI scope per execution, store writes serialized on `_gate`).** Worker count = `MatmonRuntimeOptions.PollingWorkers` (`Matmon__PollingWorkers`, default 8, min 1), surfaced read-only on the System/Config page. So one slow/timing-out sensor no longer blocks the rest of the cycle.
- **Retries** (`MonitoringSettings.RetryCount`, inheritable, "Retries" on the element/template editors) - a check that comes back **Critical** is run again up to that many times (2 s apart, at most 5) before the result counts (`SensorRetry` in Core, used by the primary's recorded checks AND a probe's scheduled checks / recorded run jobs; an editor's Test runs once). Not for sensors whose answer cannot change by asking again (probe heartbeat/health, local health, mail health, Matmon update, the syslog sensors). A failure that stays says "(failed N times in a row)". ⚠️ The setting was stored, inherited and shown for a long time and did NOTHING; default is 0 (only the built-in "Small Office Baseline" template sets 1), so making it work changed nothing for a sensor nobody set it on.
- **Statistics are accurate, downsampled aggregates - not a running average - and are stored per channel.** `SensorStatisticsBucket` carries avg/min/max, the low/high percentile (bottom 1% / top 1%) and a healthy/warning/critical distribution (→ uptime %); `DefaultChannelKey` is the channel identity. `Matmon.Core/Telemetry/TelemetryRollup.AggregatePerChannel` (pure, unit-tested) emits one bucket **per numeric, non-virtual channel** per window (a bare value with no channels folds into a `"default"` bucket); `Aggregate` (single default-channel) is kept for the unit tests. The SQLite `sensor_statistics` PK is `(sensor_id, bucket_minutes, bucket_start, default_channel_key)`; `SqliteTelemetryRepository.MigrateStatisticsToPerChannelKey` rebuilds an older 3-column-PK table once (existing rows keep their channel key, so prior history survives as the then-primary channel). `StatisticsRollupService` (Primary-only, every 5 min) calls `IMonitoringWorkspaceStore.RunTelemetryMaintenance`, which recomputes the recent buckets per sensor/channel from raw data **and** applies all telemetry retention (raw/statistics/events) **plus resolved-alert retention** (keeps every active alert but caps the resolved tail to the newest 500 within the event-retention window, so `_document.Alerts` - Alerta-style persist-until-ack, previously never pruned - and `workspace.json` stay bounded; the AlertRaised/Resolved events keep the audit trail). The Alerts page also renders only active alerts + the newest `ResolvedRenderCap` (200) resolved rows into the DOM (tab counts still use the full set) so a long history doesn't inflate the page. Pruning and aggregation are therefore **off the polling hot path** - `RecordSensorObservation` only appends the raw observation, its state-change event and the alert sync. **The poll path only re-saves `workspace.json` when the alert sync actually changed `_document.Alerts`** (observations + events live in SQLite, so alerts are the only workspace-state a poll touches): `SyncSensorAlertFromObservation`/`MarkAlertsRecoveredForElement` return whether they made a **persist-worthy** change (raise / resolve / recover / re-alarm / state|message|identity change) and `RecordSensorObservation` `QueueSave(Telemetry)`s only then. A healthy poll, or an active alert whose only change is its decorative `LastSeenUtc`, no longer rewrites the file every poll (that was per-poll disk churn); `LastSeenUtc` is recomputed on the next poll so its persistence lagging by a save is harmless. Covered by `AlertSaveChurnTests`. The SensorDetails Statistics tab shows one channel at a time (the "primary"/graph channel by default) with a **Channel** selector (`StatsChannel`) when a sensor has multiple channels with stats. **Per-channel logging is opt-out:** each channel value carries `SensorChannelValue.LogByDefault` (executors set it `false` for noise like boolean up/valid flags - e.g. SSL `valid`, TCP `open`); the user can override it per channel via a "Log to statistics" checkbox in the Channels & thresholds editor, stored as `MonitoringSettings.ChannelLogging` (channel key → bool, inheritable + trimmed like `ChannelVisuals`). `RunTelemetryMaintenance` reads `GetChannelLogOverrides` and passes it to `AggregatePerChannel`, which skips channels resolving to not-logged (`override ?? channel.LogByDefault`). **Virtual `sensorState` channel:** `SensorExecutionResultHelper.ApplyDefaultChannelSelection` (called centrally in `SensorExecutionService`) prepends a virtual `sensorState` channel to every result (`1` = healthy, `0` = problem, `IsVirtual = true`); it's excluded from the statistics rollup (numeric, non-virtual only) but **is** surfaced in the Channels & thresholds editor as a read-only row - no thresholds, but it can be picked as the **primary/default channel** (→ `MonitoringSettings.DefaultChannelKey = "sensorState"`, honored by `ApplyDefaultChannelSelection`) and given a visual/logging. `WorkspaceSensorChannelThresholdFieldInput.IsVirtual` drives the read-only rendering in `_SensorThresholds` (the `BuildSensorChannelHints` `!IsVirtual` filter was removed; virtual channels sort last). **Dynamic (script) sensors don't fabricate channels:** `BuildSensorChannelHints` no longer synthesizes a placeholder row from `defaultChannelKey` - a dynamic sensor with no observation shows an empty-state ("channels appear after the first run") and its channels are only the ones from the latest observation (plus any the user adds manually). A managed channel key (has stored thresholds/visuals/logging) that isn't in the latest reported channels is flagged `WorkspaceSensorChannelThresholdFieldInput.IsOrphaned` (only once the sensor has actually reported channels) and rendered as a dimmed "no longer reported" row with a delete affordance - never auto-pruned, so config survives a transient empty run. `SensorThresholdEditorState.visibleCount` is driven by real (reported/configured) rows, so a fresh dynamic sensor shows no blank channel cards.
- **Telemetry now lives in SQLite (Phase A done).** `Matmon.Core/Telemetry` holds `ITelemetryRepository` (storage contract for observations/events/statistics) and the embedded `SqliteTelemetryRepository` (WAL, `Microsoft.Data.Sqlite`). `InMemoryMonitoringWorkspaceStore` delegates all telemetry storage/queries/prune/cleanup to it; the `SensorHistory`/`Events`/`SensorStatistics` collections on `WorkspaceDocument` are kept only as a backup/restore transport and are **always empty in `workspace.json`** (cleared on load). On startup `MigrateDocumentTelemetryIntoRepository` moves any telemetry found in an existing `workspace.json` into `telemetry.db` once (only when the DB is empty), then drops it from the JSON. DB path: `data/telemetry.db` (override `Matmon__TelemetryPath`). The former save bottleneck is gone - telemetry saves no longer re-serialize history. Backup create pulls the selected telemetry sections from the repo into the snapshot; restore pushes them back via `ReplaceAll*`. **Perf:** the repo keeps an in-memory latest-observation-per-sensor cache (`_latestBySensor`), so `GetLatestObservations`/`GetLatestObservation` (dashboard + polling hot paths) never scan the table; WAL is checkpoint-truncated on startup and after bulk imports, with `wal_autocheckpoint` on. Without this the dashboard did a full-table window scan per load (~15s on a real DB).

## Auth & authorization

Cookie auth (`Program.cs`). Roles `Viewer` / `User` / `Admin` (`MatmonUserRole`). Admin-only pages are declared with `AuthorizePage(..., MatmonSecurity.AdminPolicy)` conventions; a global `MatmonPageWriteGuard` MVC filter enforces write protection (POST allowed only on `/Login`, `/Logout`, `/Setup`, `/Account` (self-service, any authed user), `/Alerts` for operators (`CanOperateAlerts` = Admin/User, so **Viewer is read-only**), else Admin). API paths return 401/403 (JSON) instead of redirecting. Passwords hashed via `MatmonPasswordHasher`. **Secrets encrypted at rest via ASP.NET DataProtection:** credential bundles (`HydrateCredentialBundles`/`ProtectCredentialBundles`) **and** notification secrets - SMTP `EmailNotificationSettings.Password`, `WebhookNotificationSettings.Secret`, `NotificationReceiver.Secret` (`HydrateNotificationSecrets`/`ProtectNotificationSecrets`, called from the credential hydrate/protect on every load/save; the plaintext is `[JsonIgnore]`-cleared before serialize and restored after, ciphertext in `Protected*` fields; legacy plaintext migrates on first save). Never written to `workspace.json` in the clear. **Secret sensor PARAMETERS too** (an inline `winrm.password` typed into a sensor's own fields rather than a credential bundle - one was found in the clear in a real workspace): `ProtectSecretParameters`/`HydrateSecretParameters`, called from the same credential protect/hydrate pair, so they follow every path those take (save, load, `.bak`, local + cloud backup, the portable passphrase re-seal). A parameter is secret when a sensor type DECLARES it `SensorParameterKind.Secret` or when its last name segment ends in password/secret/apikey/token/passphrase/privatekey (`IsSecretParameter` - a retired type's or hand-typed parameter is in no definition, and guessing "not secret" there is the expensive mistake). Parameters are a plain string dictionary, so the ciphertext lives in the VALUE behind the `enc:dp1:` marker; the in-memory document always holds plaintext (executors, probe assignments and editors are unchanged) and only the serialized form is sealed. A value that fails to decrypt keeps its ciphertext and is never re-sealed, like a credential bundle with `HydrationFailed`. Legacy plaintext is sealed on the next save; older snapshots under `data/backups/` still hold it until they age out. (`discovery-jobs.json` persists discovery suggestions' settings as-is - normally no secrets there, but it is not on this path.) The **Local Program** allow-list (`LocalProgramSensorExecutor.IsAllowed`) resolves symlinks (`File.ResolveLinkTarget`) to the final target before the allow-list check, so a link inside an allowed dir can't escape it.

**First-run setup (`/Setup`).** A fresh install with **no provisioned admin** runs a one-time setup that creates the first admin account (e-mail + password, `MatmonUser.Email`; login matches e-mail *or* username). `IMonitoringWorkspaceStore.IsSetupRequired()` is true while `WorkspaceDocument.SetupCompletedUtc` is null; a Primary-only middleware (before auth, in `Program.cs`) funnels every non-exempt page to `/setup` until done. `CompleteInitialSetup(email, password)` creates the admin + stamps `SetupCompletedUtc` + seeds one **default notification rule** (`SeedDefaultNotificationRuleLocked`, also run on the headless `Matmon__Auth__*` seed path, guarded by zero existing rules): all sensors, Warning+Critical, to the built-in **All users** receiver, with **no fixed sender** so it falls back to the workspace default SMTP - inert until an admin configures SMTP (or points it at the Cloud sender), then it delivers automatically with no editing. (For this to survive, `EnsureDefaultNotificationConfiguration`'s per-load rule fixup now skips reassigning a `ReceiverId` that is a built-in/virtual receiver - `NotificationReceiverDefaults.IsBuiltIn` - instead of clobbering it because it isn't in `NotificationReceivers`.) **No admin is auto-seeded by default** - `MatmonAuthOptions` defaults to empty and the old "fall back to admin/admin" lines are gone; setting `Matmon__Auth__Username/Password` (env) still pre-provisions an admin headlessly and marks setup done. `EnsureDefaultUsers` migrates any **existing** install (already has users) to `SetupCompletedUtc = now` so the wizard never hijacks a configured workspace. The optional setup *wizard* steps (networks / discovery / probes / notifications, skippable) land after account creation - not built yet.

**Credential editor (definition).** Container/host + template credential bundles render as a compact **list** (one row per bundle: name + kind chip + Edit/Delete) with editing in an **overlay modal dialog** (a `mat-listgroup` of rows, each editor a MatUi `<dialog data-credential-modal>` opened through `MatUi.dialog` by `initializeCredentialEditors` in `js/app/sensor-editor.js` - closing a NEW row's dialog without Done (Esc, backdrop, X) discards it; Add reveals a hidden slot and opens its dialog, a row left blank collapses out). **Every credential kind now has explicit mapped fields** - Windows (`winrm.*`), SSH/Linux (`ssh.*`), Proxmox (`pve.*`), SQL Server (`mssql.*`), SNMP (`snmp.*`), UniFi (`unifi.apiKey`), **Mail** (`mail.smtpUsername`/`mail.smtpPassword`/`mail.imapUsername`/`mail.imapPassword` - both accounts of the Mail Health round-trip in one encrypted bundle), Generic (`generic.username/password/token`, consumed by the script sensors via the MATMON_* substring resolver). The legacy raw **key=value "Advanced values"** editor was removed app-wide; `ApplyCredentialBundles` starts from the bundle's already-stored values and overlays the explicit per-kind fields (a blank Secret field preserves the stored secret - `ApplyCredentialSecretField` - so dropping the raw editor never wipes data). **Generic fallback:** `MonitoringSettings.ApplyCredentialValuesForKinds` first resolves a bundle of the sensor's expected kind; if none exists it falls back to a **Generic** bundle (the explicitly-selected one when it's Generic, else the first) and maps its `generic.username/password/token` onto the keys the sensor actually reads (Windows→`winrm.*`, SSH/Linux→`ssh.*`, SQL→`mssql.*`, UniFi→`unifi.apiKey` from the token, Mail→`mail.smtp*`+`mail.imap*` using the same account for both legs; Proxmox token-auth + SNMP have no mapping). So one shared Generic credential can serve typed sensors that lack a dedicated bundle.

## Configuration (env vars)

All under the `Matmon__` prefix (see `appsettings.json` + README). Common: `Matmon__Mode`, `Matmon__WorkspacePath`, `Matmon__SyslogPath` (the syslog database, default `syslog.db` beside the workspace), `Matmon__PluginsPath` (external plugin DLLs, default `plugins` beside the workspace; beside the executable on an agent), `Matmon__Auth__Username|Password`, `Matmon__HeartbeatIntervalSeconds`. `Matmon__TrustedProxies` says whose `X-Forwarded-For/-Proto/-Host` is believed (`TrustedProxies`: default loopback, RFC 1918, link-local and IPv6 ULA; a list of addresses/CIDRs replaces it, `any` trusts everybody, entries that do not parse are logged and ignored) - the headers used to be believed from ANY sender, so a client could pick the address the per-IP rate limits (agent enrolment, push) count and the scheme/host the instance builds links from. ⚠️ On Docker Desktop every published-port connection arrives from the private gateway address, so there anyone can still set the header; on Linux the real client address arrives. `Matmon__DockerSocketPath` (default `/var/run/docker.sock`) and `Matmon__UpdateFeedUrl` belong to the self-update (see **Self-update**). `Matmon__AllowedProgramPaths` (semicolon/newline list) ADDS to the **Local Program** allow-list kept under System > General - read directly from the env var by `LocalProgramSensorExecutor` (not appsettings). Seeding/provisioning flags default to false: `SeedSampleData`, `ProvisionLocalDockerProbe`, `ProvisionDemoSensors`, `AutoCreateProbeSystemSensors`, `CreateStarterMap`, `DemoServicePartner` (dev/preview: seeds a dummy managing partner - `DemoServicePartnerSeed` - so co-branding is visible without a real cloud link; short-circuits the cloud loop). Secondary: `ProbeId`, `ProbeName`, `ProbeToken`, `PrimaryUrl`. **Matmon.Cloud link - managed in the UI (System → Cloud), not env.** The primary connect is an **OAuth/PKCE claim** (UniFi-style, no password on the instance): enter a name (pre-filled by `CloudInstanceNameSuggestion` - the wizard, System → Cloud and "Disconnect & reconnect" all use it: a name the admin gave the root probe, else the first label of the host name the admin reached the instance by - `nas` from `http://nas.fritz.box:8099` - else the root probe's name / the machine name; an IP address or `localhost` says nothing about the machine and falls through. ⚠️ Every fresh install's root probe is called `ProbeElement.DefaultRootName` = "Primary Probe" and the suggestion used to be exactly that, so each new installation of one account collided with the previous one; the store's seed uses the same constant, which is how the suggestion tells "the admin chose this" from "nobody did"), hit **Connect** → the admin's browser is redirected to the cloud consent page (`/instances/claim`, cloud-login-gated) which creates the instance under the signed-in account and hands a one-time code back to the instance's `/CloudClaim` callback, which exchanges code+verifier at `POST /api/instances/claim/exchange` for the id + token (see **Cloud instance claim** below). Two **Advanced** fallbacks remain: e-mail+password headless provision (`OnPostCloudProvisionAsync` → cloud `/api/provision`) and manual paste of an existing instance id + token (`OnPostCloudConnect`). Disconnect to unlink - **`DisconnectCloud` also turns OFF `RelayAlerts` + `FullAccessEnabled` and disables the built-in "Matmon Cloud" sender** (kept, so rules keep their reference), so a disconnected link can't leave relay rules silently dropping every alert or the tunnel client retrying with no token; re-enable them after reconnecting. **Provision hardening:** `/api/provision` (password-only) **refuses accounts with 2FA enabled** (`403 two_factor_required` - the browser Connect flow signs in through the normal login and honours 2FA) and is **rate-limited per client IP** (`AddRateLimiter` policy `provision`, 10/min → 429); the instance maps 401/403/409/429 to clear messages. The instance also **refuses a plain-http cloud URL to a public host** for both provision + claim (`CloudUrlPolicy.IsPlainHttpAllowed` in Core: https always ok; http only to loopback / RFC1918 / link-local / a dotless Docker alias / a `.local` name) so the sign-in password never travels unencrypted to a public FQDN. **A connect is a NEW instance; taking one over is an explicit act (`InstanceService`).** `CreateAsync` always creates: a fresh installation - even one run through the setup wizard on the same machine, suggesting the same name - never inherits the id, plan or license of an existing cloud instance; when the account already has an instance of that name the new one gets the next free "Name (2)" (`UniqueName`, pure + tested). It used to REUSE a same-named offline instance silently ("reconnect-safe"), which is exactly how a reinstalled box came back as the OLD instance with its old license - and how a second box that merely shared a name could take over a first one that was switched off (token rotated, license moved). Taking over is `TakeOverAsync(accountId, instanceId)`: the user's explicit choice, offered by `FindTakeoverCandidateAsync` (the instance named by ID - a "disconnect & reconnect" knows the id it dropped - else the account's same-name instance) as a `TakeoverCandidate` whose `State` is `Available` (offline, enabled), `Live` (heartbeating) or `Deactivated`. Only `Available` can be taken over: a live one would be kicked offline, and a deactivation is an admin lock a customer must not lift by reconnecting (`InstanceConflictException` `Live` / `Deactivated`). A takeover keeps id, plan, license, memberships, history, backups and the instance's organization (it never moves it), re-issues the token - which locks out whatever installation held the old one, so two boxes never report as one instance - and is written to the account log. The consent page offers it as two radio options, **default "Create a new instance"** (the mistake that stays visible - a fresh Free instance - rather than the one that silently locks another box out), and re-resolves everything on POST (the posted instance id must be this account's and still `Available`). Headless `/api/provision` takes `takeOver` (default false, so an older client that sends nothing gets a new instance); a takeOver of a live or deactivated instance is `409 name_in_use|instance_deactivated`, and the answer carries the name the instance really got plus `tookOver`. **While connected the link identity is locked** - the cloud URL/id/token are shown read-only and only the display name stays editable (`OnPostCloudRenameAsync`); changing the URL or linking a different instance requires **Disconnect** first (the old `OnPostCloudUrl` in-place URL edit was removed). This persists to `WorkspaceDocument.CloudSettings` (`CloudConnectionSettings`; token **DataProtection-encrypted** at rest via the credential protector), exposed through `GetCloudConnectionSettings`/`GetCloudConnectionToken`/`SetCloudConnectionSettings`/`DisconnectCloud`. The Primary-only `CloudConnectionService` re-reads settings every ~5s and connects/disconnects **live (no restart)**; it sends a heartbeat on a configurable cadence (`CloudConnectionSettings.CloudHeartbeatIntervalSeconds`, set in System → Cloud, else the `Matmon__CloudHeartbeatIntervalSeconds` env/default **30s**, floored at 15 - **separate from the probe `HeartbeatIntervalSeconds`** so slowing the cloud beat doesn't slow probes) carrying aggregate metadata (version, host, sensor/probe/map counts, open-alert / error / warning / ack counts from `GetActiveAlertCounts`, **plus its own effective interval `HeartbeatIntervalSeconds`** - the metadata gather is wrapped so a failure there still posts a minimal beat rather than reading as offline) - the dead-man-switch + public-dashboard feed - **plus a protocol version** (`CloudConnectionService.ProtocolVersion`, int, bumped when the cloud↔instance contract changes): the cloud stores it on the instance and flags any instance reporting an older protocol than `InstanceService.CurrentProtocolVersion` (or none = pre-versioning) as an **"Outdated"** badge in the instance lists (`InstanceService.IsOutdated`) - and records the last outcome in `WorkspaceDocument.Cloud` / `CloudConnectionState` (shown on the tab). **The heartbeat does NOT re-save `workspace.json` every beat:** `UpdateCloudConnection` keeps the volatile status/last-heartbeat in memory and only `QueueSave`s when the link **identity** (instance id / cloud url) changes, and `SetLicenseToken` keeps the freshest (re-signed-every-beat) token in memory but persists it at most once per **6h** (a 14-day-lease token survives a restart). Before this, every ~30s beat force-serialised the whole document and re-protected every secret - pure disk churn. The cloud aggregates these across an account's instances into a sidebar alert box (Err/Warn/Ack/Offline) + dashboard, and treats an instance offline once its **adaptive online window** lapses: each heartbeat stamps `CloudInstance.OnlineUntilUtc = now + InstanceService.GraceFor(reportedInterval)` (`= max(90s, 3× the instance's reported interval)`), and online/offline everywhere reads that deadline vs `now` (`IsOnline`, the list/summary/alert query filters). This replaced the old fixed 150s `OfflineAfter` cutoff (kept only for the migration backfill), so a deliberately slow beat no longer reads as a false outage while a fast one is still noticed promptly. A pre-upgrade instance that doesn't report its interval falls back to `DefaultHeartbeatSeconds` (60 → 180s grace). Migration `AddInstanceHeartbeatCadence` adds the two columns + backfills the deadline for currently-online rows. The heartbeat handler also returns the latest release version (for the instance's update badge) via `ExecutorClient.GetLatestVersionAsync`, which it awaits **inline** - so that refresh is **bounded to 5s and negatively cached for 5 min** after a failed attempt (`ExecutorVersionState.MarkFailure`); an unreachable/hung executor used to stall every instance's heartbeat response past the instance's 15s client timeout, so every instance recorded "failed" beats while the cloud already had them. **Cloud-side lifecycle management:** from the cloud an operator can sever/remove an instance without touching the box - **Disconnect** (`InstanceService.DisconnectAsync`) rotates the instance's token so its next heartbeat 401s and it shows disconnected, while the row + config stay (re-claimable: reconnect from the instance and **take it over** on the consent page); **Delete** soft-deletes (hidden, restorable) and **Delete permanently** (`PurgeAsync`, admin-only, only on an already-soft-deleted instance) removes the row (cascades backups/memberships, detaches cloud sensors). These are exposed to the platform admin (`Admin/InstanceDetail`: Disconnect/Delete/Restore/Purge), the owning account (`/Members`, owner-gated Disconnect + Delete - the owner "Delete" spells out its real effect: the host loses its connection, a paid licence is cancelled, only an admin can restore) and the managing **partner** (`Reseller/CustomerDetail`, per-instance Disconnect/Delete gated on the customer's `PartnerCanManage` consent - `DisconnectAsResellerAsync`/`DeleteAsResellerAsync`). **Any of these lifecycle actions force-closes a live Full Access tunnel at once** (`TunnelRegistry.CloseAsync`, called from `DisconnectAsync`/`SetDisabledAsync(true)`/`DeleteAsync`/`DeleteAdminAsync`/`PurgeAsync`), and the browser `/app` + `/embed` routes re-check `Disabled`/`DeletedUtc`/`LicenseTunnelEnabled` per request (defence in depth) - so a revoked/deactivated instance stops serving the console immediately instead of lingering until the socket drops. **Deactivate is a deliberate lock, not an outage:** `SetDisabledAsync(true)` marks the instance offline, sets `OfflineNotified` (so the dead-man "went offline" e-mail does NOT fire), logs it, and customer surfaces show **"Deactivated"** (via `InstanceService.InstanceStatusText`) instead of a plain "Offline"; the admin Deactivate button confirms first. The heartbeat endpoint distinguishes a **blocked** instance (valid token, but `Disabled`/`DeletedUtc`) from a bad token via `InstanceService.CheckTokenAsync`→`TokenCheck` and returns **403 `{error:instance_deactivated|instance_deleted}`** (not 401), which the instance maps to a clear "deactivated by the cloud administrator" status while it keeps beating so it recovers the moment it is reactivated. A **deliberate disconnect** initiated by the instance itself (`OnPostCloudDisconnect`) now also tells the cloud first (best-effort `POST /api/instances/{id}/disconnect`, instance-token auth, before `DisconnectCloud` drops the token) so the cloud marks it offline **immediately** (`RecordDisconnectAsync` clears `LastHeartbeatUtc` - which is what keeps the dead-man alert quiet - and leaves `OfflineNotified` FALSE, so a later reconnect sends no spurious "back online"; the cloud-side `DisconnectAsync` does the same since 2026-10-25, and a reactivation or restore gives the instance a fresh grace window (`OnlineUntilUtc`) so the monitor's next tick does not mail "went offline" before its next beat) instead of lingering "online" for the 150s timeout; if the cloud is unreachable the timeout is still the fallback. **Public status page:** the anonymous `/status?token=` page (name/online/counts/last-heartbeat) is gated by `CloudInstance.PublicStatusEnabled` (migration `AddPublicStatusEnabled`, grandfathered on for existing rows) - `FindByPublicTokenAsync` serves it only while enabled and the instance is not disabled/deleted, so a leaked link goes dark when the owner disables it. The owner can **regenerate** the token (`RegeneratePublicTokenAsync`, invalidates the old link) or **disable** the page (`SetPublicStatusEnabledAsync`) on the instance's Members page; the link is shown only to Owner/Admin (not Viewers). The instance can set its own **cloud display name** from System → Cloud ("Update name" → `OnPostCloudRenameAsync` → cloud `POST /api/instances/{id}/name`, instance-token auth); the cloud owner can also rename it on the instance's Members page. Over the Full Access tunnel the embedded UI's live AJAX poll drops to 30s (the `_Layout` emits `data-embedded` → `core.js` reads it). The env vars `Matmon__CloudUrl` + `Matmon__CloudInstanceId` + `Matmon__CloudInstanceToken` are only a **first-run bootstrap**: once the user connects/disconnects in the UI (`CloudSettings.Configured`), the UI wins and env is ignored. ⚠️ **An environment link IS an identity**: `MatmonRuntimeOptions.HasCloudBootstrapLink` (URL + a valid instance id + token; a bare URL only prefills the form and is not a link) - a workspace that has not taken over in the UI links itself to that instance, so a fresh data folder started with the SAME environment is that cloud instance again, license included (the local dev override `docker-compose.dev.override.yml` carries one - which is why wiping `data/` there and re-running the wizard reconnects to the old instance). The wizard's cloud step and System → Cloud therefore say so (`CloudEnvLinkActive`: "already linked by the environment", with the instance id) and offer **Keep this link** (`Config.OnPostCloudKeepEnvLink` stores it, so it is managed in the UI from then on) or **Unlink** (`OnPostCloudUnlinkEnvLink`: tells the cloud it is leaving, then `DisconnectCloud`, so the environment is ignored and Connect asks the cloud for a NEW instance); the wizard used to show "not connected" for it while the link and the license were in fact active. A cloud feature switched on while the link still comes from the environment (relay, Full Access, the heartbeat interval, rename, partner consent, the cloud backups) adopts that link first, like "Keep this link" (`Config.AdoptEnvironmentLink`): those features read the STORED link, so they used to report success and do nothing. A bare `Matmon__CloudUrl` (no id + token) shows the Connect form prefilled, not a fake connected card (`CloudLinkActive`). A changed heartbeat interval beats at once - the cloud's grace comes from the interval the last beat reported, so a longer new interval used to make the cloud declare the instance offline (and mail/push everyone) first. Empty = fully offline; the link never takes the monitor down (failures are logged + retried). Login is **e-mail + password** (`LoginModel.Email`), aligning the local identity with the cloud account. Matmon.Cloud is a **separate repo** (proprietary, same stack: ASP.NET Core .NET 10 + PostgreSQL, accounts/ownership).

**Reseller co-branding.** A managing **partner** org (cloud `Organization.IsPartner`) sets a logo (`LogoBytes`/`LogoContentType`, **PNG/JPEG only, magic-byte-validated** ≤256KB - SVG/other rejected because the raster-only PDF would crash), accent colour (`BrandColorHex`, validated to `#RRGGBB`) and contact URL (`ContactUrl`, validated to absolute **http/https** so a `javascript:` link can't XSS a managed instance) on the cloud **Partner-portal `/reseller/branding`** page (`Pages/Reseller/Branding.cshtml`, Reseller-role-gated, resolves the acting partner org via `OrganizationService.GetPartnerOrgIdForAccountAsync`). *(This branding config was moved out of the generic company page `/organization` - it is a partner capability, not a company-profile field; `/organization` now shows partners just a link to the portal. **Cloud alert relay (as a "Cloud" notification sender).** The relay is a **sender kind**, not a separate side-channel: `NotificationEndpointKind.Cloud`. Enabling it in System → Cloud (`CloudSettings.RelayAlerts`, master switch, **no recipients field**) auto-provisions/enables a built-in **"Matmon Cloud"** sender (`SetCloudRelaySettings(bool)` → ensures one exists/enabled; disabling turns it off but keeps it so rules keep their reference). A rule that selects the Cloud sender delivers through the gateway like any other rule - recipient from the rule's **receiver** (`ResolveRecipient`), templates from the rule. `NotificationDispatchService` matches rules **once** then routes by the rule's sender kind: a Cloud sender → `NotificationTransportClient` POSTs to the cloud's `/api/instances/{id}/notify` (instance-token auth, `{channel:"email",to,subject,text,html}`) when the link is connected + relay enabled (`NotificationDeliveryFactory.ResolveCloudRelay`); see **Channels** for the rest. Same cooldown/episode throttle + retry/backoff for all channels. **SMS and phone calls ride the same path:** two RECEIVER kinds, `NotificationEndpointKind.Sms`/`Voice` (a number in international format, `PhoneNumbers.Normalize` - the same rule the cloud applies; the receiver editor refuses anything else), used with the Cloud sender: the delivery's `CloudChannel` is `sms`/`voice`, the body carries the rule's SHORT text (`{{summary}}`) and a `severity`. **Critical only:** `NotificationSeverity.IsCritical` (= `state.urgent`, i.e. Critical and not recovered); the dispatcher skips a warning or a recovery to a phone route QUIETLY (debug log - `NotificationDeliveryFactory.IsPhoneRoute`), in rules and escalations alike, and the factory refuses it in words for the test button, which pretends a critical alert for a phone route (or it could never be tested). The cloud checks severity again and enforces per-instance limits; a refusal comes back as 422, which the transport does not retry (a DROPPED e-mail too - no SMTP on the cloud, no valid recipient: it used to answer 202, which the instance counted as delivered and its Send test reported as sent) (a 429 would be retried and send a stale SMS later). The cloud sends them through seven.io or smsflatrate.net - a primary provider and an optional fallback that takes over in the same attempt when the first does not deliver (down, out of credit, key refused), set up in the cloud admin under System > SMS & calls; every message is a spool entry that says which provider delivered (Matmon.Cloud `PhoneProviderRouter`). A phone receiver with a non-cloud e-mail sender says it needs the Matmon Cloud sender; a webhook sender may use the number as `{{receiver.target}}` (an SMS gateway of one's own). Log lines mask the number (`PhoneNumbers.Mask`).

**Browser notifications (Web Push) - a sender of its own.** `NotificationEndpointKind.Push` is the built-in "Browser notifications" sender: one per instance, created by the boot invariant `EnsureBrowserPushSender` (an admin may switch it off or rename it, not delete it - it would come back), editor type read-only like the Cloud sender. Its RECEIVER names users, not addresses: a built-in user group (All users / admins / operators) reaches its members' devices, a receiver with e-mail addresses the devices of the users with those addresses (`ResolvePushDevices`); anything else is refused in words, and so is a rule nobody it names has a device for ("nobody in 'All users' has switched browser notifications on yet"). **The rule**: "Browser notifications" - every sensor, Warning + Critical, to All users, 15 min / 5 - added by **migration 10** to an existing workspace and at setup (`EnsureBrowserPushRuleLocked`; ⚠️ the setup seed counts only rules OTHER than it, because migration 10 adds it to a fresh document before setup, and the old "no rule yet" guard then skipped the e-mail default). **Devices**: `PushDevice` (Core) in `WorkspaceDocument.PushDevices` - user, endpoint, p256dh, auth, a name from the user agent ("Chrome on Android"), created / last used; upserted by endpoint (the same browser signed in as someone else takes THEIR notifications), at most 20 per user, removed with their user, **never in a backup** (instance-bound: the subscription belongs to the browser and to this instance's VAPID pair). Registered on **Account > Notifications** ("This device": permission, `pushManager.subscribe` with the instance key, `POST /api/browser-push/devices`; "Turn them off here" unsubscribes + `/remove`; the page lists the endpoints the server knows, so a subscription the server forgot shows as OFF instead of being re-registered behind a Remove; "My devices" with Send a test / Remove). The APIs (`GET /api/browser-push/key`, `POST /api/browser-push/devices[/remove]`) need the cookie AND an `X-Matmon-Request` header (a cross-site page cannot send that without a preflight nobody answers). On iPhone/iPad Web Push works in the installed app only (iOS 16.4+) - the card says so; it needs https like the service worker. **The protocol**, taken over from MatMail (no NuGet): `Services/WebPush/` - `WebPushEncryption` (RFC 8291 aes128gcm; `BrowserPushTests` checks it byte for byte against the RFC's own example), `WebPushKeys` (VAPID P-256 pair in `push-keys.json` beside the workspace, the private half DataProtection-sealed; lose it and every device must turn notifications on again), `WebPushClient` (`matmon-webpush` HttpClient whose `ConnectCallback` only ever connects to a PUBLIC address - the endpoint comes from a browser, so otherwise a signed-in user could make the instance post into its own network; TTL 1 day, Urgency high for a critical alert, a Topic per alert so an undelivered older one is replaced; 404/410 = the device is gone and is forgotten) and `BrowserPushNotifier`. The transport (`NotificationTransport.Push`) counts it delivered when ONE push service took it; it is retried only when nobody got it and some only failed (a retry would repeat it on the devices that have it). **What it shows** (`NotificationDeliveryFactory.BrowserPushContent`): the rule's subject as title, its short message as text without the subject repeated at its start, a tap opens the sensor (`element.id` / `alert.id` are context values now), one notification per alert (`tag`), the open-alert count as the app badge; `sw.js` shows it (icon + the white-M `brand/badge-96.png` for Android's status bar) and focuses or opens the window on a tap. The rule list's type chip now comes from the SENDER (it showed the legacy ChannelKind - "Email" for a browser or webhook rule), and a built-in user group receiver reads as its name (it read "email · unset"). Verified end to end with a headed Edge: subscribed through the Account page (endpoint at wns2-*.notify.windows.com), a test accepted by the Windows push service. **Matmon.Cloud has the same** per ACCOUNT (its `CloudPushDevice`, the VAPID pair in its platform settings, the device card on its account page): it tells the devices of everyone with access to an instance when that instance goes offline or comes back (its docs/ui-conventions.md).

**Cloud instance claim (OAuth/PKCE "Connect").** The chicken-and-egg-free way to link a fresh instance: it has no token yet, so SSO can't be reused. `Config.OnPostCloudClaim` generates a PKCE verifier + `code_challenge = base64url(SHA-256(verifier))` and a random state, stores `{state, verifier, url}` in a **DataProtection-encrypted, HttpOnly, SameSite=Lax, 10-min cookie** (`matmon_cloud_claim`), and redirects the browser to `{cloudUrl}/instances/claim?redirect_uri={self}/CloudClaim&state=…&name=…&code_challenge=…`. The cloud consent page (`ClaimInstanceModel`, cloud-login-gated; validates `redirect_uri` is absolute http/https and shows its host) on confirm creates a new instance owned by the signed-in account (`CreateAsync`) or - by explicit choice - takes an existing one over (`TakeOverAsync`; see **A connect is a NEW instance** above), then `ClaimCodeStore.Issue(instanceId, token, challenge)` (single-use, 5-min, in-memory) and redirects back with `?code=…&state=…`. The instance callback `/CloudClaim` (`CloudClaimModel`, admin-only) validates state against the cookie (`FixedTimeEquals`), POSTs `{code, codeVerifier}` to cloud `POST /api/instances/claim/exchange` (anonymous - protected by PKCE), and stores the returned id + token via `SetCloudConnectionSettings`. The account **password never touches the instance**; the token never touches the browser (only the useless-without-verifier code does). `ClaimCodeStore.Consume` removes the code on **any** attempt (one verifier guess per code) - a slightly-stronger-than-spec PKCE. **Cancel + reconnect UX:** the cloud consent page's **Cancel** now redirects back to the instance callback with `?error=access_denied` (instance `CloudClaimModel` drops the pending claim + shows "Connection cancelled in the cloud"); and when the cloud has severed the link (status "unauthorized"), System → Cloud shows a **"Disconnect & reconnect"** button (`Config.OnPostCloudReconnect` = `DisconnectCloud` then re-enter the claim with the same URL/name AND `reconnect=<the instance id it just dropped>` → the consent page offers exactly that instance for takeover, preselected - the admin did ask to reconnect - and it still takes a click; it is never guessed from the name). A cloud **deactivation** ("deactivated") shows a contact-your-provider note instead (reconnecting can't lift it). The PKCE helper (`CloudClaimFlow.Challenge`) mirrors the cloud's `ClaimCodeStore.Challenge` exactly.

**Cloud SSO ("Sign in with Matmon Cloud").** OAuth2 authorization-code with the cloud as IdP. `/signin-cloud?handler=Start` → cloud `/oauth/authorize` (member-gated consent) → code → local callback exchanges it at cloud `POST /oauth/token` using the **instance token as the client secret** → maps the account's instance role (Owner/Admin→Admin, Viewer→Viewer) → `store.UpsertCloudUser` find-or-creates a local user (`MatmonUser.CloudLinked`, password-less/SSO-only; an existing local account with that e-mail wins) → signs in. CSRF via a state cookie; codes are single-use (cloud `AuthCodeStore`, 5-min). The Login page shows the button only when the cloud link is connected. **Offline password fallback:** SSO accounts are password-less, so the self-service `/account` page lets any signed-in user set/change their own local password (`store.HasLocalPassword`/`ChangeOwnPassword`; a password-less account may set a first one without the current) - giving SSO users an e-mail+password credential for when the cloud is unreachable. `MatmonPageWriteGuard` allows the `/Account` POST for any authenticated user.

**Full Access (operate the local UI through the cloud) - shown to users as "Remote access" since 2026-10-27, internal names unchanged; the setup wizard's cloud step can switch it on (licence-gated).** A WebSocket reverse tunnel so a browser reaches a Primary behind NAT. Enable it in System → Cloud (`CloudSettings.FullAccessEnabled`); the Primary-only `TunnelClient` keeps an outbound WS open to the cloud (`GET /api/instances/{id}/tunnel`, instance-token auth), receives browser requests, replays them against its own UI and returns the responses (multiplexed by id; absolute self-URLs in `Location` are made root-relative). Cloud side: `TunnelRegistry` (one WS/instance) + the browser route `/instances/{id}/app/{**path}` (cloud login + membership gated) forwards via `TunnelProxy`, which rewrites root-relative URLs/redirects/cookie paths into the `/instances/{id}/app` prefix. **Seamless auto-login (no second sign-in inside the console).** A user who opens the console is already authenticated on the cloud and a member, so the cloud injects an identity assertion into the tunneled request - `X-Matmon-Cloud-User: "{email}|{InstanceRole}"` (set in `TunnelProxy.ForwardAsync` from `http.User`/`GetRoleAsync`, on both the `/app` and `/embed` routes) - and the instance auto-signs-them-in. Trust anchor: the instance's `TunnelClient` stamps every request it replays with a **per-process random secret** (`X-Matmon-Tunnel-Auth`, `TunnelAuthSecret` singleton), and the `TunnelAutoLogin` middleware (registered between `UseAuthentication`/`UseAuthorization` in Host `Program.cs`) honours the assertion **only** when that secret matches (`FixedTimeEquals`) → `UpsertCloudUser(email, MapRole(role))` + sets `context.User` from the assertion **on every tunneled request** (a backup cookie is re-issued via `SignInAsync` only when the identity actually changes). **`UpsertCloudUser` propagates the cloud-asserted role for SSO-only accounts** (cloud-linked, no local password) - so a cloud demotion (Owner→Viewer) takes effect on the instance - but leaves a **local-password** account's role untouched (the instance admin owns it). (Caveat: the store's "guarantee at least one enabled Admin" safety net re-promotes the *sole* user if a demotion would leave zero admins, so demoting the last admin never sticks - by design.) Authenticating per-request from the assertion - rather than relying on the auth cookie surviving the cross-origin console iframe round-trip - is what makes sign-in seamless (the cookie-dependent version "stuck" only after navigating back and forth). The instance is directly reachable, so the secret is essential: a forged `X-Matmon-Cloud-User` sent straight to the instance carries no valid secret and is ignored (verified: such a request still 302s to `/Login`). The cloud strips inbound `X-Matmon-Cloud-User`/`X-Matmon-Tunnel-Auth` (browser can't supply them) and the `TunnelClient` skips any inbound `X-Matmon-Tunnel-Auth` before adding its own. `MapRole` mirrors `SigninCloudModel` (Owner/Admin→Admin, else Viewer). The manual **"Sign in with Matmon Cloud"** OAuth button (`/signin-cloud`) still works for **direct** access; it is superseded by auto-login through the tunnel (and its `redirect_uri` is built from the local host, so it does not work *through* the tunnel - auto-login is the tunnel path). Cloud Instances list has an **Open** link. **Console access = members OR a partner-with-consent** (`InstanceService.ResolveConsoleAccessAsync`, used by the `Console.cshtml` page + the `/app` + `/embed` proxy routes): a member gets their own role, and - fulfilling the consent promise "your partner may open and operate your instances" - the **owner of the partner org managing the customer** gets `Admin` (operate) **only while the customer consents** (`Organization.PartnerCanManage`). This is deliberately SEPARATE from `GetRoleAsync` (which still gates owner-level member/delete actions), so consent grants console operation, not member/delete power. The partner portal (`Reseller/CustomerDetail`) shows a consent banner + an **Open** action per instance when consent is granted, and a **Request consent** button (`OrganizationService.RequestPartnerConsentAsync` e-mails the customer's owner) when not; the customer grants/revokes it on their own Company page (`SetPartnerConsentAsync`), and `InviteAccept` tells the invited customer up front that the partner can only open/operate once they allow it. The cloud **console** (`Console.cshtml`) wraps the instance UI in a chromeless iframe (`/instances/{id}/embed/{**path}`) inside the cloud shell (single menu). While the tunnel is up the header bar carries a **Cloud | Instance switch** (`ConsoleSwitch`, a MatUi `mat-seg` of two links, decided 2026-10-25): Cloud = the cloud's own summary of the instance (`?view=cloud` - status, alerts, sensors, plan, details from its heartbeat), Instance = its own UI through the tunnel; both links keep the page that is open (the server builds them from the console path, `cloud.js` keeps the Cloud link in step with the frame). It replaced a full-screen button that hid the cloud's menu and left no way to the cloud's view of an instance while the tunnel was connected. To keep the browser URL correct on **reload / deep-link**, the console is also routable as `/instances/{id}/c/<inner path>` (`AddPageRoute` → `ConsoleModel.EmbedPath`), and `cloud.js` `initConsoleFrame` mirrors the same-origin iframe's location into that outer URL via `history.replaceState` on each iframe `load` (iframe nav uses `replaceState` so it never pollutes parent history; browser Back within the instance traverses the iframe's own history, and only the console boundary fires a parent popstate → turbo re-render). Runtime URLs (JS `fetch`/XHR, e.g. the dashboard's live `/api/…` polling) are handled by a **client shim** `TunnelProxy` injects into each tunneled page's `<head>` (wraps `fetch`/`XMLHttpRequest.open` to prefix root-relative URLs) - so live AJAX works too. Remaining edge: client-initiated WebSockets aren't tunneled (Matmon's UI uses AJAX polling, so N/A today); a subdomain-per-instance deployment would remove the need for rewriting entirely. **Tunnel hardening:** the tunneled UI shares the cloud origin, so the browser sends the cloud's own cookies along with the instance's - `TunnelProxy.ForwardAsync` **strips every cookie named `.Matmon.Cloud.*`** before forwarding (the cloud names ALL its cookies with that prefix for exactly this: `.Matmon.Cloud.Auth` (session), `.Matmon.Cloud.Antiforgery`, `.Matmon.Cloud.TempData`, `.Matmon.Cloud.Pending2fa`), so a modified instance can never capture an operator's cloud session; the instance's own default `.AspNetCore.*` cookies (path-scoped to the prefix) pass through. The proxy also **normalises the forwarded path** (leading slashes collapsed, any `://` rejected with 400) and the instance's `TunnelClient.ReplayAsync` **refuses any path that doesn't resolve to its own host:port** - a `/instances/{id}/embed//evil.com/x` request used to forward as `//evil.com/x`, which the instance resolved to `http://evil.com/x` and replayed *with the operator's cookies, the identity assertion and the tunnel secret* (SSRF + secret leak). Keep both guards. **Tunnel robustness + visibility:** the instance surfaces live tunnel state (`TunnelState` singleton - connected / connected-since / last-error / consecutive-failures / requests-served) on **System → Cloud** ("Full Access" row: "Connected since …" / "Not connected — <last error> (retrying…)" / "Off"), so an admin can tell a healthy idle tunnel from a silently-failing one (a reverse proxy that drops WS upgrades, or a 401/403 handshake). `TunnelClient` logs connect failures at **Information** (first) → **Warning** (≥3 in a row, with the classified reason) instead of Debug, and reconnects with **exponential backoff + jitter** (5→10→20→40→60s, reset on success). Both ends set a **20s WebSocket keep-alive** (`ClientWebSocket.Options.KeepAliveInterval/Timeout` + cloud `UseWebSockets`) so a silently half-open tunnel is detected in ~20-40s instead of waiting out TCP retransmits. A replayed response is **capped at 20 MB** (`ReplayAsync` → 413 "download it directly on the instance") so one big download can't blow past the cloud's 32 MB/message limit and drop every console user; the Config tab also warns "link degraded" when the last successful heartbeat is older than ~3x the cadence (`HeartbeatStale`). **Plan awareness + refusals (`TunnelConnectPolicy`, pure + tested):** the client used to ask only "switched on and linked?" and never "does the plan include it?", so an instance on a plan without Full Access was turned away every minute for as long as it ran (3705 attempts in a row on a local instance), each one a warning with a stack trace. `TunnelClient` now asks `ILicenseService.Current.TunnelEnabled` first - the licence arrives with every heartbeat, so it is known locally; the client is a singleton and `ILicenseService` is scoped, hence one `IServiceScopeFactory` scope per look - and `TunnelConnectPolicy.Decide` answers Idle / NotIncluded / Connect. **NotIncluded never opens a socket:** it logs once at Information, sets `TunnelState.NotIncluded` (System → Cloud then reads "Switched on, but not included in this plan - it connects as soon as the plan includes Full Access", in the muted colour rather than the warning one) and looks again every 20 s (`NotIncludedPoll`). A **401/403 from the cloud** (`IsDefinitiveRefusal` - an answer, unlike a network error) is logged once as a warning (later ones at Information), then waited out for 10 min (`RefusedRetry`) by `WaitForChangeAsync`, which polls a `Signature` of everything that could change the answer (the Full Access and link switches, url, instance id, the plan and a 12-character hash of the token - never the token itself) every 15 s and returns the moment it changes, so a plan upgrade or a reconnect connects within ~15 s instead of after the wait. Any other failure keeps the 5→60 s exponential backoff.

**Licensing (cloud is the license authority; template-based).** The cloud signs a per-instance license token (ECDSA P-256 over a compact payload) that Matmon verifies **offline** against a public key baked into `Matmon.Core` (`LicensePublicKey.Spki`); `Matmon.Core/Domain/Licensing.cs` holds `LicenseTier` (Free/Business/Enterprise/**Custom**), `LicenseInfo`, and `LicenseCrypto` (sign/verify, unit-tested). **The plan is a cloud-managed template** (`LicenseTemplate`): assigning it to an instance **snapshots** its values + price onto the instance (frozen), while the template NAME is read live (rename cascades). The token payload is now `t/p/e/iss/id` **+ `n` (plan name), `sl` (sensor limit), `csl` (cloud-sensor limit), `te` (tunnel/Full-Access), `cse` (cloud-sensors)** - the new fields are **nullable** so legacy tokens verify and map to permissive defaults; **the cloud `LicenseSigner.Payload` and `Matmon.Core.LicenseCrypto.Payload` must stay key-identical.** Local side: `CloudConnectionService` fetches the token each heartbeat + caches it (`store.Get/SetLicenseToken`); `ILicenseService` validates offline (Free fallback) and enforces **probe limit** (`CanAddProbe`) + **sensor limit** (`CanAddSensor`) + **Full-Access gate** (`OnPostCloudFullAccess` refuses if `!TunnelEnabled`); System → Cloud shows plan name + probe/sensor/cloud-sensor/Full-Access. **Every user path that adds a probe/sensor enforces the limit** - the manual create handlers (`Workspace.CreateHandlers`), the **setup wizard** probe step (`Wizard.OnPostCreateProbe`) and **discovery apply** (`Discovery.EnsureSelectedSensors`, which stops mid-run at the limit and reports "some selected sensors were not created"); the wizard/discovery paths used to call the store directly and bypass the gate. (The internal demo/provision seeders are intentionally unmetered.) Cloud side: the **reset-to-Free** path (`OrganizationLicenseService.ApplyFreeAsync`) and the **new-instance default** (`InstanceService.ApplyDefaultTemplateAsync`) filter `Category == Free` before picking a template - archiving the Free plan no longer silently grants the cheapest PAID plan (with no pool license); with no Free plan they drop to built-in Free semantics (tier 0, 1 probe, unlimited sensors, no tunnel), never a paid plan. **The plans (decided 2026-10-22):** tier 0 is shown as **Personal** - free, personal use only, unlimited sensors, 1 probe; **Business** - unlimited sensors, 1 probe (commercial use, Full Access, cloud sensors); **Enterprise** - unlimited everything. Agents never count as probes (2026-10-23, `LicenseInfo.CountLicensedProbes`), on every plan. The wire tier stays `Free = 0`/`LicenseCategory.Free`; only the name a user reads changed (`LicenseInfo.PersonalPlanName`/`TierName`, cloud `LicenseTier.Name`). The offline fallback (`LicenseInfo.Fallback`) and the cloud's seeds/fallbacks follow it; the templates already in a cloud database are admin data and keep their values until an admin edits them. The "personal use only" clause itself belongs in the LICENSE/terms - not written yet. **The licence leaves with the link (2026-10-25):** `DisconnectCloud` drops the cached licence token and so does linking another instance id (`SetCloudConnectionSettings`), and `LicenseService` ignores a token signed for an instance other than the one this installation is linked to; an unlinked box accepts the offline token it was given. Before, a disconnected or relinked installation kept the old instance's paid plan for the rest of the lease. A manually pasted token is refused when expired (it used to be "applied" while the plan stayed Personal). **Offline / air-gapped licensing:** a platform admin can issue a long-lived (365-day) token for an instance that never checks in - `Admin/InstanceDetail` "Issue offline token" → `LicenseSigner.SignOffline(instance, days)` (same payload/format as the lease `Sign`, only a longer expiry, still capped by the plan's own end date; requires `License:PrivateKey`). The operator pastes it on the instance under **System → Cloud → Advanced → Offline license** (`Config.OnPostCloudOfflineToken`), which verifies it offline against the baked public key (`LicenseCrypto.Verify`) and stores it (`SetLicenseToken(token, persistImmediately: true)` - bypasses the 6h heartbeat-save gate). A *connected* instance's token stays cloud-managed (the next heartbeat overwrites a pasted one), so this is for genuinely offline installs. **Renew + pre-expiry warning (cloud):** a runtime-limited pool license (`OrganizationLicense.ExpiresUtc` from the plan's `RuntimeDays`) can be **renewed** (`OrganizationLicenseService.RenewAsync` extends by another term from the remaining end, clears any scheduled cancellation + the notice flag, propagates the new end to the mounted instance) - "Renew" buttons on Admin/OrganizationDetail + Reseller/CustomerDetail. The hourly `LicenseExpirySweepService` now also **warns before expiry**: `NotifyUpcomingExpiryAsync` e-mails the org owner + managing-partner owner once per term (`OrganizationLicense.ExpiryNoticeSentUtc`, migration `AddLicenseExpiryNotice`; `CloudSpoolKind.License`) when the end is within 7 days, then `ProcessExpiredAsync` cancels the ones already past. `LicenseInfo.DisplayName` = plan name (or tier for legacy). NB the cloud's `License__PrivateKey` and Matmon's baked public key are a keypair - regenerate both together. **The production private key is NOT in the repo:** `LicensePublicKey.Spki` holds the prod *public* key (compiled in); the matching *private* key exists only as the cloud's `License__PrivateKey` env (`LicenseSigner` has no committed default - it signs only when the env is set, and the `/api/instances/{id}/license` endpoint issues no token when unset → instance stays on the cached license / Free). Local dev + prod must both set `License__PrivateKey`. `LicenseCryptoTests` use ephemeral keypairs (no committed key matches the baked one) plus a baked-key well-formedness guard. To rotate: `dotnet run keygen.cs`, put the SPKI-base64 public in `Licensing.cs`, the PKCS#8-base64 private in the cloud env.

## Docker

`Dockerfile` at `src/Matmon.Host/Dockerfile` (SDK build → aspnet runtime; installs PowerShell + ssh + NTLM for sensors; binds `:8099`; takes a `MATMON_VERSION` build-arg → env). ⚠️ Its restore layer COPYs each project file individually before `dotnet restore` (for layer caching) - so **every project the Host references must be listed there** (`Matmon.Core`, `Matmon.Probe`). A missing one fails the restore, and with it every image build, CI run and deploy. The image also runs an `agent` stage that publishes the three agent platforms (see **Agent**). Compose files: `docker-compose.yml` (local primary + sample probe), `docker-compose.master*.yml` (portable primary, GHCR pull / host-network / local build). CI: `.github/workflows/docker-image.yml` builds on PR, publishes to GHCR on push to `main`/`dev`. **Syslog ports are not published by default** (no collector runs until one is added, and a container only receives what is published): `docker-compose.yml` carries commented `514:514/udp` + `514:514/tcp` lines and the README explains them. On Docker Desktop (Windows/macOS) published UDP arrives from the gateway address, not the device - see **Syslog**.

**Install snippets** (the cloud's `_InstallMatmon` panel - shown on `/instances` (expanded while the account has no instance) and `/instances/new` - and the Matmon.Web homepage's self-host section): `docker run` and a simple Docker Compose, written to be EQUIVALENT: same image (`ghcr.io/real-ttx/matmon:latest`), port 8099, `restart: unless-stopped`, and the same `matmon-data` volume. ⚠️ The compose names the volume explicitly (`name: matmon-data`): Compose would otherwise prefix it with the project name (`<folder>_matmon-data`), so someone moving from `docker run` to Compose would silently start on an EMPTY volume and think their data was gone. The panel also says what the volume is: **it holds everything, including the cloud link** (`workspace.json` has the instance id + token) - removing only the container keeps the instance's identity, and a genuinely fresh start needs the volume removed too (`docker compose down -v` / `docker volume rm matmon-data`). The snippets are written flush-left inside `<pre>` (markup indentation would end up in the copied text) and the cloud's copy buttons (MatUi `data-copy="#id"`) copy the element's trimmed `textContent` - checked by pulling the served text and letting `docker compose config` parse it. The command carries no instance id or token on purpose (see "An environment link IS an identity"); a pre-linked compose would be a different, deliberate feature.

## Branches & versioning

- **`main`** = release branch (tagged `latest`); **`dev`** = ongoing work (tagged `nightly`). Day-to-day work happens on `dev`; merge to `main` for releases.
- The build version is shown in the UI (sidebar footer "Matmon &lt;version&gt;", links to `/About`). It is resolved by `Matmon.Probe/MatmonVersion` in this order: the `MATMON_VERSION` env var (which CI bakes into the image: **release** `0.1.<run>-<builddate>` from the root `VERSION` file, **dev** `nightly-<run>-<builddate>`); then a version baked INTO the entry assembly with `-p:MatmonVersion=…` (root `Directory.Build.props` emits an `AssemblyMetadata("MatmonVersion")` attribute only when the property is set); then `local-<builddate>`. `builddate` = UTC `yyyyMMdd-HHmm`. The baked tier exists for the agent: it runs on a customer's machine where nobody sets the env var, and the auto-update compares its version with the instance's manifest - an explicit attribute rather than `InformationalVersion`, which the SDK defaults to "1.0.0". ⚠️ The `local-` fallback reads the ENTRY assembly's file time, falling back to `Environment.ProcessPath` - because `Assembly.Location` is always EMPTY in a single-file app (IL3000), which would otherwise have made the agent report its process start time, i.e. a different version on every start. Not the other way round: for `dotnet Matmon.Host.dll` the process path is dotnet.exe.

## Agent

The agent is **the Docker probe's code in a generic host** - not a second implementation - so it speaks exactly the protocol a primary expects. Verified end-to-end: the win-x64 single-file build ran under probe-01's identity against a live primary and exercised assignments, run jobs, discovery jobs, heartbeat and the observation post (36/36 responses 200); the primary recorded its results.

**Measured size** (self-contained, both platforms alike): folder publish **93 MB**; single-file + compression **43 MB** (one ~41 MB executable + native SQLite, + SqlClient SNI on Windows). Our own code is 0.83 MB of that - the rest is the .NET runtime, and the SQL drivers with their Azure/Identity dependencies are **10.8 MB**. Trimmed it is **19 MB, but NOT safe as-is**: 29 trim warnings, 9 of them on the probe's JSON exchange with the primary (every `PostAsJsonAsync`/`ReadFromJsonAsync` in `SlaveHeartbeatService`/`SlaveSensorWorker`) - trimmed, DTO members could silently vanish from the wire. Making it safe = System.Text.Json source generation for the probe DTOs; the third-party SQL drivers warn too.

**Enrolment + the Agents page.** An admin creates a **single-use, short-lived code** on `/agents` (`Pages/Agents.cshtml`, nav item next to Probes; POST is admin-only via the write guard, the list is visible to every role) and runs `matmon-agent enroll --url <instance> --code <code>` on the machine; the page renders ready-to-paste Windows (`New-Service`) and Linux (systemd unit, `Type=notify`) recipes around it. The agent trades the code at the anonymous **`POST /api/agents/enroll`** (Primary-only, rate-limited 10/min per client IP - policy `agent-enroll`, the instance's first `AddRateLimiter`) for a probe id + token (`AgentEnrollRequest`/`AgentEnrollResponse` in `Matmon.Probe`). Why a code instead of handing out the probe token: the token is the agent's credential for its whole life and an install command ends up in shell histories and tickets - the code works once, for ≤ 7 days (1h / 24h / 7d offered, `MaxAgentEnrollmentValidity`), and is **stored only as a SHA-256 hash** (`AgentEnrollment` + `AgentEnrollmentCode` in Core: 20 symbols from an alphabet without 0/O/1/I/L/U, normalised case/dash-insensitive; shown exactly once via TempData). The probe is created **at redemption**, not when the code is issued (`RedeemAgentEnrollment`, store partial `.Agents.cs`), so an install that never happened leaves no dead probe; its name is the admin's or else the machine's host name, and `ProbeElement.AgentEnrolledUtc` marks it as an agent - the Agents page is a VIEW over those probes (`SystemProbeOverview.IsAgent`, also an "Agent" chip on the Probes page), not a second model. Wrong, used, revoked and expired codes all answer the same `400 invalid_code`. **Agents are not probes in the licence model** (decided 2026-10-23): `LicenseInfo.CountLicensedProbes` counts the instance's own probe and every remote probe but no probe with `AgentEnrolledUtc`, so enrolment checks no licence at all and a plan with one probe (Personal, Business) takes any number of agents; System → Cloud shows them beside the probe count as "not counted". (Before, the root counted and those plans allowed no agent at all; an agent still maps an older instance's `403 probe_limit` to a message.) Worth knowing: an agent is a full probe - it can scan and monitor other devices in its network too. **Re-enrolment:** a code can also be bound to an EXISTING remote probe (`AgentEnrollment.ProbeElementId`; "New install code" on an agent's row, "Move to an agent" on a remote probe's row on the Probes page → `Agents.OnPostCreateForProbe`). Redeeming it creates nothing: the probe gets a NEW token and `AgentEnrolledUtc`, keeping its sensors, history and alerts - a reinstalled machine gets its probe back, a Docker probe moves onto an agent - and whatever still runs under the old token is locked out on its next request, so two processes never report as one probe. Moving a Docker probe onto an agent this way frees its licence slot (`RedeemAgentEnrollment(code, host, os)` → `AgentEnrollmentResult`: `Invalid` / `Enrolled`). A code whose probe was deleted meanwhile is dead; the local root cannot be targeted. Pending codes are in `WorkspaceDocument.AgentEnrollments` and are **always stripped from backups** (instance-bound + short-lived). ⚠️ `[TempData]` round-trips a date-shaped STRING back as a `DateTime` and then fails to assign it to the string property (InvalidCastException on the next GET) - the expiry rides as `DateTime?`. **An agent is bound to a host - the machine it sits on.** The probe is the agent's connection to the instance; the machine is a `HostElement` inside it, and `ProbeElement.BoundHostId` says which one (a probe can hold many hosts - the devices an agent scans - so the machine's has to be named). `FindBoundHost()` returns it only while it is still inside the probe's own subtree, so a host that was deleted or moved out is simply unbound rather than dangling. Redeeming a code (`BindAgentHostLocked`) binds one of three ways: the host the code named (`AgentEnrollment.HostElementId`, picked with the element picker on the Agents page - a host that already has an agent is not offered and `CreateAgentEnrollment` refuses it; the host is MOVED under the agent's probe, so its sensors run on the agent and settings it inherited from its old place - credentials, schedules - stop applying, which the page says up front), the host a re-enrolled probe already has, or a NEW host named after the machine (address = the reported machine name, else `localhost`). A named host that vanished, or that another agent took in the meantime, never fails the enrolment: the agent gets a host of its own. The baseline sensors (System Health, Windows Update / Package Updates) are created under the bound host, the update sensors with an explicit target `localhost` - with no target a sensor inherits its host's address, and a host chosen by its IP is not recognised by `LocalTarget` as this machine, so the sensor would go out over WinRM/SSH to itself. The probe keeps only what is its own (the heartbeat). The Agents page shows "Host: …" per agent (a warning when it has none) and marks unused codes that are bound to an existing host, and both trees say "Matmon agent" next to the host (`ProbeElement.AgentLabel`). ⚠️ The Monitoring page builds its OWN detail line in `Workspace.OptionsAndRows.cs`, a second copy of `DashboardSnapshotProvider.BuildDetails`, so anything the tree should say has to go into both - the agent note was first only in the dashboard one and the page showed nothing. **Migration 6** (`MigrateAgentProbesToBoundHosts`) gives every agent that predates this a host (named after the probe, address `localhost`) and moves its machine sensors into it; the admin's own sensors and the heartbeat stay on the probe. One limit worth knowing: a restore keeps the live schema version, so restoring a backup made before this does not re-run the migration and brings such agents back unbound (the Agents page says so) until they are re-enrolled.

**Bundled agent binaries (download from the instance).** The Docker image carries the agent that matches it: a separate `agent` build stage publishes `Matmon.Agent` for **win-x64, linux-x64, linux-arm64** into `/app/agent/<rid>/` with the same `MATMON_VERSION` baked in (`-p:MatmonVersion`). How it is packaged is declared ONCE in `Matmon.Agent.csproj` (a property group conditional on a runtime identifier: self-contained, single file, compressed, native libs embedded - one ~41-43 MB file per platform, ~130 MB added to the image); the Dockerfile and `scripts/publish-agent.ps1` (local dev: publishes into `src/Matmon.Host/agent/`, gitignored + dockerignored) only pass `-r`. `Services/AgentPackageStore` discovers the packages on disk (`Matmon__AgentPackagesPath`, default `agent` under the content root) against a FIXED platform list - a URL segment is never turned into a path unchecked - and caches each file's SHA-256 keyed by write time + length. `GET /api/agent/packages` (manifest: version + per-platform size/sha256/url - what the auto-update will read) and `GET /api/agent/packages/{rid}` (the file, `ETag` = sha256, `X-Matmon-Agent-Sha256`, range support) are **not anonymous**: allowed for a signed-in user, for a valid enrolment code in the `X-Matmon-Enrollment-Code` header (**checked, not consumed** - `IsAgentEnrollmentCodeValid` - a header rather than a query string so the code stays out of access logs), or for an enrolled agent (`X-Matmon-Probe-Id` + probe token); rate-limited with the enrol policy. The Agents page lists the packages with download buttons, and its install recipes DOWNLOAD the binary from the instance with the code before enrolling with it (PowerShell `Invoke-WebRequest -Headers` with the progress bar off - PS 5.1 is painfully slow with it; Linux picks x64/arm64 from `uname -m`). Without packages (a plain source run) the page and the recipes say so instead of pointing at a 404.

**Auto-update with rollback.** The agent follows its instance's build EXACTLY (up or down - versions are build labels, not something to order) via `AgentUpdateService` (agent-only hosted service): 2 min after start, then hourly (`Matmon__AgentUpdateCheckMinutes`, floor 5, + up to 5 min jitter) it reads the manifest with its probe credentials, and `AgentUpdatePolicy.Decide` (pure, tested) skips: same version, an unversioned `local-*` instance build (every rebuild would look like a release), no package for this platform (`RuntimeInformation.RuntimeIdentifier`), or a version that was rolled back less than 24 h ago. Otherwise it downloads next to its own executable (same volume → the swap is a rename; `matmon-agent.new.exe` on Windows because it is executed once), checks the SHA-256 against the manifest and that `<new> --version` prints the offered version - all while the working agent still runs - then copies ITSELF to `matmon-agent-updater[.exe]` and launches that as `apply-update`: the updater is the known-good build, so the thing doing a rollback is the thing that is known to work. **Detached on purpose:** a Windows child survives its service being stopped; under systemd it would not (stopping a unit kills its cgroup), so it runs as a transient unit via `systemd-run --collect`. The updater (`ApplyUpdateCommand`) writes `pending.json`, stops the service (the name is resolved, not assumed: Windows = the service whose registry `ImagePath` is this exe, Linux = the unit in `/proc/self/cgroup`), keeps `<exe>.bak`, swaps (retrying - "service stopped" and "exe released" are not the same instant on Windows), starts the service and waits **3 min** for the NEW build's `confirmed` file, which that build writes after its first successful heartbeat (a process that starts but cannot reach its primary is not a working agent). No confirmation, or any failure after the swap → stop, restore `.bak`, start, record `rolled-back`. The outcome goes to `last-update.json` + `update.log` in the state directory (`AgentConfigFile.ResolveStateDirectory`: `/var/lib/matmon-agent` on Linux, else the config folder) and rides every heartbeat as `ProbeHeartbeatRequest.UpdateStatus` → `ProbeStatusSnapshot` → `SystemProbeOverview.UpdateStatus`, shown on the Agents page along with an "Update pending → <version>" chip. Only under a service manager (`WindowsServiceHelpers.IsWindowsService` / `SystemdHelpers.IsSystemdService`) - an interactive agent has nothing to start the new build - and `Matmon__AgentAutoUpdate=false` switches it off. **Signed packages.** The hash alone only proves the file matches a manifest from the same instance over the same channel (a man in the middle on plain http could swap both), so the image build signs every package: `Matmon.Probe/AgentPackageSignature` (ECDSA P-256, the licence pattern) over `matmon-agent|<rid>|<version>|<sha256>` - a genuine package cannot be relabelled as another platform or version. The Dockerfile's agent stage takes the private key as a **BuildKit secret** (`--mount=type=secret,id=agent_signing_key`; CI: `secrets.MATMON_AGENT_SIGNING_KEY` via build-push-action `secrets:`), runs `scripts/sign-agent-packages.cs` (a file-based app with `#:project` on Matmon.Probe; it verifies each signature against the BAKED public key first, so a secret that does not belong to it fails the build) and writes `<package>.sig`. `AgentPackageStore` serves it in the manifest (`signature`) and as `X-Matmon-Agent-Signature`; the Agents page marks packages Signed/Unsigned. The agent checks it in `DownloadAsync` right after the hash and BEFORE the file is ever executed (`--version`): a present signature must be valid (`AgentUpdatePolicy.CheckSignature`), and an agent that came signed itself refuses an unsigned package - `-p:MatmonAgentRequireSignature=true` is set by the build exactly when it signs (`AgentPackageSignature.RequiredByThisBuild`), otherwise stripping the signature from the manifest would be the way around it. Without the secret (a local build, or CI before the secret exists) nothing is signed and nothing is required - exactly the old behaviour. The private key lives only in the CI secret and in an offline backup (generated with `scripts/new-agent-signing-key.cs`, which prints only the public key); rotating it strands agents built with the old key until they are reinstalled once. Not covered: a man in the middle replaying an OLDER genuine manifest - the agent follows its instance's version by design.

**Tray icon + setup (Windows).** The Windows package is the `net10.0-windows` build of the same project (`UseWindowsForms`; the Dockerfile and `publish-agent.ps1` pass `-f net10.0-windows` for `win-*`, `EnableWindowsTargeting` lets the Linux Docker build do it) - still ONE file, ~54 MB (WinForms adds ~13 MB). Tray code lives in `Tray/` behind `#if WINDOWS`. `matmon-agent.exe tray` (and a plain double-click on a machine that is not set up yet) starts `TrayApplication`: a SEPARATE per-user process, because the service runs in session 0 and cannot show UI; single instance via a `Local\` mutex, STA thread, `FreeConsole` so no console lingers. It only LOOKS at the service through a local named pipe (`AgentStatusPipeServer`, pipe `matmon-agent-status`, one request `status` → `AgentStatusSnapshot` JSON: version, probe, instance URL, connected, last heartbeat, sensors, last update, config path - **never the token**, so Authenticated Users may read it) and draws its icon at runtime (the flat M of matmon.eu + a state dot: connected / instance unreachable / service stopped / not set up). Menu: Status…, Open instance (→ its Agents page), Set up…, Open log folder, Exit. **Nothing that changes the agent goes through the pipe** (every local user could re-point it); "Set up…" runs `matmon-agent.exe setup --url --code [--force] --result <file>` ELEVATED (one UAC prompt, `runas`, result via a JSON file because an elevated shell-started process's console cannot be read): enrol first (a bad code leaves nothing half-installed), copy itself to `%ProgramFiles%\Matmon Agent\matmon-agent.exe`, create the `Matmon Agent` service with `sc.exe` (auto start, restart-on-failure) or restart the existing one, and register the tray under HKLM `Run` as `conhost.exe --headless "<exe>" tray` - the agent is a CONSOLE app (so `enroll`/`--version` work in a terminal and the updater can read stdout), and `conhost --headless` is what starts it at sign-in without flashing a console window. The Agents page's Windows recipe is now just download + `setup`. ⚠️ **A running tray locks the executable**, so every swap (updater and setup) goes through `ApplyUpdateCommand.Replace`: rename the running file aside to `<exe>.old-<time>` (Windows allows renaming a running exe, not overwriting it), then place the new one - putting the old one back if that fails - and `DeleteSetAside` tidies up on the next agent start. The tray notices the service's version change AND the installed file's write time changing, and restarts itself onto the new file (both conditions, or two trays of different builds would hand over forever).

**Agent config file.** `enroll` writes the identity to `%ProgramData%Matmon Agentagent.json` / `/etc/matmon-agent/agent.json` (override `--config` or `MATMON_AGENT_CONFIG`) in the same `Matmon` section shape as the Docker probe's settings; the service reads it with environment variables and switches re-added after it, so `Matmon__*` still wins. On Windows the config/state FOLDER gets an ACL of its own too (`SecureDirectoryWindows`: SYSTEM, Administrators and the enrolling user may change it, Users may only read, owned by Administrators): under ProgramData it inherited "Users may create files", so a standard user could plant the update hand-shake files the SYSTEM service reads, or create the folder first and own it. A package the agent refuses (unsigned for a signed agent - known from the manifest, so not even downloaded - a bad hash or signature, a wrong `--version`) is recorded as a failed update, so the 24 h pause applies instead of a 43-54 MB download every hour; the status pipe backs off when it cannot be created instead of spinning a core; the tray's Set up passes `--force` whenever an identity is on disk. The file is **created with its ACL** (`AgentConfigFile`: Windows = no inheritance, SYSTEM + Administrators + the calling user; Unix = `UnixCreateMode` 0600, dir 0700) rather than written and then restricted - restricting afterwards both leaves a readable window and locks out a non-elevated caller, whose Administrators membership is deny-only (that bug left an unreadable `.tmp` behind). `enroll` refuses to replace an existing identity without `--force` and plain http to a public host without `--allow-http` (`CloudUrlPolicy`, same rule as the cloud link); the service **refuses to start** without URL + id + token instead of 401-looping in a log nobody reads.

## Self-update (System > Updates)

The instance updates ITSELF two ways, decided by what it runs in and never configured (`SelfUpdateMode`): a container with the Docker socket mounted replaces its own container, a Windows service swaps its own program folder; anything else says so on the page (with the compose line / the install command) and is updated by hand. Everything lives in `Services/SelfUpdate/`: `ISelfUpdateTarget` (IsAvailable / CheckAsync / ApplyAsync / ReadLastOutcomeAsync), `DockerSelfUpdateTarget`, `WindowsSelfUpdateTarget`, the pure `SelfUpdatePolicy` (install window in the workspace display zone - may run past midnight, the same hour twice = all day; a build that was rolled back or failed is not tried again for 24 h, matched by image id / version) and `SelfUpdateService` (Primary only; a hosted singleton: first look after 2 min, then hourly - reads how the last update ended, checks, and with `SelfUpdateSettings.AutoUpdate` installs inside the window; "Check now" / "Install now" on the page). Before every install the configuration (all sections but telemetry) is saved as a local backup snapshot `pre-update-<version>` - schema migrations only move forward, so a rollback across one has something to go back to. Settings (`WorkspaceDocument.SelfUpdate`: auto, window 03-05) and the last outcome (`SelfUpdateOutcome`) are instance-bound and stripped from every backup package. The page is `/system/updates` (`SystemUpdatesModel`, admin-only, a tab of `_SystemTabs`). `/healthz` carries `version` - it is what both updaters wait for.

**Docker** (`DockerEngineClient` - the Engine API over the unix socket, JSON kept as `JsonNode` so a container is recreated from its own inspect output with every field this code does not know about intact): the own container is found through `/proc/self/mountinfo` (`.../containers/<id>/hostname`, whatever the host name was set to), else the short-id host name. Check = the registry's digest for the tag the container runs (`GET /distribution/<ref>/json`) against the running image's RepoDigests; when it differs the image is PULLED at check time (so the window only costs the restart, and the offer can name the version from the image's `MATMON_VERSION`) and the image ids decide in the end (an image loses its RepoDigests when its tag is removed by hand - the registry is asked whenever there is one; only a name no registry knows is "built locally"). A tag pinned by digest has nothing to follow. ⚠️ Before the pull the RUNNING image gets a tag of its own (`<repo>:matmon-rollback`, `DockerSelfUpdateTarget.RollbackTag`): with the containerd image store (Docker Desktop, newer engines) an image whose last tag moved to the new image can no longer be addressed - the container keeps running, but the helper could not be created from it ("404 No such image"; found in the live test). Apply takes the running image by id, else that tag, else - rather than nothing - the new image. Apply = start a helper container from the image the instance RUNS (the known-good build does the rollback, the agent's rule) with the same socket bind (its host-side Source from the own container's Mounts - on Docker Desktop that is `/run/host-services/docker.proxy.sock`) on the own container's first network (or host networking): `Matmon.Host docker-update-helper` (`DockerUpdateHelper`) renames the old container aside (`<name>-old-<time>`), creates the new one under the old name from `DockerContainerRecreation.Build` (pure + tested: a container's Config is the image defaults MERGED with the operator's settings, so every value equal to the OLD image's default - its env such as `MATMON_VERSION`, Cmd/Entrypoint, labels, WorkingDir, ExposedPorts, Volumes... - is dropped and the new image supplies its own; the operator's env, HostConfig (binds, ports, restart policy), networks with their aliases (minus the id Docker adds) are kept; a host name equal to the old id is dropped; extra networks are connected after create; the version variable is ALWAYS dropped (`--version-variable`) and, when the old image cannot be inspected any more, the new image's defaults are the comparison - carried over, the new build reported the old version and was rolled back as "not up"), stops the old one, starts the new one and waits up to 3 min for `/healthz` with the new version on the new container's address. Done = the old container is removed and the new one carries `eu.matmon.update.from/at` labels. Not up (stopped, KEEPS RESTARTING - with a restart policy a crashing container counts as running between restarts - or no answer) = the new one is removed and the old one renamed back and started; its last distinct output lines go into the outcome. ⚠️ The port is read ASPNETCORE_URLS FIRST: the .NET base image sets `ASPNETCORE_HTTP_PORTS=8080` and Matmon's image overrides it with URLS - read the other way round, the helper waited on 8080 and rolled every update back (found in the live test). The outcome is the helper's last output line (`MATMON-UPDATE-OUTCOME {json}`); the instance reads it from the exited helper (`eu.matmon.update.helper-for=<name>`), stores it and removes the helper. Mounting the socket is the operator's decision (root on the host) - the page and README say so. Verified 2026-10-26 against a local registry: selftest-1 -> 2 replaced in ~5 s with env, volume, socket, port and restart policy intact; a broken build (exits at once) rolled back with its output in the outcome. **Matmon.Cloud runs the same files** (`Services/SelfUpdate`, namespace changed - the version and its image variable are constructor parameters for that reason): change both.

**Windows setup + tray icon (`src/Matmon.Setup`, decided 2026-10-26).** What a user downloads is ONE file, `MatmonSetup-x64.exe`: a WinForms program (self-contained single file, ~51 MB, deliberately NOT referencing Host/Probe/Core) with the program zip appended (`Matmon.Probe/SetupPayload`: 24-byte trailer "MMSETUP1" + offset + length; a single-file bundle ignores bytes after it; `SetupPayloadTests`). The installation itself is `Services/SelfUpdate/WindowsInstallation.cs` (Windows-only static class, no ASP.NET/Probe dependencies, LINKED into the setup), so the setup and `Matmon.Host.exe install-service` install exactly the same thing: the service `Matmon` (delayed auto start, restart on failure, registry `Environment` = `ASPNETCORE_URLS` + `Matmon__WorkspacePath`), the program folder, the data folder (SYSTEM + Administrators only, owned by Administrators - a user who pre-created it cannot change it back), one firewall rule named `Matmon` (replaced, never piled up), and the "Installed apps" entry (`HKLM\...\Uninstall\Matmon`, with `MatmonDataFolder` / `MatmonPort` values `Find()` reads back; `RefreshRegisteredVersion` is called by the running service after a self-update). The BARE setup (the bytes before the package) is installed as `%ProgramData%\Matmon\app\Matmon.exe` (until 2026-10-27 `setup\Matmon Setup.exe`, which read as if an installer ran at every sign-in; `RefreshSetupProgram` moves an older installation: new file, Run value, Start menu entry and uninstall command point at `app\`, the old file is replaced by the new build so a tray running from there restarts onto it and hands over at once - `Program.Main` forwards a legacy-path `/tray` - and the old folder goes once nothing runs from it) - outside the program folder, so a self-update never removes it - and is three things (started WITHOUT arguments it is the tray, not the installer: a double-click opens the tray or, when one runs, Matmon in the browser): the uninstaller (`/uninstall`; it copies itself to %TEMP% first, because a running exe cannot delete its own folder, and that copy removes itself afterwards), the **tray icon** (`/tray`, `TrayApp`: started at every sign-in through HKLM `Run`, value `Matmon`; the setup folder grants Users read + execute for it) and the elevated helper for the tray (`/service=start|stop|restart`). ⚠️ Hence the manifest is **asInvoker**, not requireAdministrator: the tray must run as the signed-in user, so `Program.Main` relaunches itself elevated (`runas`, one UAC prompt) for everything but `/tray`, and the NON-elevated parent starts the tray after a successful install (an elevated process would start it elevated). The tray only reads: service status (any user may) + `/healthz` (version), icon = the flat M with a state dot (`Matmon.Agent/Tray/TrayIcons.cs`, linked into both - it also holds `DrawMark`, the one vector copy of the mark the setup header draws too: green running, amber starting / not answering, red stopped, grey not installed); menu Open Matmon (also double-click) / Logs / Updates / Start / Stop / Restart (shield icon, through the elevated copy) / Close; a balloon when Matmon goes down or comes back ON ITS OWN (none for what the user just asked for). No "open data folder" on purpose: Explorer's "Continue" on an admin-only folder would ADD the user to its ACL. A Start menu entry **"Matmon"** (all users, `WindowsInstallation.StartMenuShortcutPath`, created via WScript.Shell together with the tray's Run value and removed with it) starts the tray again after it was closed; when one runs already, the second start opens Matmon in the browser instead (the mutex check in `TrayApp.Run`). An installation from before the entry existed gets it from the running service after an update (`RefreshSetupProgram`). Install and uninstall end every running tray first (`StopTrayIcons`, any session) - it holds the setup program open. ⚠️ **A self-update must bring the setup program along**: it swaps only the program folder, and the tray + uninstaller live outside it, so they stayed on the first installed build for good (found when the new tray mark never showed up). The package therefore carries `setup/MatmonSetup.exe` (Dockerfile `windows-package` stage), the running service puts it in place of the installed copy once per start (`WindowsInstallation.RefreshSetupProgram`, from `WindowsSelfUpdateTarget.ReadLastOutcomeAsync`: running copy renamed aside to `.old-<time>`, deleted on a later start) and the tray notices its own file changed (same stamp on two ticks, so a half-written copy is never started), releases its mutex and restarts itself onto it. The header is matmon.eu's: the FLAT mark (`brand/matmon-mark-flat.svg`, its path + gradient drawn as a GDI+ vector by `TrayIcons.DrawMark`, so no raster copy to keep in step) beside "Matmon" on white; version and channel sit bottom left in the button bar, on the buttons' line. Wizard: welcome (install / update with versions) -> options (folders, port with a free-port check, firewall, tray) -> progress -> finish (link, open in browser), or confirm -> uninstall (keeps the data unless ticked). Silent: `/silent [/dir=] [/data=] [/port=] [/firewall] [/notray] [/package=<zip>]`, `/uninstall /silent [/removedata]`; exit code + `%TEMP%\matmon-setup.log`. Icons: `src/Matmon.Setup/matmon.ico` (10 sizes, also the Host exe's icon), generated from `brand/app-icon-512.png` by `scripts/make-windows-icon.cs`. CI publishes the setup in the `windows-package` stage and `package-windows.cs --setup` writes `MatmonSetup-x64.exe`, uploaded to the release before the zip and the manifest. **Online setup:** the same program with NOTHING appended (`MatmonSetup-x64-online.exe`, ~50 MB, written by `package-windows.cs --setup` beside the full one and uploaded with it) - `SetupRunner.SourceOf` = Embedded / File (`/package=`) / Online. Online it reads the feed of its OWN build's channel (a nightly setup installs the newest nightly; a release or local build the newest release; `/feed=<url>` overrides) and downloads + verifies through `Services/SelfUpdate/WindowsUpdateFeed.cs` - split out of `WindowsSelfUpdateTarget` and linked into the setup (with `AgentPackageSignature`), so the self-update and the setup trust a package for exactly the same reasons (SHA-256 of the manifest, the CI signature; a signed setup - the Dockerfile passes `MatmonAgentRequireSignature` to the setup publish too - refuses an unsigned package before downloading it). The progress bar shows the download share; the version that gets registered is the manifest's. `WindowsUpdateFeedTests` cover the download (stand-in feed); verified 2026-10-26 against the real `windows-latest` release (190 MB in 8 s, hash ok - that release is NOT signed yet, the CI secret is missing). ⚠️ The wizard's page panel is added to the body only once it holds its controls and has its final size: added empty first, it measured them at its default 200 px width and kept a scroll range for a page that fits (a stray scrollbar on the options page); and the three footer buttons have a fixed size and one margin rule - AutoSize plus a margin of Cancel's own put it a few pixels higher than the others. Pages are checked by rendering the form via reflection (`DrawToBitmap`), which needs no UAC. Verified 2026-10-26: builds (setup 239 MB with the package), the wizard renders and finds the payload, the tray runs non-elevated and single-instance. NOT verified: a real elevated install / update / uninstall and the tray's service control (UAC).

**Windows** (`WindowsSelfUpdateTarget`, `WindowsUpdateApplier`, `WindowsServiceInstaller`): `Matmon.Host.exe install-service [--port 8099] [--data <dir>] [--open-firewall]` (elevated) copies the unpacked package to `%ProgramFiles%\Matmon`, creates the service `Matmon` (delayed auto start, restart on failure) whose own registry `Environment` carries `ASPNETCORE_URLS` and `Matmon__WorkspacePath` (`%ProgramData%\Matmon\data` - an update never touches it), and gives the data folder an ACL of its own (SYSTEM + Administrators only: it holds workspace.json AND the DataProtection keys, and ProgramData would let Users read them); `uninstall-service` removes the service and leaves program and data. As a service the content root is the program folder (`WebApplicationOptions.ContentRootPath`, `AddWindowsService`). The feed (`WindowsUpdateFeed`) is the rolling GitHub release of the channel - `windows-latest` (release builds) / `windows-nightly` - with `matmon-windows-x64.json` (version, file, size, sha256, signature) beside `matmon-windows-x64.zip`; `Matmon__UpdateFeedUrl` replaces it; a local build follows nothing. Apply = download, sha256, the CI signature over platform `instance-win-x64` (`AgentPackageSignature`, the agent's key and rules - a signed build refuses an unsigned package), unpack beside the program folder, run the new `Matmon.Host.exe --version`, copy the RUNNING program folder to `<install>.updater` and start `apply-update` from there (`ServiceControl.LaunchDetached`): stop the service, move the folder aside (`.bak-<time>`), move the new one in, start, wait 3 min for `/healthz` with the new version - else move it back and start the old one; outcome in `<data>/update/last-update.json` (+ `pending.json`, `update.log`), written BEFORE the restored build starts; leftovers (`.updater`, `.bak-*`, `.new-*`, `.failed-*`) are tidied once an outcome is read. The agent's service control moved to `Matmon.Probe/ServiceControl` for this (Windows SCM + systemd). **CI** builds the package in the Dockerfile's `windows-package` stage (Host published self-contained win-x64 + the agent packages beside it, `scripts/package-windows.cs` zips, writes the manifest and signs with the agent key when the secret is there) and exports it through `windows-feed` (`--target windows-feed --output type=local`); both stages sit BEFORE `final`, because the last stage is a plain `docker build`'s default target. The workflow uploads zip then manifest (`gh release upload --clobber`, the release is created on first use, nightly as prerelease) - hence `contents: write`. Verified 2026-10-26: the `windows-feed` stage builds locally (189 MB zip incl. the agent packages, manifest), the unpacked `Matmon.Host.exe --version` answers and the program runs natively on Windows (healthz, pages, static assets). ⚠️ A file-based app (the scripts) runs with reflection-based JSON switched off - the manifest is written with `Utf8JsonWriter`; and `.dockerignore` excludes `scripts/` except the scripts the image build runs. NOT verified yet: the Windows SERVICE path (install-service, an update, a rollback) - it needs an elevated install on a Windows machine - and the release upload, which only runs in CI.
