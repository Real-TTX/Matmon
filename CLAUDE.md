# CLAUDE.md

Guidance for working in this repository. Keep it in sync with the code — update it whenever architecture, persistence, interfaces, or major data flow change.

## What Matmon is

A lightweight, self-hosted network monitoring platform (a compact PRTG-style alternative) for home / small-business networks. ASP.NET Core on **.NET 10**, C#, Razor Pages UI, Docker-first. MIT licensed. Published image: `ghcr.io/real-ttx/matmon:latest`.

## Build / run / verify

- **Requirements:** .NET 10 SDK (developed against `10.0.203`), Docker Desktop or compatible runtime.
- **Build:** `dotnet build Matmon.slnx` (note: `.slnx`, not a classic `.sln`).
- **Run locally (dev):** `dotnet run --project src/Matmon.Host` → http://localhost:5084 (`ASPNETCORE_ENVIRONMENT=Development`). Default login `admin` / `admin`. For a live loop use `./scripts/dev.ps1` (`dotnet watch run`) — rebuilds/reloads on every change so the browser always shows current code.
- **Run via Docker:** `docker compose up --build` → primary on http://localhost:8099, sample secondary probe on http://localhost:8100.
- **Health check:** `GET /healthz` and `GET /api/mode` (both anonymous).
- **Tests:** `dotnet test tests/Matmon.Tests/Matmon.Tests.csproj` (xunit). Baseline covers the pure core logic (threshold parsing/evaluation, channel-threshold escalation, schedule calculator, settings inheritance). Coverage grows with each refactor.

## Solution layout

Two projects under `src/`:

- **`Matmon.Core`** — framework-free domain. `Domain/` holds the monitoring model, the `ISensorExecutor` implementations, inheritance/threshold/schedule logic, notifications. `Sample/` holds the default sample topology (`SampleTopologyFactory`).
- **`Matmon.Host`** — the web app.
  - `Program.cs` — startup, cookie auth, authorization policies, minimal APIs (probe heartbeat/assignments/observations/discovery), sensor-executor DI registration, mode-dependent hosted services.
  - `Services/` — persistence, polling, probe registry, dashboard/config providers, backup scheduler, slave (secondary) workers.
  - `Pages/` — Razor Pages UI (`.cshtml` + `.cshtml.cs`). Shared layout in `Pages/Shared/_Layout.cshtml`.
  - `wwwroot/` — `css/site.css` (large, ~9k lines), `js/site.js`, Bootstrap 5 + jQuery under `lib/`.

## Architecture: primary / secondary

Mode is set via `Matmon__Mode=Primary|Secondary` (default Primary).

- **Primary** owns the UI, configuration, alerts, history and global state. Registers `SensorPollingService` + `BackupSchedulerService`. Exposes the `/api/probes/*` endpoints that secondaries call.
- **Secondary** connects **outbound** to the primary (works behind firewalls/NAT), pulls assigned sensor work, executes it, and POSTs results back. Registers `SlaveHeartbeatService` + `SlaveSensorWorker`.
- Probe auth: a per-probe token sent as `X-Matmon-Probe-Token` header or `?token=` query (`ReadProbeToken` in `Program.cs`; validated via `IMonitoringWorkspaceStore.TryValidateProbe`).
- **Heartbeat full-sync:** the secondary heartbeat (`ProbeHeartbeatRequest`) also carries system details — OS, host name and reachable IPv4 subnets (CIDR), collected by `ProbeSystemInfoProvider`. The primary keeps them on the in-memory `ProbeStatusSnapshot` (`InMemoryProbeRegistry`). They surface on the probe **Usage** page ("System & networks" panel; the local primary reports itself) and the scoped probe's reported subnets are folded into **Discovery**'s subnet suggestions. The new heartbeat fields are optional (backward-compatible).

## Domain model

Tree of `MonitoringElement`s: `ProbeElement` → `FolderElement` → `HostElement` → `SensorElement` (see `Matmon.Core/Domain`). Settings and credentials are **inheritable** from parents; a sensor overrides only the fields that differ (`MonitoringInheritanceResolver`). Thresholds per channel: `SensorThresholdEvaluator`. Scheduling: `MonitoringSchedule` / `MonitoringScheduleCalculator`.

**Tags** (`MonitoringElement.Tags`, `MonitoringTemplate.Tags`) are free-form labels that **cascade**: a sensor's *effective* tags are its own plus every ancestor's (`MonitoringTagResolver.ResolveEffective`; `Normalize`/`Parse` clean + dedupe). Template tags merge into an element's own tags on apply (copy semantics). Tags show as chips on the Sensor Detail header (inherited ones styled subtly) and on monitoring tree/list nodes (own tags), and the monitoring search box matches tags so you can filter the tree by tag.

**Element picker** (`Pages/Shared/_ElementPicker.cshtml` + `Ui/ElementPicker.cs` + `initializeElementPickers` in site.js) is the reusable replacement for long element/sensor `<select>` dropdowns: a field that looks like a `workspace-input` but opens a modal that shows the topology as an **indented tree** while browsing and a flat **tag-filterable** path list while searching (`is-flat` toggled by the filter; `ElementPickerOption.Depth` drives indentation), single-select, writing the chosen id into a hidden input (fires `change`). Client-side filtering, so it stays instant regardless of element count. Rolled out to: notification rule Target, **map tile Target**, and every **parent/target select** (SensorCreate/SensorAssistant/ElementEditor — carrying `data-sensor-parent-select` so the preview re-post still fires — plus FolderCreate/HostCreate/ProbeCreate). `WorkspacePageViewModel.PickerElements` + `Model.PickerOptionsFor(validOptions)` build the per-context option set from the legacy `SelectListItem` ids. *(Discovery's scope-probe select is a separate `DiscoveryModel` page and still a plain select.)* For map tiles the picker's hidden value carries `data-map-property-element` + `data-selected-name` so the map designer's change-sync/preview keep working, and `addTile` re-runs `initializeElementPickers` for cloned tiles. Tag fields (ElementEditor/TemplateEditor/SensorCreate/SensorAssistant) are progressively enhanced into a **chip editor** (`data-tag-input` + `initializeTagInputs`); the original input stays as the hidden comma-joined value.

**Tag-as-target** (`MonitoringTargetResolver` in Core — pure token parse/format; `IMonitoringWorkspaceStore.ResolveTargetSensors(token)` — topology resolution): a target is a single string token that is either an element id (GUID) or a tag, written `tag:<name>`. A picker with `AllowTags=true` shows an **Element ⇆ Tag** toggle plus a selectable tag list; choosing a tag writes the `tag:<name>` token into the hidden value and the trigger shows `# <name>`. `ElementPickerModel.SelectedValue` (string, wins over `SelectedId`) round-trips the token; `is-tag-mode` (root class) + `setMode` in `initializeElementPickers` flip the two lists. A **tag** target resolves dynamically to every sensor whose *effective* tags include it (cross-tree aggregation, same as a folder subtree). Wired so far: **map tiles** — `MonitoringMapTile.TargetTag` (mutually exclusive with `ElementId`); `MapEditor`'s `MapTileInput.TargetToken` parses into `ElementId`/`TargetTag` via the resolver; `MapDisplayProvider.BuildTagAggregateTile` → the shared `BuildAggregateFromSensors` rolls the matching sensors up (worst state + healthy count) exactly like a container tile. *(Notification rule targets still store a plain `TargetElementId` — there is no rule dispatch yet, so tag matching there is deferred.)*

**Templates** (`MonitoringTemplate` + `TemplateEditor`) are **copy + origin**, not live inheritance. Applying a template (at sensor creation, or via the edit page / Templates "apply") bakes the template's resolved settings into the element's own `Settings` and records `MonitoringElement.TemplateOriginId`. Editing the template afterwards does **not** change existing elements; a "Restore from template" action re-copies the current template values (template wins). `ApplyTemplateCopy` (Workspace.cshtml.cs) is the single entry point; create lets the user's form values win, re-apply/restore lets the template win. The legacy live-inheritance list `AppliedTemplateIds` is no longer populated — `MigrateAppliedTemplatesToCopies` (store ctor) bakes any remaining links into `Settings` + sets the origin + clears the list on load. The TemplateEditor "Impact" tab lists sensors whose origin (directly or via the template's parent chain) is this template. Templates still chain via `ParentTemplateId` (resolved when copied).

**Sensors** are `ISensorExecutor` implementations registered in `RegisterSensorExecutors` (`Program.cs`): Ping, HTTP (+ HttpAdvanced), SNMP (+ interface/UPS), Synology NAS/Health, Proxmox PVE (legacy scope-based) + **Proxmox Health** (`proxmox-health`, cluster: quorum, nodes online, VM/container/storage rollups) and **Proxmox Node Health** (`proxmox-node-health`, per-node CPU/mem/disk + VM/container online/offline; `pve.node` selects a node, else the first visible one) — both thin wrappers that clone settings + set `pve.scope` and delegate to `ProxmoxPveSensorExecutor`; the shared `AppendResourceTypeChannels` always emits `vmOnline`/`vmOffline`/`containerOnline`/`containerOffline` (+ totals) and storage online/offline, **VMware Health** (`vmware-health`, vSphere **SOAP/vim25** API at `/sdk` — works on vCenter *and* standalone ESXi: hosts connected, VM power rollup, datastore usage) + **VMware Host Health** (`vmware-host-health`, per-ESXi-host CPU/mem from `summary.quickStats` + VM online/offline on that host; `vmware.host` selects a host, else the first) — both share the minimal `VSphereSession` SOAP client (RetrieveServiceContent → Login (cookie auth) → CreateContainerView → RetrieveProperties, namespace-agnostic XML parse) in `VMwareHealthSensorExecutor`; credentials are a **Generic** username/password bundle (`generic.username`/`generic.password`), UniFi Health (cloud api.ui.com / local controller, X-API-KEY — availability, not SMART), PowerShell Remote (generic script-over-WinRM, manual), Windows Health (`windows-health` — dedicated type delegating to the PowerShell engine with the CPU/mem/disk/SMART script; owns Windows-health auto-discovery), Windows Service/Process, Linux SSH Health, Local Script (runs a pwsh/bash/sh script **on the Matmon host/probe itself** — local counterpart to PowerShell Remote, reuses its `ParseOutput`/channel-parsing via `internal` helpers; `pwsh` ships in the image; exposes the monitoring context to the script as env vars — `MATMON_HOST`/`MATMON_TARGET` + the selected credential's fields as `MATMON_USERNAME`/`MATMON_PASSWORD`/`MATMON_TOKEN` and verbatim `MATMON_CRED_<FIELD>`, via `MonitoringSettings.TryResolveCredentialBundle` with empty kinds so any credential bundle is usable; the available variables are listed as a styled reference card in the sensor editors — `ScriptSensorVariables` (Core, per-type list) + the `_ScriptVariables` partial, rendered in the general Parameters section of SensorCreate/SensorAssistant/_SensorParameters), Local Program (`local-program` — runs a local **executable by path**; the path must be on an admin allow-list, the `Matmon__AllowedProgramPaths` env var (semicolon/newline list of exact files or directories), enforced by `LocalProgramSensorExecutor.IsAllowed` which `Path.GetFullPath`-normalizes so `..` traversal can't escape; empty list = nothing runs; surfaced read-only on the System/general page; the path is picked as a **dropdown** (`program.base`, options built from the allow-list at startup) plus an optional `program.relative` for a program under an allowed directory; reuses the script-sensor parsing + `MATMON_*` context env), SSL Certificate (+ chain), MSSQL Query, TCP Port, DNS, NTP, Docker Container, Backup Job, Disk SMART, Probe Heartbeat, Probe Health. The sensor-type dropdown is grouped into `<optgroup>`s by `SensorTypeCategories` (Core). A script-body parameter uses `SensorParameterKind.ScriptEditor` — rendered as a syntax-highlighting code editor (a transparent textarea over a highlighted `<pre>`, `initializeScriptEditors`/`highlightScript` in site.js; dependency-free). The per-kind render `switch` lives in **three** places (`_SensorParameters` partial + the inline lists in SensorCreate/SensorAssistant); note SensorCreate/SensorAssistant each have a **credentials** section list and a **general** section list — non-credential fields (scripts) render via the *general* one, so new cases must go there. A parameter can be **conditional**: set `VisibleWhenParameterKey` + `VisibleWhenValues` and it only shows when that other field has one of the values (e.g. the script sensors' `regexPattern` only shows when `outputFormat=regex`) — computed server-side (`IsSensorParameterVisible`) and toggled live by `initializeSensorParameterVisibility` in site.js. NB: `CloneSensorDefinition` (catalog rebuild) must copy every `SensorParameterDefinition` field — `Group`/`VisibleWhen*` were once dropped there, silently disabling grouping + conditions. Adding a sensor type = new `ISensorExecutor` + registration (`RegisterSensorExecutors`) + add its `Definition` to `EnsureSensorDefinitionCatalog` (rebuilt every load, so new types appear in existing workspaces too) + `SensorScheduleDefaults`/`SensorTelemetryProfiles` entries + parameter definitions (`SensorParameterDefinition`).

**Detailed per-platform Disk sensors** (separate from the compact Health sensors' single SMART-summary channel): `SynologyDiskSensorExecutor` (`synology-disk`, SNMP synoDisk table), `WindowsDiskSensorExecutor` (`windows-disk`, a thin wrapper that delegates to the generic `PowerShellRemoteSensorExecutor` engine with a fixed disk script + JSON output — a `state` string key drives the sensor state), `LinuxDiskSensorExecutor` (`linux-disk`, reuses `LinuxSshHealthSensorExecutor.StartSshProcess`/`ParseKeyValueChannels` — now `internal` + a `script` parameter — with a smartctl+df script), `ProxmoxDiskSensorExecutor` (`proxmox-disk`, reuses the now-`internal` Proxmox HTTP/auth helpers `CreateHttpClient`/`BuildApiBaseUri`/`BuildAuthorizationHeader`/`ReadApiDataAsync` over `/nodes/{node}/disks/list`). Each emits `ChannelMode.Dynamic` per-disk channels + an overall `smartStatus` (0/1/2) and `diskCount`; reusing the parent executor's machinery avoids duplicating the remoting/API plumbing.

**Update sensors** (pending OS/package updates, same delegation pattern as the disk sensors; default poll 6h, Availability profile): `WindowsUpdateSensorExecutor` (`windows-update`, delegates to the PowerShell engine running a `Microsoft.Update.Session` COM-API script → `pendingUpdates`/`securityUpdates`; live-verified), `LinuxUpdateSensorExecutor` (`linux-update`, reuses the SSH runner with a cross-distro apt/dnf/yum/zypper script → `pendingUpdates`/`securityUpdates`), `SynologyUpdateSensorExecutor` (`synology-update`, SSH `synoupgrade --check` → `updatesAvailable`; best-effort, needs DSM SSH + a privileged account). All default to **Warning** when updates are pending.

## Persistence (important — and the current bottleneck)

App state lives in a single JSON workspace file (`data/workspace.json`, configurable via `Matmon__WorkspacePath`), loaded and held entirely in memory by `Services/InMemoryMonitoringWorkspaceStore.cs` (~3700 lines; still large — decomposition is Phase B, in progress). The state is one private `WorkspaceDocument` with 13 collections, guarded by `_gate`. The class is now `partial`, split by concern into sibling files: `InMemoryMonitoringWorkspaceStore.Backup.cs` (backup/restore), `.Persistence.cs` (load/save: `LoadDocument`, the debounced `QueueSave`/`SaveDocumentLocked`, `.bak` refresh) and `.Telemetry.cs` (the telemetry facade: `RecordSensorObservation`, history/event/statistics getters, `RunTelemetryMaintenance` rollup+retention, `CleanupStorage`, `MigrateDocumentTelemetryIntoRepository`). The core `.cs` (~3100 lines) keeps topology/template/notification/user/map CRUD, alerts, credentials, defaults and the sensor-definition catalog. There is **no relational database for app state**; the `Microsoft.Data.SqlClient` dependency is only for the MSSQL *sensor*.

- Saves are debounced via a timer with two priorities: `Configuration` (~750ms) and `Telemetry` (~10s, max 30s dirty delay). `SaveDocumentLocked` serializes the **entire** document to a temp file then atomically moves it; a full-file `.bak` copy is refreshed every 5 min. Section-based backups live under `data/backups/`.
- Data-protection keys: `data/dataprotection-keys`. Runtime `data/` is gitignored.
- **Retention & statistics are per-sensor-type by default.** `Matmon.Core/Telemetry/SensorTelemetryProfiles` maps each sensor type to a profile (raw-observation days, statistics bucket minutes, statistics-retention days, event-retention days): *Responsive metrics* for latency/throughput sensors (raw 3d, hourly buckets, stats 14d), *Availability* for up/down sensors (raw 3d, daily buckets, stats 14d, events 90d), *Infrastructure* for probe sensors (raw 2d, stats 14d), and *General* as the fallback (raw 3d, hourly, stats 14d). (Defaults are deliberately lean — ~3 days raw + ~2 weeks of statistics — to keep `telemetry.db` small; bump per-sensor for a longer history.) An explicit `MonitoringSettings` override on the sensor/its ancestors always wins; the profile is only the fallback. The ElementEditor surfaces this as a visible **Telemetry & retention** section that shows the active profile and uses it for the field placeholders.
- **Poll cadence is per-sensor-type by default too.** `Matmon.Core/Domain/SensorScheduleDefaults` maps each type to a fallback poll interval (ping 30s, http/snmp 60s, ntp 5m, ssl/cert 6h, backup-job 30m, disk-smart 15m, …; `Default` 60s). `SensorPollingService` uses it as the `IsDue` fallback so a sensor with no explicit `PollingInterval` polls at a sane type-specific rate instead of a flat 15s. An explicit schedule on the sensor/its ancestors still wins.
- **Statistics are accurate, downsampled aggregates — not a running average — and are stored per channel.** `SensorStatisticsBucket` carries avg/min/max, the low/high percentile (bottom 1% / top 1%) and a healthy/warning/critical distribution (→ uptime %); `DefaultChannelKey` is the channel identity. `Matmon.Core/Telemetry/TelemetryRollup.AggregatePerChannel` (pure, unit-tested) emits one bucket **per numeric, non-virtual channel** per window (a bare value with no channels folds into a `"default"` bucket); `Aggregate` (single default-channel) is kept for the unit tests. The SQLite `sensor_statistics` PK is `(sensor_id, bucket_minutes, bucket_start, default_channel_key)`; `SqliteTelemetryRepository.MigrateStatisticsToPerChannelKey` rebuilds an older 3-column-PK table once (existing rows keep their channel key, so prior history survives as the then-primary channel). `StatisticsRollupService` (Primary-only, every 5 min) calls `IMonitoringWorkspaceStore.RunTelemetryMaintenance`, which recomputes the recent buckets per sensor/channel from raw data **and** applies all telemetry retention (raw/statistics/events) **plus resolved-alert retention** (keeps every active alert but caps the resolved tail to the newest 500 within the event-retention window, so `_document.Alerts` — Alerta-style persist-until-ack, previously never pruned — and `workspace.json` stay bounded; the AlertRaised/Resolved events keep the audit trail). The Alerts page also renders only active alerts + the newest `ResolvedRenderCap` (200) resolved rows into the DOM (tab counts still use the full set) so a long history doesn't inflate the page. Pruning and aggregation are therefore **off the polling hot path** — `RecordSensorObservation` only appends the raw observation, its state-change event and the alert sync. The SensorDetails Statistics tab shows one channel at a time (the "primary"/graph channel by default) with a **Channel** selector (`StatsChannel`) when a sensor has multiple channels with stats. **Per-channel logging is opt-out:** each channel value carries `SensorChannelValue.LogByDefault` (executors set it `false` for noise like boolean up/valid flags — e.g. SSL `valid`, TCP `open`); the user can override it per channel via a "Log to statistics" checkbox in the Channels & thresholds editor, stored as `MonitoringSettings.ChannelLogging` (channel key → bool, inheritable + trimmed like `ChannelVisuals`). `RunTelemetryMaintenance` reads `GetChannelLogOverrides` and passes it to `AggregatePerChannel`, which skips channels resolving to not-logged (`override ?? channel.LogByDefault`). **Virtual `sensorState` channel:** `SensorExecutionResultHelper.ApplyDefaultChannelSelection` (called centrally in `SensorExecutionService`) prepends a virtual `sensorState` channel to every result (`1` = healthy, `0` = problem, `IsVirtual = true`); it's excluded from the statistics rollup (numeric, non-virtual only) but **is** surfaced in the Channels & thresholds editor as a read-only row — no thresholds, but it can be picked as the **primary/default channel** (→ `MonitoringSettings.DefaultChannelKey = "sensorState"`, honored by `ApplyDefaultChannelSelection`) and given a visual/logging. `WorkspaceSensorChannelThresholdFieldInput.IsVirtual` drives the read-only rendering in `_SensorThresholds` (the `BuildSensorChannelHints` `!IsVirtual` filter was removed; virtual channels sort last).
- **Telemetry now lives in SQLite (Phase A done).** `Matmon.Core/Telemetry` holds `ITelemetryRepository` (storage contract for observations/events/statistics) and the embedded `SqliteTelemetryRepository` (WAL, `Microsoft.Data.Sqlite`). `InMemoryMonitoringWorkspaceStore` delegates all telemetry storage/queries/prune/cleanup to it; the `SensorHistory`/`Events`/`SensorStatistics` collections on `WorkspaceDocument` are kept only as a backup/restore transport and are **always empty in `workspace.json`** (cleared on load). On startup `MigrateDocumentTelemetryIntoRepository` moves any telemetry found in an existing `workspace.json` into `telemetry.db` once (only when the DB is empty), then drops it from the JSON. DB path: `data/telemetry.db` (override `Matmon__TelemetryPath`). The former save bottleneck is gone — telemetry saves no longer re-serialize history. Backup create pulls the selected telemetry sections from the repo into the snapshot; restore pushes them back via `ReplaceAll*`. **Perf:** the repo keeps an in-memory latest-observation-per-sensor cache (`_latestBySensor`), so `GetLatestObservations`/`GetLatestObservation` (dashboard + polling hot paths) never scan the table; WAL is checkpoint-truncated on startup and after bulk imports, with `wal_autocheckpoint` on. Without this the dashboard did a full-table window scan per load (~15s on a real DB).

## Auth & authorization

Cookie auth (`Program.cs`). Roles `Viewer` / `User` / `Admin` (`MatmonUserRole`). Admin-only pages are declared with `AuthorizePage(..., MatmonSecurity.AdminPolicy)` conventions; a global `MatmonPageWriteGuard` MVC filter enforces write protection (POST allowed only on `/Login`, `/Logout`, `/Setup`, `/Alerts` for operators, else Admin). API paths return 401/403 (JSON) instead of redirecting. Passwords hashed via `MatmonPasswordHasher`. Credentials encrypted at rest via ASP.NET DataProtection (`HydrateCredentialBundles` / `ProtectCredentialBundles`).

**First-run setup (`/Setup`).** A fresh install with **no provisioned admin** runs a one-time setup that creates the first admin account (e-mail + password, `MatmonUser.Email`; login matches e-mail *or* username). `IMonitoringWorkspaceStore.IsSetupRequired()` is true while `WorkspaceDocument.SetupCompletedUtc` is null; a Primary-only middleware (before auth, in `Program.cs`) funnels every non-exempt page to `/setup` until done. `CompleteInitialSetup(email, password)` creates the admin + stamps `SetupCompletedUtc`. **No admin is auto-seeded by default** — `MatmonAuthOptions` defaults to empty and the old "fall back to admin/admin" lines are gone; setting `Matmon__Auth__Username/Password` (env) still pre-provisions an admin headlessly and marks setup done. `EnsureDefaultUsers` migrates any **existing** install (already has users) to `SetupCompletedUtc = now` so the wizard never hijacks a configured workspace. The optional setup *wizard* steps (networks / discovery / probes / notifications, skippable) land after account creation — not built yet.

**Credential editor (definition).** Container/host + template credential bundles render as a compact **list** (one row per bundle: name + kind chip + Edit/Delete) with editing in an **overlay modal dialog** (`credential-row` + `credential-modal-*`, `initializeCredentialEditors` in site.js; Add reveals a hidden slot and opens its dialog, a row left blank collapses out). **Every credential kind now has explicit mapped fields** — Windows (`winrm.*`), SSH/Linux (`ssh.*`), Proxmox (`pve.*`), SQL Server (`mssql.*`), SNMP (`snmp.*`), UniFi (`unifi.apiKey`), Generic (`generic.username/password/token`, consumed by the script sensors via the MATMON_* substring resolver). The legacy raw **key=value "Advanced values"** editor was removed app-wide; `ApplyCredentialBundles` starts from the bundle's already-stored values and overlays the explicit per-kind fields (a blank Secret field preserves the stored secret — `ApplyCredentialSecretField` — so dropping the raw editor never wipes data). **Generic fallback:** `MonitoringSettings.ApplyCredentialValuesForKinds` first resolves a bundle of the sensor's expected kind; if none exists it falls back to a **Generic** bundle (the explicitly-selected one when it's Generic, else the first) and maps its `generic.username/password/token` onto the keys the sensor actually reads (Windows→`winrm.*`, SSH/Linux→`ssh.*`, SQL→`mssql.*`, UniFi→`unifi.apiKey` from the token; Proxmox token-auth + SNMP have no mapping). So one shared Generic credential can serve typed sensors that lack a dedicated bundle.

## Configuration (env vars)

All under the `Matmon__` prefix (see `appsettings.json` + README). Common: `Matmon__Mode`, `Matmon__WorkspacePath`, `Matmon__Auth__Username|Password`, `Matmon__HeartbeatIntervalSeconds`. `Matmon__AllowedProgramPaths` (semicolon/newline list) is the allow-list for the **Local Program** sensor — read directly from the env var by `LocalProgramSensorExecutor` (not appsettings), empty by default = nothing runs. Seeding/provisioning flags default to false: `SeedSampleData`, `ProvisionLocalDockerProbe`, `ProvisionDemoSensors`, `AutoCreateProbeSystemSensors`, `CreateStarterMap`. Secondary: `ProbeId`, `ProbeName`, `ProbeToken`, `PrimaryUrl`.

`Dockerfile` at `src/Matmon.Host/Dockerfile` (SDK build → aspnet runtime; installs PowerShell + ssh + NTLM for sensors; binds `:8099`; takes a `MATMON_VERSION` build-arg → env). ## Branches & versioning

- **`main`** = release branch (tagged `latest`); **`dev`** = ongoing work (tagged `nightly`). Day-to-day work happens on `dev`; merge to `main` for releases.
- The build version is shown in the UI (sidebar footer "Matmon &lt;version&gt;", links to `/About`). It is resolved by `Services/MatmonVersion` from the `MATMON_VERSION` env var, which CI bakes into the image: **release** `0.1.<run>-<builddate>` (base from the root `VERSION` file), **dev** `nightly-<run>-<builddate>`. With no env var (plain local/compose build) it falls back to `local-<builddate>` from the assembly timestamp. `builddate` = UTC `yyyyMMdd-HHmm`.

## Conventions

- C# nullable + implicit usings on; modern C# (collection expressions `[]`, records, pattern matching). Keep new code matching the surrounding style.
- Razor Pages, one page = `Xxx.cshtml` + `Xxx.cshtml.cs`. Create/Edit dialogs are the `*Create` / `*Edit` / `*Editor` pages. The sensor editors (SensorCreate, SensorAssistant, ElementEditor, TemplateEditor) share partials to avoid duplication: `Pages/Shared/_SensorThresholds.cshtml` (`@model ISensorThresholdEditor`), `_SensorSchedule.cshtml` (`@model ISensorScheduleEditor`), `_SensorParameters.cshtml` (`@model ISensorParameterEditor`, the structured per-parameter fields — incl. the per-kind render switch, conditional-visibility data and the "Available variables" panel — a sensor-scope template renders the **same** fields, not a raw key=value textarea) and `_SensorCredentials.cshtml` (`@model ISensorCredentialEditor`, the credential selector + credential-kind fields; lives in the dedicated **Credentials** tab). **All four editors now render params + credentials only via these partials** — there is no inline duplication left, so a per-kind case or panel is added in **one** place. The credential-kind fields and general fields share the same `SensorParameterFields` list (each partial renders its subset by index), so binding reconstructs the whole list. Each input model in `Workspace.cshtml.cs` implements those interfaces; render with `Html.PartialAsync(..., new ViewDataDictionary(ViewData){ TemplateInfo = { HtmlFieldPrefix = "<Prefix>" } })`. The schedule editor is mode-based (inherit/every/daily/weekly/monthly) with value+unit intervals and a JS live "next runs" preview (`initializeScheduleEditors` in site.js). **Weekly fires on multiple weekdays** (e.g. Mon + Thu at 05:00): `MonitoringSchedule.DaysOfWeek` (list; legacy single `DayOfWeek` is the fallback via `ResolveDays()`), the editor renders weekday **checkboxes** (`ScheduleDaysOfWeek` on `ISensorScheduleEditor`), and `MonitoringScheduleCalculator` takes the soonest/most-recent occurrence across all selected days. **Defaults are simple** (`SensorScheduleDefaults`): ping = 30s, every other sensor = 5min, with a **hard 15s floor** (`SensorScheduleDefaults.Minimum`) the calculator clamps every interval to.
- **Tabs are app-wide one style.** The canonical tab UI is `.sensor-tabs` / `.sensor-tab` (clean underline, no panel frame) driven by `data-sensor-tabs` (bar) + `data-sensor-tab-target` (button) + `data-sensor-tab="<name>"` (panel); `initializeSensorTabs` in site.js toggles panels scoped to the bar's `closest("form")`. Used by SensorCreate/SensorAssistant, ElementEditor, TemplateEditor (edit mode), Config/System and SensorDetails. The shared `_SensorThresholds`/`_SensorSchedule` partials carry their own `data-sensor-tab` so any page rendering them gets the Thresholds/Schedule tab for free. Don't reintroduce the old boxed `.workspace-tabs` style.
- **Sensor Create/Assistant "preview" re-post recomputes server-side state** (suggested name via `EnsureSuggestedSensorName`, applied template defaults, rebuilt channel/parameter fields). `OnPostPreviewSensorFields` and `OnPostDiscoverSnmp` must `ModelState.Clear()` before `return Page()` — otherwise the `asp-for` tag helpers re-render bound inputs from the posted ModelState and mask the recomputed values (the prefilled name would stay e.g. "Ping 3" after switching the type to HTTP).
- All workspace mutations go through `IMonitoringWorkspaceStore` and must run under its `_gate`; they call `QueueSave(SavePriority.*)`.
- `DashboardSnapshotProvider.CreateSnapshot()` is **heavy** — it clones the workspace twice, builds a telemetry series (graph points) for every sensor and calls `SyncAlerts` (a GET-time mutation). Use it only on the dashboard (`/Index`) and `/api/dashboard`. The shared `_Layout` summary strip uses the cheap `GetWorkspaceSummary()` (topology counts only); never put `CreateSnapshot()` on a path that runs for every page.
- **Alerts are Alerta-style: they persist until acknowledged.** `MonitoringAlert` has `AcknowledgedUtc`, `RecoveredUtc` and `ResolvedUtc` (`IsActive = ResolvedUtc is null`). Recovery does **not** silently close an unacknowledged alert: `MarkAlertsRecoveredForElement` (poll path) and the recovery branch of `SyncAlerts` (dashboard) only set `ResolvedUtc` when the alert is already acknowledged; otherwise they set `RecoveredUtc` and keep it active (shown in the Open list with a "Recovered" pill). Acknowledging a recovered alert resolves it (`AcknowledgeAlert`). A re-alarm clears `RecoveredUtc`. Pausing a sensor still resolves outright via `ResolveAlertsForElement`.
- Keep the build green (`dotnet build Matmon.slnx`) after each change.
