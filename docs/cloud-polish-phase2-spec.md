### 3. Bekannte Fallen (jede hat schon einmal Zeit gekostet)

- **HttpClient-Timeout = `TaskCanceledException : OperationCanceledException`.** In Background-Loops **immer** `catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)` — ein nackter `catch (OperationCanceledException) { break; }` beendet die Schleife beim ersten Timeout (das war die Ursache für „Instanz immer wieder offline").
- **Git Bash mangelt Pfade:** bei `--tmpfs /app/data` o. ä. `MSYS_NO_PATHCONV=1` voranstellen.
- **`sleep N` im Vordergrund ist blockiert** → `run_in_background` oder until-Schleifen mit Zeitlimit.
- **`docker compose up --build cloud` verwirft den manuell gesetzten Alias `matmon-cloud`** → Instanz-Heartbeat meldet „Name or service not known" → Alias neu setzen (§2).
- **Cloud-Cookie-Namen sind `.Matmon.Cloud.*`** (Auth, Antiforgery, TempData, Pending2fa). `TunnelProxy` strippt genau dieses Präfix. Neue Cloud-Cookies **müssen** das Präfix tragen.
- **Cloud `[TempData] string` nie mit GUID-Strings befüllen** (Serializer castet zurück nach `Guid` → `InvalidCastException`); Property als `Guid?` typen.
- **Razor Pages Query-Key `page` ist reserviert** — Server-Paging nutzt `p`.
- **Cloud DataProtection-Keys liegen im Volume `matmon-cloud-keys`** — Container ohne dieses Volume starten = alle Sessions ungültig.
- **Ein fresh gebautes Instanz-Image trägt ein gebackenes `/app/data/workspace.json`** aus `src/Matmon.Host/bin/Debug/net10.0/data/` im Build-Kontext (Build-Hygiene-Backlog). Für Wegwerf-Instanzen `--tmpfs /app/data` + `Matmon__Auth__Username/Password`.
- **`workspace.json`-Mutationen nur unter `_gate` + `QueueSave(SavePriority.*)`.** Lesen über die geklonten Accessoren (`GetAllElements` etc.), nicht am Live-Baum arbeiten.
- **Sensor-Editoren rendern Parameter in ZWEI Listen** (Credentials + General) — neue Fälle in die General-Liste.
- **Antiforgery in Razor Pages ist automatisch** — kein manuelles CSRF-Handling nötig (2026-07 verifiziert).
- **Nach dem Cloud-Deploy von `86b48ee` müssen sich alle Cloud-User einmal neu anmelden** (Auth-Cookie umbenannt). Bei weiteren Cookie-Umbenennungen den User vorher informieren.

### 4. Workflow pro Finding / Arbeitspaket („Definition of Done")

1. **Finding lesen, Code an `Datei:Zeile` öffnen und die „Verified reason" gegen den aktuellen Stand prüfen.** Zeilen können sich seit dem Audit leicht verschoben haben; ist das Problem bereits weg → als „no change needed" berichten, nicht blind ändern.
2. **Fix umsetzen wie unter „Fix" beschrieben** (Abweichungen sind erlaubt, wenn sie begründet werden). Bestehende Muster verwenden. Keine Funktionalität „nebenbei" umbauen.
3. **Tests:** für reine Logik (Core, Services ohne DB) Unit-Tests in `Matmon.Tests` / `Matmon.Cloud.Tests` ergänzen. Für DB-/UI-Pfade: lokaler Smoke (§2) mit `curl`, `docker logs`, psql.
4. **Build + alle Tests grün** in jedem betroffenen Repo (`dotnet build` + `dotnet test`). Warnungen aus neuem Code beseitigen.
5. **Lokale Stacks neu bauen** (§2) und den Fix **einmal real ausführen** (z. B. Deaktivieren → Tunnel geschlossen; Passwort-Backup planen → Blob in der Cloud „encrypted"). Ergebnis notieren.
6. **Doku:** Matmon-`CLAUDE.md` (Abschnitt „Configuration → Matmon.Cloud link", „Full Access", „Persistence → Cloud backup", „Licensing") anpassen; Cloud-`README.md`/`docs/` wenn ein Cloud-Konzept betroffen ist.
7. **Commit pro Finding oder pro eng zusammenhängender Gruppe**, Conventional-Commits-Stil mit Finding-ID im Body, z. B.:
   ```
   fix(cloud): close a live Full Access tunnel on Disconnect/Deactivate/Delete

   P2/link-tunnel-1, P2/product-polish-crosscut-1
   ```
   Kein Attributions-Trailer (Regel 1).
8. **Push:** `git push origin dev` && `git push origin dev:main` (beide Repos, falls beide geändert).
9. **Bericht nach §6.**

#### WP1 — Lifecycle-Konsistenz: Disconnect / Deactivate / Delete beenden auch den Tunnel; Rollen propagieren

**Findings:** `P2/cloud-customer-admin-lifecycle-1`, `P2/cloud-customer-admin-lifecycle-2`, `P2/link-tunnel-1`, `P2/product-polish-crosscut-1` (gleicher Fix wie link-tunnel-1), `P2/link-tunnel-2`.

**Design:**

1. **Cloud `TunnelRegistry.CloseAsync(Guid instanceId, string reason)`** (`src/Matmon.Cloud.Api/Services/TunnelRegistry.cs`): Verbindung aus `_connections` nehmen, `Socket.CloseAsync(NormalClosure, reason)` best-effort (Timeout 3 s), alle `Pending`-TCS mit einem Fehler abbrechen. Idempotent (kein Eintrag → no-op). Sollte `RunAsync` die Verbindung beim Beenden selbst entfernen, muss `CloseAsync` damit koexistieren (TryRemove).
2. **Aufrufer in `InstanceService`** (`src/Matmon.Cloud.Api/Services/InstanceService.cs`): `DisconnectAsync` (Z. ~1031), `SetDisabledAsync(id, true)` (~786), `DeleteAsync` (~608) + Admin-Delete, `PurgeAsync` (~1071), sowie der Lizenzpfad, wenn `LicenseTunnelEnabled` auf `false` wechselt (`ApplyTemplateSnapshot`). `TunnelRegistry` ist ein Singleton ohne Abhängigkeiten → einfach injizieren (kein DI-Zyklus).
3. **Browser-Routen re-checken** (`Program.cs` `app.Map("/instances/{instanceId:guid}/app/{**path}", …)` ~Z. 718 und `/embed/…` ~743): vor dem Forward die Instanz per PK laden (Standard-Query-Filter blendet gelöschte aus → 404) und `Disabled` / `!LicenseTunnelEnabled` → kleine HTML-Antwort 403 „This instance is deactivated / Full Access is not licensed". Ein PK-Lookup pro Request ist okay (ggf. 30 s Memory-Cache).
4. **Deactivate = bewusster Admin-Akt, kein Ausfall:** `SetDisabledAsync(true)` setzt zusätzlich `OfflineNotified = true` und `OnlineUntilUtc = null` (verhindert die Dead-Man-Mail) und schreibt einen `AccountLog`-Eintrag (`Kind = Instance`, „Deactivated by platform admin <email>"); `SetDisabledAsync(false)` setzt `OfflineNotified = false`. **UI:** Admin/InstanceDetail-Button mit Bestätigungsdialog (Muster: bestehende `confirm`-Buttons in `cloud.js`). Kunden-Oberflächen (Instances-Liste, Instanz-Seite, Console-Summary, Alerts-Dashboards) zeigen bei `Disabled` ein **„Deactivated"**-Badge statt „Offline" — eine kleine Helper-Funktion `InstanceStatus For(instance, now)` → `Online | Offline | Deactivated | Disconnected` und überall benutzen.
5. **Instanz sieht, dass sie deaktiviert wurde:** Heartbeat-Endpoint der Cloud (`/api/instances/{id}/heartbeat`) antwortet bei gültigem Token aber `Disabled` mit **403 `{ "error": "instance_deactivated" }`** statt 401 (401 bleibt für ungültigen Token). Instanz `CloudConnectionService.SendHeartbeatAsync` mappt 403+Body auf den Status „deactivated by cloud administrator" (Anzeige in System → Cloud; siehe auch WP5).
6. **„Remove instance" ehrlich machen** (`Pages/Members.cshtml(.cs)` Owner-Aktion): umbenennen in **„Delete instance"**, Bestätigungsdialog mit den realen Folgen (Instanz wird ausgeblendet + deaktiviert, der laufende Host verliert die Verbindung (401), eine gemountete Lizenz wird gekündigt, nur ein Plattform-Admin kann wiederherstellen). Hilfetext entsprechend.
7. **Rollen-Propagation SSO-only** (`src/Matmon.Host/Services/InMemoryMonitoringWorkspaceStore.cs` `UpsertCloudUser`, Z. ~250): Wenn `existing.CloudLinked && string.IsNullOrEmpty(existing.PasswordHash)` (reiner SSO-User) → `existing.Role = role` übernehmen (+ `UpdatedUtc`), sonst lokale Rolle behalten. `TunnelAutoLogin` baut den Principal aus dem Rückgabewert → wirkt sofort pro Request. In `CLAUDE.md` unter „Cloud SSO" den Satz ergänzen.

**Abnahme:** (a) Admin deaktiviert eine Instanz mit offener Console → Iframe zeigt binnen 1 s die 403-Seite, `TunnelRegistry.IsConnected` = false, in `docker logs matmon-primary-1` „tunnel closed by cloud: deactivated"; **keine** „instance offline"-Mail (smtp4dev/Spooler leer); Kundenliste zeigt „Deactivated"; Instanz System → Cloud zeigt „deactivated by cloud administrator". (b) Reaktivieren → Tunnel verbindet innerhalb ≤ 30 s neu, Status wieder ok. (c) Owner-Disconnect vom Cloud-UI → Tunnel zu, Instanz meldet „unauthorized". (d) Cloud-Rolle Owner→Viewer für einen SSO-only-User → nächster Console-Request auf der Instanz hat Viewer (Schreib-Buttons weg). Lokaler User mit Passwort behält Rolle. **Tests:** `Matmon.Tests`: Store-Test für Punkt 7 (SSO-only wird herabgestuft, lokaler User nicht). `Matmon.Cloud.Tests`: `TunnelRegistry.CloseAsync` idempotent + bricht Pending ab (mit einem Fake-WebSocket oder über die öffentliche API prüfbar).

#### WP2 — Link-/Tunnel-Status sichtbar und robust; kein Save-Sturm durch Heartbeats

**Findings:** `P2/link-tunnel-3`, `P2/product-polish-crosscut-2` (gleicher Fix), `P2/link-tunnel-4`, `P2/link-tunnel-5`, `P2/link-heartbeat-status-1`, `P2/link-license-partner-backup-6` (gleicher Fix wie heartbeat-status-1).

**Design (alles Instanz, außer dem Cloud-Keep-Alive):**

1. **`TunnelState` Singleton** (`src/Matmon.Host/Services/TunnelState.cs`, neu): `Enabled`, `Connected`, `ConnectedSinceUtc`, `LastAttemptUtc`, `LastError` (Kurztext + HTTP-Status, falls Handshake 401/403), `ConsecutiveFailures`, `RequestsServed`, `LastRequestUtc`. `TunnelClient` (`Services/TunnelClient.cs`) aktualisiert ihn an allen Übergängen. **Anzeige** in `Pages/Config.cshtml` Cloud-Tab, Block „Full Access": „Connected since …" / „Not connected — last error: … (retrying)" / „Disabled" — im bestehenden `<dl class="config-list">`-Stil. Zusätzlich im Cloud-Tab der **Heartbeat-Status typisiert** (statt String „ok"): `Ok | Failed | Unauthorized | Deactivated | Disabled` + **Staleness**: wenn `now - LastOkUtc > 3 × Intervall` → Warn-Chip „link degraded — last successful heartbeat X min ago".
2. **Logging + Backoff im `TunnelClient`:** Verbindungsfehler/Drops von `LogDebug` (Z. 83/194/213) auf `LogInformation` (erster Fehler) und `LogWarning` ab 3 Fehlern in Folge; 401/403 beim Handshake als eigener Text („cloud refused tunnel: unauthorized / not licensed"). Reconnect-Backoff 5 s → 10 → 20 → 40 → 60 s (Cap) mit Jitter, Reset nach erfolgreichem Connect. Zuerst prüfen, ob um Z. 300–315 (`Task.Delay(delay, …)`) bereits ein Backoff existiert und diesen erweitern statt duplizieren.
3. **WebSocket Keep-Alive:** Instanz `ClientWebSocket.Options.KeepAliveInterval = 20 s` und `KeepAliveTimeout = 20 s` (beides in .NET 10 vorhanden) in `RunTunnelAsync`; Cloud `app.UseWebSockets(new WebSocketOptions { KeepAliveInterval = 20 s, KeepAliveTimeout = 20 s })` in `Program.cs`. Ergebnis: ein halboffener Tunnel wird nach ≤ ~40 s erkannt und neu aufgebaut.
4. **Replay-Größencap** in `TunnelClient.ReplayAsync`: Antwort-Body beim Lesen zählen; über **20 MB** → `TunnelResponse(request.Id, 413, …, "This response is too large for Full Access. Download it directly on the instance.")` statt Puffern/Base64. Cloud-seitiges Message-Limit (32 MB in `TunnelRegistry`) unverändert lassen und die Konstante kommentieren, damit beide zusammenpassen.
5. **Heartbeat-Status nicht mehr in `workspace.json` schreiben:** `CloudConnectionState.LastStatus/LastHeartbeatUtc` werden **nur noch im Speicher** gehalten (neuer Singleton `CloudLinkStatus` oder im `CloudConnectionService` exponiert; die Config-Seite liest daraus). `UpdateCloudConnection` (Store Z. ~1340, `QueueSave(Configuration)`) darf nur noch persistieren, wenn sich **Identität** ändert (`InstanceId`/`CloudUrl`) — Ist-Zustand: jeder Beat (alle 15–30 s) serialisiert das gesamte Dokument inkl. Re-Protect aller Secrets. **Lizenz-Token** (`SetLicenseToken`, Z. ~1478): nur persistieren, wenn sich die **verifizierte `LicenseInfo` ohne `iss`/IssuedAt** vom gecachten Token unterscheidet **oder** der letzte persistierte Token älter als 6 h ist (damit ein Neustart nie ohne aktuellen Token dasteht). `SetServicePartnerInfo` hat bereits `ValueEquals` — so lassen. **Zusätzlich prüfen** (aus `link-license-partner-backup-6`): ob `SaveDocumentLocked` beim `ProtectNotificationSecrets` die Live-Plaintext-Secrets kurzzeitig nullt, die der `NotificationDispatchService` ungeklont liest — falls ja: vor dem Serialisieren einen Klon protecten, nicht das Live-Dokument.

**Abnahme:** (a) Full Access an, Cloud-Container stoppen → Config-Seite zeigt binnen ≤ 40 s „Not connected — last error …", `docker logs` zeigt Information/Warning; Cloud wieder starten (+ Alias!) → „Connected since" innerhalb ≤ 60 s. (b) Reverse-Proxy-Simulation: `Matmon__CloudUrl` auf eine http-URL zeigen, die keine WS-Upgrades kann → klarer Fehltext statt Stille. (c) `stat`/`docker exec … ls -l --time-style=full-iso /app/data/workspace.json` über 5 Minuten bei ruhigem System: **keine** Änderung der mtime durch Heartbeats (vorher: alle 30 s). (d) Datei > 20 MB über die Console laden → 413-Seite, Console-Tunnel bleibt für andere Nutzer offen. **Tests:** Pure-Logik für Backoff-Reihe + Staleness-Berechnung (`Matmon.Tests`); Lizenz-„changed ignoring iss"-Vergleich (`LicenseCrypto`-Payload ist in Core testbar).

#### WP3 — Backup/Restore als Produktschicht (portabel, ehrlich, mit Zahlen)

**Findings:** `P2/link-license-partner-backup-1`, `-2`, `-3`, `-4`, `-7`, `-8` + der Report „nach Wizard-Restore fehlten Probes" (kein Code-Pfad gefunden → Zähler/Logging als Diagnose).

**Design:**

1. **Geplante Cloud-Backups mit Passphrase** (Instanz): `WorkspaceBackupJob` (`src/Matmon.Core/Domain/WorkspaceBackup.cs`) bekommt `ProtectedPassphrase` (Ciphertext, persistiert) + `[JsonIgnore] Passphrase` (transient). Hydrate/Protect im Store nach dem Muster der Notification-Secrets (`HydrateNotificationSecrets`/`ProtectNotificationSecrets`, Purpose z. B. `"backup-passphrase"`). `Pages/BackupJobEditor` zeigt bei Destination = Cloud ein Passphrase-Feld (leer = unverändert, Checkbox „clear"). `BackupSchedulerService` reicht die Passphrase an `CreateBackupBytes(sections, reason, passphrase)` weiter; das Label bekommt dieselbe „(encrypted)"-Markierung wie der manuelle Pfad (`Config.OnPostCloudBackupNowAsync`).
2. **Cloud `CloudBackup` bekommt `Kind` (int: `0 Manual`, `1 Scheduled`) und `Encrypted` (bool)** → Migration `AddCloudBackupKind`. `POST /api/instances/{id}/backups` (`Program.cs` ~Z. 590–615) liest `?kind=&encrypted=` (Default manual/false für alte Instanzen). **Retention: newest 10 pro `Kind`** statt gesamt (Z. ~603–612), damit ein manuelles DR-Backup nicht vom Tages-Job verdrängt wird. Backups-Seiten (`/backups`, Instanz-Seite, Wizard-Liste der Instanz) zeigen Kind + Schloss-Icon. Instanz `Services/CloudBackupClient.PushAsync` sendet beide Query-Parameter; `WorkspaceBackupJob`-Läufe = `scheduled`.
3. **Datei-Restore honoriert `SecretsPortable`:** aus `RestoreBackupBytes` (Store `.Backup.cs` Z. ~352–380) die Protector-Auflösung in `private IDataProtector ResolveSecretProtector(BackupPackage package, string? passphrase)` extrahieren (Verifier prüfen; fehlende/falsche Passphrase → aussagekräftige `InvalidOperationException`) und **auch** in `RestoreBackupSnapshot(fileName, sections, passphrase?)` (Z. ~286) verwenden. `Pages/BackupRestore` erkennt über `FindBackupSnapshotDetails` ein portables Paket und zeigt das Passphrase-Feld.
4. **Restore-Ergebnis mit Zahlen + Verlusten:** `WorkspaceBackupRestoreResult` erweitern um `Probes`, `Sensors`, `Templates`, `Rules`, `Users` (gezählt **nach** `ApplyBackupSections`) und `DroppedSecrets` (Liste: Bundle-/Sender-Name, Grund). Die vier Hydrate-Methoden sammeln Fehler in eine Liste statt nur zu loggen. UI-Ausgabe in Config → Backup-Tab, `BackupRestore` und **Wizard-Restore-Schritt**: „Restored 3 probes, 42 sensors, 5 templates, 2 rules. ⚠ 2 credentials could not be decrypted (SNMP ‚core-switch', SMTP sender) — re-enter them." Zusätzlich ein `LogInformation` mit denselben Zahlen (Diagnose für den Probe-Report).
5. **Normalisierer nach Restore:** Alle Post-Load-Schritte aus `.Persistence.cs` (`NormalizeLoadedDocument`, `EnsureSensorDefinitionCatalog`, `MigrateRetiredProxmoxSensors`, `MigrateAppliedTemplatesToCopies`, `EnsureDefaultNotificationConfiguration`, `EnsureDefaultUsers`, … — die vollständige Liste aus `LoadDocument`/Konstruktor lesen) in **eine** Methode `NormalizeDocumentLocked(WorkspaceDocument)` bündeln und sowohl beim Laden als auch am Ende von `ApplyBackupSections`/vor dem Save des Restores aufrufen. Achtung auf Schritte, die nur einmalig laufen dürfen (Telemetrie-Migration) — die bleiben im Ladepfad.
6. **Passphrase-Mindestlänge 12** serverseitig in `CreateBackupBytes` (nicht-null + < 12 → `ArgumentException`) und in beiden UIs (`minlength="12"` + Hinweis). **Restore** akzeptiert weiterhin jede Länge (ältere Pakete).

**Abnahme:** (a) Cloud-Job mit Passphrase anlegen → nächster Lauf erscheint in der Cloud mit Kind = scheduled, encrypted = true; Wizard-Restore auf einer Wegwerf-Instanz (`--tmpfs /app/data`) mit dieser Passphrase → Credentials funktionieren (ein Sensor mit Credential läuft grün). (b) 11 geplante Läufe verdrängen **nicht** ein manuelles Backup.
